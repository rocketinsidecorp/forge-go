# Security Policy

## Supported versions

Forge is pre-release. Only the `main` branch receives security fixes. Once
versions are tagged, this section will list the supported release lines.

## Reporting a vulnerability

Do not open a public issue for a suspected vulnerability.

Report it privately through GitHub's **Report a vulnerability** form on the
repository's **Security** tab
(`github.com/rocketinsidecorp/forge-go/security`). If private reporting is not
available, contact the maintainer through their GitHub profile and ask for a
private channel before sharing details.

Please include:

- affected package, command, or generated file;
- Forge version or commit (`forge version`);
- steps to reproduce or a proof of concept;
- impact as you understand it.

You will receive an acknowledgement, and fixes are coordinated with the
reporter before public disclosure. There is no bug bounty.

## Scope

In scope:

- framework packages in this repository, including the database adapters
  (`postgres`, `mysql`, `sqlite`), their test packages, `sqldb`, and
  `migrate`;
- the `forge` CLI, including files generated by `forge new` (Dockerfile,
  Compose file, CI workflow, Dependabot configuration, env files,
  application skeleton);
- the migration runner and the `migrate`/`rollback` commands;
- insecure defaults.

Out of scope:

- vulnerabilities in application code written by Forge users, including SQL
  they write;
- deployments that override defaults in ways the documentation warns against
  (for example, exposing a `trusted-proxy` container directly to clients, or
  setting `FORGE_DATABASE_ALLOW_PLAINTEXT=true` on an untrusted network);
- issues in the Go toolchain, the database drivers (pgx,
  go-sql-driver/mysql, modernc.org/sqlite), the database servers, Docker, or
  base images, which
  should be reported upstream.

## Security defaults

The design and its assumptions are documented in
[docs/THREAT_MODEL.md](docs/THREAT_MODEL.md). Summary:

- configuration is validated at startup; `production` refuses plain HTTP;
- in `production`, PostgreSQL connections must use `sslmode=verify-ca`
  or `verify-full` (prefer `verify-full`; `require` is rejected) and MySQL/MariaDB
  connections `tls=true`, unless `FORGE_DATABASE_ALLOW_PLAINTEXT=true` is set;
- the database URL is a redacted secret in logs, formatted output, and
  JSON; configuration errors never echo values; `forge doctor` drops the
  password and all query parameters except `sslmode`;
- connection URLs cannot inject driver options or pragmas: the MySQL driver
  configuration is built field by field and accepts only `tls`; SQLite URLs
  accept no parameters and the path is percent-encoded;
- MySQL multi-statement execution is enabled only for migrations, never on
  the application pool, and every MySQL/MariaDB connection runs with a
  strict `sql_mode`, `utf8mb4`, and UTC;
- SQLite files are created `0600` in a `0750` directory, with foreign keys,
  defensive mode, and no double-quoted string literals;
- HTTP timeouts, header size limit, and body size limit are always set,
  database connections have a server-side statement timeout of at least 1ms
  where the database supports one, and each readiness check has a timeout;
- security headers on every response, HSTS when TLS is in effect;
- errors reach clients only as a stable code and message; database errors
  are translated so SQL, constraint names, and values are not exposed;
- panics are recovered without leaking stack traces to clients;
- request paths with traversal segments or encoded slashes are rejected;
- bearer sessions use 256-bit random opaque tokens and persist only their
  digest; authentication accepts exactly one Bearer header and resolves
  current membership and permissions server-side;
- tenancy has no default; PostgreSQL tenant operations use transaction-local
  context for RLS so the tenant cannot leak through the connection pool;
- migrations are embedded SQL; their up scripts are checksummed when
  applied, runs are serialized across processes with a database lock (or,
  for SQLite, an operating-system file lock), and the migrator refuses to run over modified or unknown migrations;
- env files are ignored by git (except the committed, secret-free
  `.env.development`) and never copied into images;
- database tests run in a fresh database (or SQLite file) each, and CI fails
  rather than skipping them when a test server is missing;
- the generated container is static, distroless, and runs as nonroot;
- core packages have no third-party Go dependencies (enforced by a test);
  each database adapter depends on its driver, and an application links only
  the one it imports; `govulncheck` runs in CI and
  Dependabot checks dependencies weekly.

## Checks for contributors

```sh
go vet ./...
golangci-lint run
go test -race ./...    # set FORGE_TEST_POSTGRES_URL / FORGE_TEST_MYSQL_URL to include server tests
govulncheck ./...
```
