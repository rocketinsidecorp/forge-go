# ADR 0041: Model, controller, mailer and queue job generators, and `forge destroy`

- **Status:** Accepted
- **Date:** 2026-10-20

This decision is language-neutral: Forge-Go and Forge-Rust ship the same
commands, arguments, flags, file roles and printed wiring, and differ only in
the language of the generated code (see [Forge-Rust port](#forge-rust-port)).

## Context

`forge generate` offered a migration, a view, a recurring job stub, a JSON
resource, an HTML scaffold and the sign-in pages. The parity matrix
([Rails parity](../RAILS_PARITY.md)) listed the rest of `rails g`, the
controller, model and mailer generators, as missing, and there was no
`rails d` to undo a generation.

## Decision

1. **One generator toolkit, not a framework.** The new generators reuse the
   field parser, the naming rules, the all-or-nothing, refuse-to-overwrite
   file plan, the symlink checks, the declaration-conflict check and the
   printed-wiring convention of `resource` and `scaffold`. A model *is* the
   resource's model and persistence layers: the same templates, minus the HTTP
   adapter (so its files equal a resource's, byte for byte). No generator edits
   `app/bootstrap/bootstrap.go`; each prints the imports and lines to paste.
2. **Controllers are read-only and guarded.** A controller has no model, so
   its actions are `GET` pages (HTML) or `GET` JSON handlers (`--api`, like
   `forge new --api`). `create`, `update` and `destroy` are refused with a
   pointer to `scaffold`, which owns forms, CSRF and optimistic locking. The
   routes are never public unless `--public` says so: `Register...` demands a
   guard, the printed guard denies everyone until written (without Forge
   identity) or checks `NAME:read` (with it, and a migration registers that
   permission). Routes use literal patterns so `forge routes` lists them.
3. **Mailers are typed and fail closed.** One type per mailer, one method and
   one data struct per email, text and HTML templates under
   `app/mailers/templates/NAME/`, previews as `mail.Preview` values served only
   when `FORGE_MAIL_PREVIEW=true` in development or test. Template data fields
   are strings: rich types are an edit to the generated struct. The printed
   wiring starts the application without mail configured and makes every send
   fail with `mail.ErrNotConfigured` and a start-up warning, rather than
   pretending to send or refusing to boot.
4. **`generate job --queue` is a new mode, not a new default.** `forge generate
   job NAME` keeps generating the scheduler stub (documented, in use). `--queue`
   generates a typed handler for the persistent queue with its enqueue
   function; the placeholder returns a permanent error so the job is dead and
   visible instead of silently succeeding.
5. **`forge destroy` regenerates instead of keeping a manifest.** It takes the
   arguments of the generate command, renders what the generator would write
   and removes a file only while it is byte-identical. This needs no metadata
   in the application, works for files generated by earlier versions, and
   makes "refuse if modified" an exact comparison. Migrations are kept unless
   `--migrations` (a migration that ran is history); shared files (views base,
   live-update transport) are never planned for removal; nothing is removed
   through a symlink; `--force` overrides only the modification check.
6. **Names are validated before anything is built.** All names and fields are
   strict snake_case, bounded in length, and checked against Go keywords, file
   name build-constraint suffixes and reserved paths, so they cannot inject
   into Go identifiers, SQL, file paths or templates.

## Consequences

- `forge destroy` cannot find what it cannot regenerate: if the arguments
  differ from the original, files that differ are listed (or, if they do not
  exist, skipped) and nothing is removed.
- A destroyed generation leaves its kept migrations behind until
  `forge rollback` and `--migrations`; generating again meanwhile is refused.
- The mailer previews are compiled into the binary and are only reachable
  through the explicit development opt-in.

## Forge-Rust port

Same commands (`generate model|controller|mailer|job --queue`, `destroy`), same
argument grammar and flags, same file roles (domain, application, persistence;
handlers, views and routes; mailer, templates, previews; job handler and
enqueue function), same guard and permission names (`NAME:read`), same
`/_mail/NAME/` preview prefix, same refusal of write actions in controllers and
the same destroy rules. The Rust port keeps its own idioms (typed handlers,
compile-time checked templates, its own queue and mail crates) and its
own tests that generate into a fresh application and run `cargo fmt`, `clippy`
and `cargo test` on the result.
