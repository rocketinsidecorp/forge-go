# ADR 0024: Mail

- **Status:** Accepted
- **Date:** 2026-10-14

## Context

Applications need to send email: password recovery today, notifications and
receipts next. Rails' Action Mailer is the reference experience (mailer
classes, templates, previews, a test delivery list), but it inherits Ruby's
weaknesses: header values are validated late and inconsistently, SMTP
defaults to opportunistic TLS, and the delivery path trusts the template
output. Forge should offer the same ergonomics with the failure modes closed:

- an email built from untrusted input must not be able to inject headers,
  recipients or MIME parts;
- production must never send credentials or mail in clear text by accident;
- a template error must never produce a half-rendered email;
- the framework must stay stdlib-only in its core (ADR 0006) and must not
  choose an email provider (ADR 0013).

## Decision

### Package layout

| Package | Role | Imports |
|---------|------|---------|
| `mail` | `Message`, `Address`, `Encode`, `Sender` port, SMTP sender, development file sender, `Template`, preview handler, `FromConfig` | stdlib, `config`, `fault`, `uuid` |
| `mail/mailtest` | in-memory recorder (`ActionMailer::Base.deliveries`) | stdlib, `mail` |
| `auth/recoverymail` | adapter implementing `auth.RecoverySender` | stdlib, `auth`, `mail` |

`mail` and `mail/mailtest` are core packages. The adapter is a separate
package so neither `auth` nor `mail` depends on the other.

### Messages are data, validated at the boundary

`mail.Message` is a plain struct. Every sender calls `mail.Encode`, which
validates and renders RFC 5322/MIME, so there is no path from a `Message` to a
transport that skips validation (the test recorder runs it too).

- Control characters (CR, LF, NUL, all of C0/C1, DEL, U+2028/2029) and
  bidirectional overrides and isolates (U+202A-202E, U+2066-2069, U+200E/F,
  U+061C) are rejected in every header-bound string: display names, subject,
  extra header values, content types, content IDs, file names. Errors name the field and
  rule, never the value, so they cannot be used to forge log lines.
- Addresses are `net/mail`-parsed **and** restricted: ASCII dot-atom local
  part, LDH domain, one `@`, 254 bytes. Quoted local parts, comments, route
  addresses, domain literals and display-name forms in the address field are
  rejected, which removes the ambiguity used to smuggle extra recipients or SMTP
  commands. The rules live once, in `config.ValidateMailbox`, and are applied
  both by `mail` and by `FORGE_MAIL_FROM` validation.
- **Known limitation: no SMTPUTF8 and no IDNA.** An address with non-ASCII
  characters in the local part or domain (`joao@exemplo.com.br` is fine,
  `joão@exemplo.com.br` and `user@exämple.com` are not) is rejected with the
  distinct fault `mail_address_unsupported` (`mail.ErrAddressUnsupported`),
  never silently converted: an automatic punycode conversion could deliver to
  a different mailbox. Display names may be any Unicode. `auth` no
  longer provisions or signs in such logins (`auth.CanonicalLogin` refuses
  non-ASCII, see docs/AUTHENTICATION.md), so the failure is visible only for
  accounts stored before that rule, and `recoverymail` logs
  `code=mail_address_unsupported` for them. Supporting them needs IDNA
  (`golang.org/x/net/idna`, a third-party module) and SMTPUTF8 negotiation, and
  is future work.
- Non-ASCII subjects and names are RFC 2047 encoded. Plain ASCII text that
  contains `=?` is encoded too (whole value, base64 words), because a client
  would otherwise decode a hand-written `=?utf-8?b?...?=` into attacker-chosen
  text. Long headers are folded below 78 columns; folding never produces a
  whitespace-only line or a line ending in whitespace (a gateway that trims
  trailing whitespace would otherwise turn the line into the blank line that
  ends the header block).
- Extra headers come from an allow-list (`List-Unsubscribe`,
  `List-Unsubscribe-Post`, `List-Id`, `Auto-Submitted`, `Precedence`,
  `In-Reply-To`, `References`), printable ASCII only. `Bcc`, `To`, `Subject`,
  `Content-*`, `Message-ID`, `Return-Path` and anything unknown are rejected.
- `Bcc` recipients exist only in the SMTP envelope. A header named Bcc is
  never written.
- Limits: subject 255 runes, 100 recipients, 2 MiB per body, 10 attachments,
  7 MiB each, 10 MiB of content in total, about 13.7 MB once base64 encoded
  (all overridable with `WithLimits`). The encoder holds a message in memory;
  attachments are base64-encoded straight into the output buffer (about 1.4
  times the attachment size, plus the result), so concurrent sends multiply the
  figure and large files belong behind links.
- Attachment file names are reduced to a base name; names with control
  characters or bidirectional overrides (`invoice, U+202E, fdp.exe`) are rejected;
  MIME types `multipart/*` and `message/*` are rejected; non-ASCII names use
  RFC 2231 parameters.
- `Date` is UTC. `Message-ID` is `<UUIDv7@sender-domain>` (ADR 0001), unique
  and time-sortable for log correlation.
- Structure: `text/plain`; `text/html`; `multipart/alternative` (text first,
  HTML last); inline images (`ContentID`) in `multipart/related` around the
  HTML; attachments in `multipart/mixed`. Bodies are quoted-printable UTF-8,
  attachments base64, output is 7-bit with CRLF line ends and unguessable
  128-bit boundaries.

### SMTP: secure by construction

`mail.SMTPSender` is built on `net/smtp` over a connection the sender dials
itself (`net.Dialer.DialContext`, `tls.Dialer`), so deadlines and cancellation
are enforced by closing the connection (`context.AfterFunc`).

- `smtp://` (port 587) requires STARTTLS; `smtps://` (465) uses implicit TLS.
  If the server does not advertise STARTTLS the send is refused
  (`ErrTLSRequired`) before AUTH, MAIL or DATA. A stripped STARTTLS
  advertisement therefore cannot downgrade the connection.
- Certificates are always verified, TLS 1.2 minimum. There is no option to
  skip verification. Private relays are trusted through `RootCAs` /
  `FORGE_MAIL_TLS_CA_FILE`.
- AUTH PLAIN (or LOGIN when PLAIN is not offered) is produced only on a TLS
  connection; the mechanism guard sits in the `smtp.Auth` implementation so it
  holds even though `net/smtp.PlainAuth` would send credentials in clear to
  localhost.
- `AllowPlaintext` is the only escape hatch, and it covers the **message**,
  never the **password**. It permits proceeding without STARTTLS (a trusted
  network, a development server); when STARTTLS is offered it is still
  attempted and verified, and a TLS failure never falls back to plaintext.
  SMTP AUTH is sent without TLS only to a loopback host (`localhost`,
  127.0.0.0/8, `::1`), even with `AllowPlaintext`; to any other host the send
  fails with `ErrAuthFailed` before the password leaves the process.
  Production configuration validation rejects `FORGE_MAIL_ALLOW_PLAINTEXT=true`
  together with credentials for a non-loopback host. The analogy with
  `FORGE_DATABASE_ALLOW_PLAINTEXT` does not hold here: PostgreSQL's SCRAM and
  MySQL's challenge-response keep the password off the wire even on a clear
  connection, whereas SMTP PLAIN/LOGIN transmit it, and an on-path attacker can
  trigger that by stripping the STARTTLS advertisement.
- Delivery is all-or-nothing at the envelope: a refused recipient aborts before
  `DATA` (`ErrRejected`), so there is no surprise partial delivery.
- One connection per message. Pooling is rejected: stale pooled connections are
  a classic source of lost and duplicated mail, and volume belongs behind a
  queue.
- `QUIT` failure after the server accepted `DATA` is ignored so a delivered
  message is never reported as failed (which would cause a retry duplicate).
- Errors are `fault.Error`s: `ErrUnavailable` (retryable: network, timeout,
  4xx, cancellation; a timeout always wraps `context.DeadlineExceeded`),
  `ErrRejected` (other 5xx; category unavailable, HTTP 502, because a server
  refusal is not the HTTP caller's error), `ErrAuthFailed` (530/535 at any
  stage, 534/538 during AUTH, refusal to authenticate in clear),
  `ErrTLSRequired`, `ErrTLSFailed`, `ErrInvalid`, `ErrAddressUnsupported`. They carry
  only the stage and numeric reply code in `Metadata`. Server reply text is
  discarded because servers echo recipients (`550 <bob@x> unknown`) and
  sometimes credentials.

### Development and test tooling

- `mail.FileSender` (`file://` URL) writes each message as a 0600 `.eml` file in
  a 0700 directory, opened through `os.Root` so it cannot escape the directory,
  and logs only the path, after one start-up warning that mail is NOT
  delivered. Config validation and `FromConfig` both refuse it in
  `production`, with no override. It still depends on `FORGE_ENV`: an unset
  value means development, so a production container that loses its
  environment but keeps a `file:` URL would swallow mail; the start-up warning
  makes that visible in the first log lines.
- `mailtest.Recorder` records deep copies plus the encoded bytes and envelope,
  and `FailWith` simulates outages. It is concurrency-safe and runs the real
  encoder, so tests fail on messages production would reject.
- `mail.NewPreviewHandler` serves registered fixture messages (headers, HTML in
  a sandboxed iframe, text, inline images, raw source and the exact validation
  error). Because an unset `FORGE_ENV` means development, the environment alone
  is not a safe gate: construction also requires the explicit
  `FORGE_MAIL_PREVIEW=true` (`cfg.Mail.Preview`), which configuration validation
  rejects outside development and test. HTML is served under
  `Content-Security-Policy: default-src 'none'; ...; sandbox`, `nosniff`,
  `no-store`; the handler answers GET/HEAD only and its prefix matches whole
  path segments.

### Templates

`mail.Template[T]` pairs `name.text.tmpl` (text/template), `name.html.gohtml`
(html/template, the same `.gohtml` convention and contextual escaping as
`views`) and an optional `name.subject.tmpl` from an `fs.FS`. Data is typed with
`T`; rendering is fully buffered, so an error in any part returns
`ErrTemplate` and `Deliver` sends nothing. Template data is not trusted: the
subject goes through the same header validation as any other. `html/template`
context errors are detected at construction. `views.Renderer` writes to an
`http.ResponseWriter` and owns a global flat namespace, so mail uses
`html/template` directly with the same conventions rather than wrapping it.

### Configuration

`config.Mail` (additive): `FORGE_MAIL_URL` (`Secret`: `smtp://`, `smtps://`,
`file://`), `FORGE_MAIL_FROM`, `FORGE_MAIL_ALLOW_PLAINTEXT`,
`FORGE_MAIL_TIMEOUT` (default 30s), `FORGE_MAIL_TLS_CA_FILE`,
`FORGE_MAIL_PREVIEW` (development only). The URL takes no
query parameters (no `?tls=skip-verify`), ambiguous URLs are rejected like the
database URL, parse errors are never wrapped (they quote the URL and password),
credentials containing control characters are rejected (a percent-encoded
`%0d%0a` would otherwise reach the SMTP dialogue), `FORGE_MAIL_FROM` must pass
the same mailbox rules as every message, and production refuses the file
sender and `FORGE_MAIL_ALLOW_PLAINTEXT=true` combined with credentials for a
remote host. An empty URL leaves mail disabled;
`mail.FromConfig` returns `mail.ErrNotConfigured` so applications can disable
features that need mail instead of dropping messages.

### Password recovery

`recoverymail.Sender` implements `auth.RecoverySender`. It renders a built-in
(replaceable) template and builds the link from an https `ResetURL` (http only
for loopback), with the token in the query string or, with `TokenInFragment`,
after `#`. The plaintext token never appears in errors or logs. `auth` answers
the public request identically whether delivery worked or not, so the adapter
requires a `Logger` and writes one error line per failed email with the fault
code and SMTP stage only (never recipient, link or token). `New` renders and
validates a probe message, so an `AppName` or template that cannot produce a
valid email stops start-up instead of failing every send behind the uniform
202. Like every
`RecoverySender`, it should be given a queue-backed `mail.Sender` in
production so request timing does not reveal whether an account exists
(ADR 0013).

## Consequences

- Applications get Action Mailer's ergonomics with validation, TLS and
  escaping enforced by the framework instead of by discipline.
- Because the queue integration is just another `Sender`, delivering later
  needs no change in `mail`: a persistent job queue provides a `Sender` that
  serialises `Message` (it is JSON-friendly) and a worker that calls the real
  sender, using `ErrUnavailable`'s `Retryable` flag to decide retries and
  `ErrRejected`/`ErrInvalid` to dead-letter.
- No SMTPUTF8 (internationalised addresses) yet; these are rejected, not
  mangled.
- Providers' HTTP APIs (SES, Postmark, ...) are future `Sender`s in separate
  modules; the core stays stdlib-only.
- `net/smtp` is frozen upstream. The surface used (Client, Hello, StartTLS,
  Auth, Mail, Rcpt, Data, Quit) is small and covered by in-process fake-server
  tests; if it is ever removed, only `smtp.go` needs replacing.

## Not decided here

Queue integration, DKIM signing (normally done by the relay), bounce/complaint
handling, open/click tracking, HTML inlining and text alternatives generated
from HTML.
