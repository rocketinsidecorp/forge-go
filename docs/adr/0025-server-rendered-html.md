# ADR 0025: Server-rendered HTML

- **Status:** Accepted
- **Date:** 2026-10-19

## Context

Forge applications serve JSON well, but Rails-style HTML CRUD (a form, a
`422` re-render with field errors, a redirect with "Post was created.") needed
more than `views.New` and `web.DecodeJSON`:

- `views.New` parses one flat directory into a single template set, so two
  pages that both `{{define "content"}}` overwrite each other, and there is no
  layout or partial convention.
- There is no form decoding, no safe redirect, no flash message and no way for
  an HTML form, which can only send `GET` and `POST`, to reach `PATCH` or
  `DELETE` routes.
- CSRF protection exists only for cookie-authenticated JSON
  ([ADR 0012](0012-cookie-sessions-and-csrf.md)): the token travels in a
  header and the cookie is issued at login. A form cannot set a header, and a
  signed-out visitor has no cookie.
- Middleware can be added only through `forge.WithHTTPMiddleware`, an option
  of `forge.New`, which `forge.Main` creates before `Configure` runs.

Rails' answers are the reference (`application.html.erb`, `_form` partials,
`authenticity_token`, `_method`, `flash`, `redirect_to ... status:
:see_other`), with its weaknesses closed: Rails flash and session live in a
signed and encrypted cookie that needs a `secret_key_base`, `redirect_to`
accepts external URLs unless told otherwise, and mass assignment needs
`params.permit`. Core packages stay stdlib-only
([ADR 0006](0006-zero-dependency-core.md)).

## Decision

### Packages

| Package | Adds | Imports |
| ------- | ---- | ------- |
| `web` | `ParseForm`, `DecodeForm`, `FormErrors`, `Redirect`, `IsLocalPath`, `Negotiate`, `PrefersHTML`, `Flash`, `SetFlash`, `Flashes`, `FlashText`, `MethodOverride` | `fault`, `uuid` |
| `csrf` (new) | token format, `Protection` middleware, `Token` | `fault`, `web` |
| `views` | `Load`, `Options`, `RenderRequest`, `Pages`, template helpers | `csrf`, `uuid`, `web` |
| `router` | `Resources`, `ResourceRoutes`, `Action`, `ResourceMiddleware` | unchanged |
| `forge` | `App.Use`, `App.Resources` | unchanged |

`auth` now imports `csrf` for token generation and parsing; its constants and
`ErrCSRFInvalid` refer to the same values, and its behavior is unchanged.

### Template conventions

`views.Load(fsys, views.Options{})` reads a tree of `*.gohtml` files. A
template's name is its path without the extension.

- `layouts/NAME.gohtml` are layouts. The default is `layouts/application`.
- Files whose base name starts with `_` are partials (`shared/_flash`,
  `posts/_form`), included with `{{template "posts/_form" .}}`. The
  underscore stays in the name so a partial and a page never share one.
- Every other file is a page (`posts/index`). A page that defines `content`
  is rendered through the layout; any other page is a complete document.
- Each page is parsed into its own clone of the layouts and partials, so
  `content` and `title` blocks never collide. Load escapes every page once
  (executing it with nil data into a discard writer), so a template
  html/template cannot escape safely stops the application at startup.
- Rendering stays buffered: nothing is written when execution fails.
- Pages are sent with a strict Content-Security-Policy
  (`views.DefaultContentSecurityPolicy`): same-origin scripts, styles, images,
  fonts and fetches, `form-action 'self'`, `base-uri 'none'`, no framing, and
  no inline scripts, styles or event handlers.
- `views.New` and `Render` keep their flat behavior.

Helpers: `csrfField`, `csrfMeta`, `csrfToken`, `methodField`, `flashes`,
`flash`, `domID`, `dict`. Only `csrfField`, `csrfMeta` and `methodField`
return `template.HTML`, built from constants and a token that is canonical
base64url (validated or generated by `csrf`) and escaped again. Everything
else returns plain values that html/template escapes for their context.
Application functions may not replace the built-in names.

Request-bound helpers cannot be per-execution in html/template: functions are
fixed per template set, and a set cannot be cloned once it has executed.
`RenderRequest` therefore takes an escaped clone of the page from a pool
whose helpers read that clone's own request state, which is set for one
execution and cleared afterwards. Without a request (`Render`) these helpers
fail the render instead of emitting a form without a token.

### Forms

`web.DecodeForm` binds only exported fields tagged `form:"name"`, so a field
that is not meant to be set from a request cannot be (no mass assignment).
Every tagged field is assigned: an absent checkbox is `false` and an absent
or empty optional (pointer) field is `nil`. Unknown fields and repeated
values for a scalar field are `400 invalid_form`; values that do not convert
are returned together as `FormErrors`, which unwrap to
`422 invalid_fields`. Messages never contain the submitted value. Bodies are
read once through `web.ParseForm`: `application/x-www-form-urlencoded` only,
at most 1 MiB and 1000 fields (the server body limit still applies), cached
in `Request.PostForm`, and never merged with the query string. Multipart
bodies are not supported yet.

### CSRF for HTML forms

The token is the existing one: 32 random bytes, unpadded base64url, in the
`__Host-forge_csrf` cookie (`Secure`, `Path=/`, `SameSite=Lax`, readable by
same-origin JavaScript). There is no second scheme, so a token issued at
cookie login protects forms and a form token works with `auth.RequireCSRF`.

`csrf.Protection.Handler` checks every unsafe request (anything but `GET`,
`HEAD`, `OPTIONS`, `TRACE`) twice, unless its pattern is listed in
`Options.Exempt`:

1. **Origin.** `net/http.CrossOriginProtection` rejects requests a browser
   marks as cross-origin through `Sec-Fetch-Site` (including `same-site`
   sibling subdomains) or an `Origin` whose host differs from `Host`, unless
   the origin is in `Options.TrustedOrigins`. Requests without either header
   (non-browser clients) pass this check.
2. **Token.** The `X-CSRF-Token` header, or, only when there is no such
   header and the body is form-encoded, the `authenticity_token` field, must
   equal the cookie token in constant time. The query string is never read.
   A missing, repeated, malformed or mismatched token, a malformed cookie, or
   an unreadable or oversized body is rejected.

The token check is skipped for two kinds of request that a cross-site page
cannot produce, so bearer and JSON APIs keep working behind the same
middleware: requests with an `Authorization: Bearer` header (browsers never
attach one automatically, and a cross-origin script needs a CORS preflight to
add it), and requests with a JSON body (`application/json`, `*+json`), which a
form cannot send and a cross-origin script can send only after a preflight
Forge does not grant. The origin check still applies to both.
Cookie-authenticated JSON routes keep `auth.RequireCSRF`.

The cookie is issued lazily: `csrf.Token` sets it when a response embeds a
token and the request has no valid cookie, and marks that response
`Cache-Control: private`. Health checks, assets and API responses therefore
never carry `Set-Cookie`, so a misconfigured shared cache cannot hand one
token to everyone. Tokens are not rotated per request or masked: Forge does
not compress responses, so BREACH-style length oracles do not apply to
Forge's own output.

Rejections are `403` (`csrf_invalid` or `cross_origin_request`) in the JSON
error format, or a constant minimal HTML page when the client prefers HTML.

### Flash

Flash messages travel in the `__Host-forge_flash` cookie (`Secure`,
`HttpOnly`, `Path=/`, `SameSite=Lax`, session lifetime) as unpadded base64url
JSON, at most 2048 encoded bytes, four messages of 512 bytes, with kinds
matching `[a-z][a-z0-9_]{0,31}`. `web.Flash` loads the messages and expires
the cookie in the same response, so a message is shown on exactly one
request; `SetFlash` replaces that expiry when the request sets a new message.
A malformed cookie is discarded.

The cookie is **not signed**. It carries display text, never a decision, and
html/template escapes it like any other value. Forging one requires writing a
cookie for the application's own host, which the `__Host-` prefix limits to
the host itself; a user who edits their own cookie changes only what their
own browser shows. Signing would require a key Forge does not otherwise need.
Applications must not put secrets or personal data in flash messages.

### Method override

`web.MethodOverride` rewrites only a `POST` whose form-encoded body contains
`_method` = `PUT`, `PATCH` or `DELETE` (any case). Other methods, content
types and the query string are ignored, and any other value is
`400 invalid_method_override`. An override never produces a safe method, so
it cannot bypass the CSRF check in either middleware order. The body is read
through `web.ParseForm`.

### Redirects and negotiation

`web.Redirect(w, target)` answers `303 See Other` only to a local path:
absolute and scheme-relative URLs, backslashes (browsers read `/\host` as
`//host`), and control, space and non-ASCII bytes are refused with
`ErrUnsafeRedirect` before anything is written. `web.PrefersHTML` uses `Accept`
quality values; ties, `*/*` and a missing header prefer JSON.

### Routing and wiring

`Router.Resources(path, handler, middleware...)` registers index, new,
create, show, edit, update (`PATCH` and `PUT`) and destroy for the methods
`handler` implements (`Index`, `New`, `Create`, `Show`, `Edit`, `Update`,
`Destroy`); `ResourceMiddleware` wraps each action, for example with a read
or write permission chosen by `Action.ReadOnly`. `App.Use` adds middleware
before routing from `Configure`; it freezes after the first request, like
the router.

`forge new` generates `app/views` (embedded views package, application
layout, flash partial, tests) and `app/bootstrap/assets/application.css`,
and `Configure` installs `web.MethodOverride`, `csrf.Protection.Handler` and
`web.Flash`, in that order, for every database option. `forge routes` prints
the statically discovered routes, including the routes of `Resources` calls.

## Consequences

- Generated code (the planned `forge generate scaffold`) can render pages
  with `RenderRequest`, decode forms into tagged structs, re-render with
  `422` and `FormErrors`, and redirect with a flash message, using only
  framework APIs.
- Webhooks that post form-encoded bodies without a token must be listed in
  `csrf.Options.Exempt` and authenticate requests by signature.
- `__Host-` cookies require HTTPS; browsers treat `http://localhost` as
  secure, so `forge dev` works there, but plain-HTTP hosts other than
  localhost cannot hold the CSRF or flash cookie (as for cookie login).
- XSS defeats CSRF protection: a script running on the page can read the
  token. Contextual escaping, the strict page CSP and the restricted
  `template.HTML` helpers are the defenses.
- Rendering a page clones its template set the first time each pooled
  instance is used; the pool keeps escaped clones for reuse.
- Not yet provided: multipart forms and file uploads, per-page layout
  selection, digested or fingerprinted assets, Turbo/Hotwire, and
  `flash.now`-style messages for the current request.
