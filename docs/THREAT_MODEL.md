# Threat Model

Scope: the Forge framework, the `forge` CLI, and the applications and
container images that `forge new` generates, including Phase 3 identity work
through password login, login throttling, opaque sessions, browser-cookie
sessions, CSRF, recovery, security audit, and PostgreSQL tenancy enforcement,
deployment with `forge deploy` and forge-proxy, and the CI and release
pipelines of the framework and of generated applications.
Method: STRIDE per component. Items
marked **Planned** are not implemented.

STRIDE key: **S**poofing, **T**ampering, **R**epudiation, **I**nformation
disclosure, **D**enial of service, **E**levation of privilege.

## Assets

- Availability of the application process and its database.
- Integrity of request handling (correct routing, no path confusion).
- Confidentiality and integrity of data stored in the database (a server,
  or a SQLite file on the application host).
- Confidentiality of configuration values, database credentials, TLS keys,
  password hashes, active session credentials, recovery credentials, and
  internal errors.
- Integrity of the database schema and its migration history.
- Integrity of the build: source, dependencies, and container image.
- The developer's filesystem when running the CLI.

## Trust boundaries

1. Internet client -> TLS proxy / load balancer (in `trusted-proxy` mode).
2. Proxy (or client, in `tls`/`plain` mode) -> application HTTP listener.
3. Deployment environment (env vars, mounted files) -> application process.
4. Application process -> database server (network connection), or ->
   SQLite file on a local volume.
5. Migration run (`<app> migrate`) -> database.
6. Container runtime -> container.
7. Upstream code (Go modules, base images) -> build.
8. Developer shell -> `forge` CLI -> filesystem, `go` subprocesses, the
   application binary, and the development database.
9. Test process -> the test servers in `FORGE_TEST_POSTGRES_URL`,
   `FORGE_TEST_MYSQL_URL`, or `FORGE_TEST_DATABASE_URL`.
10. Application process -> telemetry collector (OTLP/HTTP) and metrics
    scraper -> the process's separate metrics listener. In the local
    observability stack: Docker daemon -> collector (log driver), collector ->
    Tempo, Prometheus and Loki, browser -> Grafana.
11. Operator machine -> deploy hosts over SSH (`forge deploy`, `forge logs`,
    `forge app`), and -> the image registry.
12. Internet client -> forge-proxy on the deploy hosts; forge-proxy ->
    application containers on the `forge` Docker network.
13. Deploy host shell (`docker exec`) -> forge-proxy control socket.
14. GitHub Actions -> third-party actions and tool images; the release job ->
    ghcr.io and Sigstore (Fulcio, Rekor) with its OIDC token; an operator ->
    ghcr.io when pulling and verifying a published image.

## Assumptions

- **Trusted proxy.** With `FORGE_HTTP_TRANSPORT=trusted-proxy` (the generated
  image default), the application port is reachable only through a proxy
  that terminates TLS. If clients can reach the port directly, traffic is
  plain HTTP and HSTS gives no protection. Forge cannot verify this; it is an
  operator responsibility.
- Forge never derives the scheme from `X-Forwarded-Proto`. It reads
  `X-Forwarded-For` only when the TCP peer is inside
  `FORGE_HTTP_TRUSTED_PROXIES` (empty by default: trust nobody), so a client
  cannot spoof its address unless the operator lists a network the client can
  send from ([ADR 0037](adr/0037-trusted-proxies-and-client-ip.md)).
- The environment and mounted files are controlled by the operator.
- The database server (or the host and volume holding a SQLite file) and its
  administrators are trusted. Forge protects
  the connection and the application's use of it, not the server itself.
- Application handlers and the SQL they contain are outside the framework's
  control.

## HTTP edge

| Threat | STRIDE | Mitigation |
| ------ | ------ | ---------- |
| Oversized request bodies exhaust memory | D | `Content-Length` above `FORGE_HTTP_MAX_BODY_BYTES` gets `413`; all bodies wrapped in `http.MaxBytesReader` (default 1 MiB). |
| Oversized headers | D | `MaxHeaderBytes` (default 1 MiB). |
| Slowloris / slow reads and writes | D | `ReadHeaderTimeout` 5s, `ReadTimeout` 15s, `WriteTimeout` 30s, `IdleTimeout` 60s by default; all must be positive. |
| Path traversal and path confusion | T, I | Requests with `.`/`..` segments, backslashes, `%2F`, or `%5C` are rejected with `400` before routing. Route registration rejects the same. |
| Late route registration or conflicts altering routing | T | Router freezes on first request; conflicting patterns return an error at registration. |
| Malformed or unexpected JSON input | T | `web.DecodeJSON` requires `application/json`, rejects unknown fields and any data after the first value, and maps oversized bodies to `413`. Other body read failures return a generic `400 unreadable_body`, so network addresses in the underlying error are not echoed. |
| Malformed or unexpected form input | T, D | `web.DecodeForm` binds only `form:"..."` tagged fields (no mass assignment), rejects unknown fields and repeated scalar values with `400`, reads only the body (never the query string), and bounds bodies to 1 MiB and 1000 fields on top of the server limit. Field errors never echo the submitted value. |
| Cross-site scripting in server-rendered pages | T, I, E | html/template escapes every value for its context; only `csrfField`, `csrfMeta` and `methodField` return `template.HTML`, built from constants and a validated base64url token. `views.Load` refuses templates html/template cannot escape safely at startup. Pages carry `views.DefaultContentSecurityPolicy` (no inline scripts, styles or handlers; same-origin resources and form targets only). Flash text is escaped like any value. |
| Subscribing to a stream the server did not render for you | E, I | Channel names are HMAC-SHA256 signed with a domain-separated label (key of at least 32 bytes, constant-time comparison, rotation through `PreviousKeys`) and expire (24 hours by default, 7 days at most). A forged, tampered, swapped-payload, wrong-key or expired token gets the same `403 stream_invalid`. See [ADR 0029](adr/0029-hotwire-assets-and-live-updates.md). |
| Cross-tenant stream subscription or broadcast | I, E | A tenant channel is distinct from the global channel of the same name; `broadcast.NewHandler` requires `tenancy.FromContext` to equal the channel's tenant (`403 stream_forbidden`, fail closed, also with no tenant), `turboStreamFrom` fails the render without a tenant instead of falling back to a shared channel, and the PostgreSQL adapter carries the tenant in the channel key. Tests cover other-tenant, no-tenant, global-vs-tenant and cross-replica cases. A signed name is a bearer capability for one channel, so mount the handler behind authentication and an `Authorize` rule (the scaffold requires the resource's read permission). |
| Revoked session or permission keeps receiving a stream | E | Streams end after `MaxConnectionAge` (30 minutes) and the browser reconnects through authentication and `Authorize` again. Tokens also expire. Applications needing faster revocation shorten the age. |
| Broadcast leaks one person's content or CSRF token to every subscriber | I | The same HTML goes to all subscribers of a channel: `Renderer.Fragment` has no response writer, so `csrfField`/`csrfMeta` fail the render, and the scaffold's partial holds only row data. Applications must not broadcast per-user content to shared channels. |
| Script or markup injection through a stream | T, E | Targets are validated DOM ids, so they cannot add attributes; content is `template.HTML` produced by html/template (escaped); Turbo executes no inline scripts under the page policy. Event framing splits payloads on `\n`, `\r\n` and `\r` into `data:` lines, so a payload cannot end an event or inject `id:`/`event:` fields. |
| SSE connections exhaust memory, file descriptors or goroutines | D | Subscribers are capped per channel (1000) and per process (10000), each has a bounded queue (64) and a slow subscriber is dropped rather than buffered; messages are capped (1 MiB; 256 KiB over PostgreSQL); excess connections get `503` with `Retry-After`; the in-memory broker starts no goroutines (one per request, owned by the HTTP server). Every write has a 10 second deadline, so a client that stops reading cannot pin a connection. Open streams are also capped per principal (16 by default; per client address when there is no authenticated principal) and per tenant (1000), so one account cannot take a channel's or the process's whole subscriber capacity (`429 stream_limit`). Proxy limits must count concurrent requests, not connections: HTTP/2 multiplexes many streams over one connection. |
| Streams block graceful shutdown | D | The in-memory broker closes when `Configure`'s context is cancelled (shutdown start) and from a shutdown hook, ending every stream so the HTTP drain completes. |
| Server read/write timeouts silently disable or kill streams | D | The handler sets a fresh write deadline before each write and clears it after the flush, with `http.ResponseController`: HTTP/2 resets a stream whose write deadline passes even when idle, so a deadline left set would kill every stream at the first quiet heartbeat interval. Tests run real servers with 150 ms (HTTP/1.1) and 250 ms (HTTP/2 over TLS) timeouts and a longer heartbeat, and check the stream survives and delivers. The handler also clears the read deadline, defensively: no test proves that is necessary with current Go. |
| Stream names leak through logs and referrers | I | Names travel in the query string (EventSource cannot set headers) and appear in access logs for their lifetime; they grant read access to one channel only, expire, are re-authorized per connection, and `Referrer-Policy: no-referrer` is sent. Do not log full query strings for `/streams`. |
| Forged or malformed PostgreSQL notifications | S, T, D | NOTIFY is database-wide: whoever can `NOTIFY` on the database can publish, so the database role is the trust boundary (use a distinct `NotifyChannel` per application). The listener parses strictly (version, field count, bounded chunk counts, canonical base64, valid channel keys), reassembles with bounded buffers (64 pending messages, a byte budget, 30 second lifetime), drops out-of-order or channel-switching chunks, and logs and ignores anything malformed; it never panics or stops. |
| Lost live updates | R | Delivery is at most once with no replay: slow consumers are dropped, notifications sent while a listener reconnects are lost, and a stream cut by a proxy misses messages. Pages are authoritative on the next navigation; do not use broadcasts as the only way to learn of a change. |
| Inline script or style allowed by the policy to make Turbo work | E | The import map's inline script is allowed by its SHA-256 only (no `'unsafe-inline'`, no nonce), and Turbo's one inline `<style>` by the hash of its exact text; a test recomputes both from the vendored files. An XSS that cannot add an inline script with the same bytes remains blocked. A custom policy replaces the default entirely. |
| Static asset server exposes files that were not meant to be public | I | Only embedded files in the digested table are served: unserved extensions, dot-files and unsafe names fail startup, undigested names, directories, `..` and encoded separators are `404`; SVG is served with a sandboxing CSP. |
| Tampered or substituted Turbo and Stimulus | T | The vendored files are unmodified, pinned by SHA-256 in a test, served from the application's own origin with digested names; no CDN is contacted. Provenance (npm integrity, licence) is in `hotwire/vendor/README.md`; updates are deliberate. |
| Open redirect | S, I | `web.Redirect` answers `303` only to local paths and refuses absolute and scheme-relative URLs, backslashes, and control, space and non-ASCII bytes before writing anything. |
| HTML form CSRF and method override abuse | T, E | `csrf.Protection` rejects unsafe requests that browsers mark cross-origin (`Sec-Fetch-Site`, `Origin`) and requires the `__Host-forge_csrf` token in the `X-CSRF-Token` header or the `authenticity_token` form field (constant-time; never from the query string). Bearer and JSON requests, which cross-site pages cannot send without a CORS preflight, skip only the token check; this holds only while the application grants no credentialed CORS. `Exempt` patterns match only the routes they name, and a form `POST` carrying `_method` is never exempt. `web.MethodOverride` accepts only `POST` form bodies and only `PUT`, `PATCH` or `DELETE`, so an override can never reach a safe method. See [ADR 0025](adr/0025-server-rendered-html.md). |
| Forged flash messages | S | The `__Host-forge_flash` cookie is `HttpOnly`, `Secure`, `SameSite=Lax`, host-only and bounded; a malformed cookie is discarded. It is unsigned: only the host itself can set it, and a user editing their own cookie only changes their own display. |
| CSRF token cached and shared | I, T | The CSRF cookie is set only on responses that embed a token, which `csrf.Token` marks `Cache-Control: private`; assets, health checks and API responses never carry it. |
| Response header injection | T | Framework header values are constants or generated UUIDs; incoming `X-Request-ID` is ignored. `net/http` neutralises CR/LF in header values when writing. |
| Clickjacking, MIME sniffing, referrer leakage | I, T | `X-Frame-Options: DENY`, CSP `frame-ancestors 'none'`, `nosniff`, `Referrer-Policy: no-referrer`. |
| Protocol downgrade | T, I | HSTS in `tls` and `trusted-proxy` modes; `production` rejects `plain`. |
| Handler panic crashes process or leaks stack | D, I | Recovery middleware logs the stack server-side and returns a generic JSON `500`. |
| Error logs flooded by disconnecting clients | D, R | `web.Error` logs client cancellations at debug level; real `5xx` failures are logged at error level with their cause. |
| Internal error details returned to clients | I | `web.Error` serializes only the `code` and `message` of a `*fault.Error`; any other error becomes a generic `500 internal_error`. Causes and metadata are never serialized. `fault.Error.Error()` omits the cause. Readiness responses expose check names and pass/fail only. Router `400`/`404`/`405` use the same format. |
| Untraceable requests | R | UUIDv7 `X-Request-ID` on every response and in every error body; the request-scoped logger (`web.Logger`) adds `request_id`, `trace_id` and `span_id` to log lines (see [Telemetry](#telemetry)). |
| Readiness endpoint abused to trigger expensive checks | D | Partial: each check runs with the request context and a 2-second timeout; the generated `database` check is a single ping through the pool. Results are not cached. Keep checks cheap. |
| OpenAPI document discloses internal routes, their permissions and types (`GET /openapi.json`, [ADR 0043](adr/0043-openapi-from-typed-routes.md)) | I | Served only in `development` and `test` by default; staging and production serve it only with `FORGE_OPENAPI_ENABLED=true`, and then log a warning at startup (`false` disables it everywhere). The document lists every described route, including admin and internal ones, with their `x-forge-permission` names, so treat enabling it as publishing the API surface. It is built from Go types and route patterns only: no request input, configuration values, secrets or data rows reach it. `forge openapi` writes it locally without listening. **Residual:** an unset `FORGE_ENV` means `development`, so a deployment that forgets `FORGE_ENV=production` serves it (the generated Dockerfile sets it, and production's TLS requirement makes the omission visible). |
| Inaccurate API description misleading clients or security review | T | Descriptions are built and checked when `Run` starts (and by `forge openapi`); unsupported types, path parameters the route lacks, duplicate operation IDs or statuses are startup errors, never guesses. `openapi.Typed` derives the description from the handler's types; generated handler tests validate every response against the document (`Document.CheckResponses`). Handlers described with `openapi.Describe` remain the application's responsibility beyond what its tests exercise. |

## Telemetry

See [OBSERVABILITY.md](OBSERVABILITY.md) and [ADR 0034](adr/0034-dependency-free-telemetry.md).

| Threat | STRIDE | Mitigation |
| ------ | ------ | ---------- |
| Personal data or secrets leaking into traces and metrics | I | Instrumentation records route patterns, methods, status codes, statement verbs, registered job/event names and error *types* only. Raw paths, query strings, headers, cookies, client addresses, bodies, SQL text and arguments, payloads, mail recipients and error messages are never recorded (tests assert this for HTTP, database, queue, outbox, scheduler and mail). String attributes are truncated to 1024 bytes. Attributes added by application code remain the application's responsibility. |
| Metric cardinality explosion from request input (memory, backend cost) | D | Label sets are fixed at registration; routes are `ServeMux` patterns, unknown methods become `_OTHER`, statuses become classes, SQL becomes an allowlisted verb. Each instrument holds at most 1000 series; beyond that measurements go to an `_overflow` series and `forge_telemetry_metric_overflows_total` counts them. Label values are capped at 128 bytes. |
| Metrics endpoint exposes operational data | I | Metrics are never served by the application router. The Prometheus listener is off by default, separate (`FORGE_TELEMETRY_METRICS_ADDR`, must differ from `FORGE_HTTP_ADDR`), `GET`/`HEAD /metrics` only, with timeouts. It has no authentication: bind it to loopback, or confirm a non-loopback address with `FORGE_TELEMETRY_METRICS_PUBLIC=true` (`production` refuses to start without it; other environments warn) and never publish the port. |
| Clients choosing trace IDs or forcing sampling (log poisoning, export amplification) | T, D | `traceparent` parsing is strict and fuzz-tested; repeated or malformed headers are ignored; invalid `tracestate` is dropped. Incoming `traceparent`/`tracestate` are ignored by default (`FORGE_TELEMETRY_TRUST_TRACEPARENT=false`): every request starts a new root trace, so clients cannot pick trace IDs, bypass `FORGE_TELEMETRY_SAMPLE_RATIO` or forward `tracestate` downstream. Trust is an explicit opt-in for services behind a proxy that sets or sanitizes the headers. The span queue is bounded (2048) and drops instead of blocking, so forced sampling cannot exhaust memory or stall requests. |
| Exporter SSRF or credential leak through configuration | S, I | The OTLP endpoint is operator configuration, never request input. It must be `http`/`https` without credentials, query or fragment; `production` requires `https` unless `FORGE_TELEMETRY_OTLP_ALLOW_PLAINTEXT=true`. The exporter never follows redirects, so headers cannot be sent to another host. `FORGE_TELEMETRY_OTLP_HEADERS` is a `config.Secret`, reserved headers and control characters are rejected, and errors name the entry position, never a value. Export errors carry the HTTP status, never the response body. |
| Telemetry backend outage degrading the application | D | Exports run on one owned goroutine with per-call timeouts and bounded retries; spans are dropped and counted when the queue is full; shutdown flushes within the shutdown budget and then gives up. |
| Secrets or personal data leaving through the OTLP log exporter (`FORGE_TELEMETRY_LOGS_EXPORTER=otlp`, opt-in) | I | The exporter sends at most what the logger writes to standard output: message and attributes resolved through `slog.LogValuer`, so `config.Secret` (database URL, OTLP headers) exports `[REDACTED]` (tested for direct, pointer, struct, config-struct and grouped values); any other value is encoded as the standard-output handler encodes it, like `slog.JSONHandler` in production (`json:"-"` and unexported fields omitted, `MarshalJSON`/`MarshalText` redactions honored, so a `*url.URL` loses its password) and like `slog.TextHandler` in `development`/`test`, never with `fmt`'s `%+v` behind a JSON handler; a value that fails to encode or panics exports a placeholder naming its type, never the error text (tested against both handlers' output). A custom standard-output handler that does not implement `telemetry.LogOutputHandler` is treated as JSON. Bodies are cut at 4096 bytes, string values at 1024, attributes at 64. Application code that logs a raw secret or personal data leaks it to the collector as it does to standard output. The same endpoint, https rule, header secrecy and no-redirect rules as traces apply. |
| Attributes redacted on standard output with `slog.HandlerOptions.ReplaceAttr` exported unredacted by the OTLP log exporter (#16) | I | slog handlers do not reveal their options, so the exporter is given the function: `telemetry.Options.LogReplaceAttr`, set by `FromConfig` (and so `forge.New`) from a logger whose handler implements `telemetry.LogOutputHandler`, as `telemetry.NewOutputHandler(w, format, opts)` and `NewLogHandler` do. It is applied with slog's semantics (message and every attribute, open groups, `LogValuer` resolved before and after, empty results and emptied groups removed), tested against slog's JSON and text output and the calls they make. **Residual:** an application that redacts with `ReplaceAttr` on a handler it builds itself (`slog.NewJSONHandler(w, opts)`, or a custom wrapper that does not implement `LogOutputHandler`), or that builds its own telemetry without `LogReplaceAttr`, exports unredacted values; OBSERVABILITY.md and the README say to use `NewOutputHandler` or set the option. Time and level are exported as logged, whatever `ReplaceAttr` does with them. |
| Log export feeding on itself or stalling requests | D | The queue is bounded (2048), logging never blocks and drops are counted; export failures are written to standard output only and never enter the log queue (`forge.New` keeps the plain logger for the exporter's diagnostics), so a down collector cannot create a loop. |
| Development exporter leaking spans into production logs | I | `FORGE_TELEMETRY_EXPORTER=log` is refused in `production`. |
| Local observability stack (`compose.observability.yaml`, [ADR 0038](adr/0038-local-observability-stack.md)) exposed on the network or opened with a guessable credential | I, S, E | Every published port is bound to `127.0.0.1` (Grafana, Prometheus, the collector's OTLP); Tempo and Loki publish nothing. Grafana's admin password has no default (`GRAFANA_ADMIN_PASSWORD` is required with `${...:?}`; a test enforces it), anonymous access and sign-up are off, and the stack's files contain no secrets. Configuration is mounted read-only. **Residual:** the password gates Grafana only; Prometheus (`127.0.0.1:9090`, OTLP write receiver on) and the collector's OTLP (`4318`) accept any local process, which can read metrics or inject telemetry. This is a single-developer local stack; do not run it on shared hosts. |
| Local stack sending data off the machine, or running unpinned code | I, T | Grafana's usage reporting, update checks, news feed, plugin preinstall, Gravatar and external snapshots are off; Tempo and Loki usage reporting is off and the collector's own metrics are off; no exporter targets anything outside the compose network. Images are pinned by exact version and digest (a test rejects `latest` and unpinned references) and Dependabot's `docker-compose` ecosystem proposes updates. |
| Any local process injecting or reading telemetry through the loopback ports | T, I | Accepted for a development stack: OTLP (4318) and Prometheus (9090) have no authentication, like the metrics listener; Grafana requires the password. Do not publish these ports and do not use the stack on shared machines or in production. |
| Secrets in observability data | I | Logs reach Loki unredacted, so whatever the application logs is stored for seven days in a named volume and readable by Grafana users. ADR 0034's recording rules apply to spans and metrics; never log secrets. `docker compose ... down -v` deletes the data. |

## Configuration

| Threat | STRIDE | Mitigation |
| ------ | ------ | ---------- |
| Insecure production configuration | T, I | `production` with `plain` HTTP transport fails at startup; `tls` without cert/key fails; non-positive timeouts or limits fail; a production PostgreSQL URL without `sslmode=verify-full`, or `verify-ca` with `sslrootcert` (`require` is refused, and so is `verify-ca` without `sslrootcert`, which would trust the system roots), or a MySQL URL without `tls=true`, fails unless `FORGE_DATABASE_ALLOW_PLAINTEXT=true`. Unknown URL schemes fail. |
| Unknown or misspelled values silently ignored | T | Unknown `FORGE_ENV` and `FORGE_HTTP_TRANSPORT` values fail validation; malformed numbers, durations, and booleans fail. |
| Trusted-proxy list that trusts clients | S | `FORGE_HTTP_TRUSTED_PROXIES` is empty (trust nobody) by default. Malformed or empty entries, `0.0.0.0/0`, `::/0`, IPv4-mapped prefixes and zoned addresses stop the process at startup (also when set programmatically: `Config.Validate`, `web.NewTrustedProxies`); errors name the entry position, not its text. Tests: `TestTrustedProxiesRejectInvalidEntries`, `TestValidateRejectsUnsafeTrustedProxies`, `TestServerRejectsUnsafeTrustedProxies`. |
| Secrets leaked through error messages | I | Malformed values are reported by variable name and expected format only. URL parse errors from `config` and from the adapters' `Open` are not wrapped, because they quote the URL. |
| Database credentials leaked through logs or output | I | `FORGE_DATABASE_URL` is a `config.Secret`: `[REDACTED]` through `fmt`, `slog`, and JSON/text marshaling; only `Reveal()` returns it. `forge doctor` drops the password and every query parameter except `sslmode`, so passwords in the user info or in `?password=`/`?sslpassword=` are not shown. pgx connection errors name the user and database, not the password. |
| TLS private key exposure | I | Key is read from a file path, not an environment variable; mount read-only. |

## Database

| Threat | STRIDE | Mitigation |
| ------ | ------ | ---------- |
| Eavesdropping or tampering on the database connection | I, T, S | PostgreSQL in `production` requires `sslmode=verify-full`, or `verify-ca` with `sslrootcert` (`require` is refused: it does not authenticate the server; `verify-ca` without `sslrootcert` is refused: pgx would trust every public CA); only `verify-full` authenticates the server's host name. A `PGSSLROOTCERT`, `PGSSLCERT`, `PGSSLKEY` or `PGSSLPASSWORD` variable the URL does not repeat is refused, not ignored, so the environment can neither weaken nor silently replace the trust the URL states. MySQL/MariaDB in `production` requires `tls=true`, which verifies the certificate; `skip-verify` and `preferred` are rejected. `FORGE_DATABASE_ALLOW_PLAINTEXT=true` is an explicit opt-out for trusted private networks. SQLite has no network connection. |
| Driver options injected through the connection URL | T, E | MySQL: the driver configuration is built field by field, never as a DSN string, and every URL parameter except `tls` is rejected, so a URL cannot enable `multiStatements`, `allowAllFiles` (`LOAD DATA LOCAL INFILE`), cleartext passwords, or client-side interpolation. SQLite: the URL accepts no parameters; the path is percent-encoded into a `file:` URI, so `?` or `#` in a file name cannot add pragmas; `:memory:` and `file:` paths are rejected. |
| Stacked-query injection | T, E | MySQL multi-statement execution is enabled only on the migrator's dedicated pool, never on the application pool. MySQL uses server-side prepared statements. |
| Silent data corruption on MySQL/MariaDB | T | Every connection sets a strict `sql_mode` (`STRICT_ALL_TABLES`, `NO_ZERO_IN_DATE`, `NO_ZERO_DATE`, `ERROR_FOR_DIVISION_BY_ZERO`, `ONLY_FULL_GROUP_BY`, `NO_ENGINE_SUBSTITUTION`), `utf8mb4`, and UTC; a connection whose setup fails is discarded. |
| SQLite file read or corrupted by other users or statements | I, T | The database file is created `0600` and its directory `0750` (the `-wal`/`-shm` files inherit the file's mode); in the image the directory belongs to `nonroot`. Defensive mode blocks corruption through `writable_schema`; foreign keys are enforced; double-quoted strings are identifiers only. |
| SQL injection | T, I, E | Repositories pass values as query arguments (`$1` or `?`), which the drivers send separately from the SQL. Forge's own SQL is constant; the MySQL session setup contains only constants and numbers; test helpers quote generated database names (`pgx.Identifier`, or a name checked against `^[a-z0-9_]{1,64}$` for MySQL). Application code that concatenates input into SQL is not prevented. |
| SQL details, constraint names, or values leaked to clients | I | Every adapter's `Translate` maps errors through `sqldb.Translate` to generic messages with stable codes; the constraint name goes to `Metadata`, which `web.Error` never serializes. Only client-caused data errors (check violation, value too long, numeric out of range, invalid datetime) become `400`; other data errors and untranslated database errors become a generic `500`. |
| Slow queries or connection exhaustion | D | A server-side statement timeout (default 30s, minimum 1ms so it can never become `0` = unlimited) on every pooled connection: all statements on PostgreSQL and MariaDB, only `SELECT` on MySQL, none on SQLite (context cancellation interrupts statements there); pool capped by `FORGE_DATABASE_MAX_CONNS`; connect timeout (5s); startup ping so a bad configuration fails before serving. PostgreSQL advisory lock waits are bounded by the statement timeout. |
| Database unreachable at runtime | D | Readiness returns `503` so the orchestrator stops routing traffic; translated errors return `503 database_unavailable` with `Retryable` set. |
| Retried transactions repeating side effects | T | Retries happen only with `Attempts > 1` and only for SQLSTATE `40001`/`40P01`. Transaction functions must not have external side effects (documented rule, not enforced). |
| Cross-process races on jobs | T | PostgreSQL only: transaction-scoped advisory locks (`AdvisoryXactLock`, `TryAdvisoryXactLock`) are released at commit or rollback and cannot leak. |

## Migrations

| Threat | STRIDE | Mitigation |
| ------ | ------ | ---------- |
| Migration files edited after being applied | T | SHA-256 checksum of each up script is recorded; a mismatch stops `migrate` and `rollback`. Down scripts are deliberately not checksummed, so a broken rollback can be fixed. |
| Older release deploying over a newer schema | T | The migrator refuses to run when the database has a version the binary does not contain. |
| Misnamed or empty files silently skipped | T | Any `*.sql` file that does not match the naming convention, or contains no SQL, is an error. |
| Unreviewed SQL executed | T | Migrations are plain SQL embedded at build time (`go:embed`); the SQL in review is the SQL executed. There is no runtime migration source. |
| Concurrent migrators corrupting state | T, D | A cross-process lock on a dedicated session serializes `migrate` and `rollback` (`migrate status` is read-only and takes no lock): a PostgreSQL session advisory lock, a MySQL/MariaDB `GET_LOCK` named per database, or an operating-system lock on the SQLite sidecar file `<database>-migrate.lock` (created `0600`). Server locks are released when the session closes; the SQLite file lock is released by the kernel when the process exits, so a crashed migrator leaves no stale lock. The SQLite lock covers one host only and is not reliable on network file systems. Locks are polled, never waited for inside the database. |
| Half-applied migration | T | Each migration and its bookkeeping row run in one transaction; on PostgreSQL and SQLite a failure leaves nothing behind. Not prevented on MySQL/MariaDB, where DDL commits implicitly: a failed migration can leave earlier statements applied (it is not recorded). Files marked `-- forge:no-transaction` can leave partial state on any database. |
| Irreversible or wrong rollback | T | A rollback checks that every step has a down script before reverting any, and reverts the most recently applied migrations (by `applied_at`), which stays correct after out-of-order application. |
| Long locks during migrations block traffic | D | Not prevented: migration sessions lift the statement timeout, and a SQLite migration holds the write lock for its whole transaction. Guidance: `SET LOCAL lock_timeout`, `CREATE INDEX CONCURRENTLY`, expand/contract ([DATABASE.md](DATABASE.md#zero-downtime-changes)). |
| Migration history tampered with by a database user | T | Not prevented: anyone who can write `forge_schema_migrations` can alter it. Checksums detect accidental edits of files, not a malicious database user. |

| Secrets committed or baked into images through env files | I | Generated `.gitignore` ignores `.env`, `.env.local`, and `.env.*.local`; `.dockerignore` excludes `.env` and all `.env.*`, so no env file reaches the image. The committed `.env.development` holds only local development values. |

Test server URLs should still point at dedicated servers; the MySQL test user needs to create databases (the generated applications use `root` on the local Compose server). |
| Browser-reload proxy reachable beyond the developer | I, T | The reload proxy exists only inside `forge dev`, only with `FORGE_ENV=development` and `FORGE_HTTP_TRANSPORT=plain` (`devloop.NewProxy` refuses anything else), and listens on the address the application would have used. It answers only `/__forge/reload.js` and an event stream (at most 32 open) itself, forwards everything else unchanged, and holds no credentials. Compiler output (source paths, code excerpts) goes to browsers (event stream, overlay and wait page alike) only when the listen address is loopback and the request's `Host` is a loopback name, which a DNS-rebound page cannot fake; otherwise there is no message. A non-loopback bind (`:8080`) exposes the application, as it would without the proxy. |
| Reload script weakening the page's CSP | T, E | The proxy adds a per-response nonce (a new random value each time) only to the one injected `<script>`, and `'self'` to `connect-src` for the same-origin event stream, only when the policy would otherwise block them; it never adds `unsafe-inline` or `unsafe-eval` (a policy that relies on `unsafe-inline` gets `'self'` rather than a nonce, which would switch its inline scripts off), and the script is served from the proxy, not inlined. A policy in a `<meta http-equiv>` tag is not edited and may block the script. Nothing is compiled into the application, so a production binary has no reload endpoint or script. The behavior differs from production by design: development responses carry the extra nonce and `Cache-Control: no-store`. |
| Dev proxy rewriting responses breaks or masks application behavior | R | Only `text/html` pages with a `</body>` are modified; other content types, compressed, partial, attachment and oversized responses pass through byte for byte; `Accept-Encoding` is forced to `identity` and the peer address becomes loopback (`X-Forwarded-For` carries the original). Reproduce proxy-sensitive behavior with `forge dev --no-reload`. |
| Restart loop or runaway builds from a busy tree | D | The watcher polls (default 500 ms) with a debounce, ignores dot-directories, `tmp`, `vendor`, `node_modules`, `bin`, `storage` and other runtime data, caps the tree at 50 000 files, and discards a build made stale by a newer change. A crashed application is not restarted until the next change. Builds are bounded by the caller's interrupt; the old process is killed after 35 s if it will not drain. The application and `go build` run in their own process groups (Unix) that are signalled as a whole, so restarts and cancelled builds leave no orphans; elsewhere only the started process is signalled. |
| Database tests silently not running in CI | R | `FORGE_TEST_REQUIRE_DATABASE=true` turns a missing test database into a failure; the framework and generated CI set it. |

An invalid or ambiguous production configuration stops the command before any connection. Not prevented: a local development or test database is dropped without a prompt, and a tunnel that makes a remote server appear on `127.0.0.1` looks local; the command prints the host and database it acted on. `schema:load` and `console` refuse system databases. |

Environment variables are readable by the same user and root through `/proc`. forge registers for hang-up, quit, interrupt and terminate before the option file is written and removes it on every exit path it controls; `SIGKILL` or a power loss can still leave the `0600` file in the temporary directory. |
| Compromised or wrong `pg_dump`/`psql`/`mysql`/`sqlite3` on `PATH` | T, E | Tools are found on `PATH` and executed directly, never through a shell, with forge-chosen arguments; a tool that receives the password in its environment or option file is trusted with it. The file is written `0600` atomically. Column defaults or comments a migration author wrote are included, as in any schema dump. |

## Deployment (`forge deploy`, forge-proxy)

See [ADR 0030](adr/0030-forge-deploy.md) and
[DEPLOYMENT.md](DEPLOYMENT.md#forge-deploy).

| Threat | STRIDE | Mitigation |
| ------ | ------ | ---------- |
| Man-in-the-middle on SSH | S, T, I | The system `ssh` client is used with the operator's `known_hosts`; `StrictHostKeyChecking` is never relaxed and host keys are never accepted automatically. `BatchMode=yes` prevents password prompts. Multiplexed control sockets live in a fresh `0700` temporary directory and are closed at the end of the command. |
| Shell injection into remote commands | E | Remote commands are POSIX shell lines run under `sh -c`; they are built only from validated configuration (service, role, host, image, volume, environment-name patterns; control characters rejected in `cmd` arguments) and every word is single-quoted. Host names starting with `-` are rejected and `--` separates ssh options from the host. `forge app exec` arguments are quoted the same way. Golden tests pin the exact command text. |
| Secrets in process lists, shell history or logs | I | Secrets reach hosts only on stdin (registry password via `docker login --password-stdin`, env files via `cat`), never in argv; an integration test asserts that no secret appears in any remote docker command line. Dry-run plans describe stdin without its content. Progress output, errors from remote stderr, and `forge logs` output pass through a redactor for every secret value (four characters or longer). |
| Secrets at rest on the operator machine | I | `.forge/secrets` must be mode `0600` or loading fails; `forge deploy init` creates it so and adds it to `.gitignore`, and `.forge` to `.dockerignore` so it cannot enter an image. `NAME=$VAR` passthrough keeps values out of the file; command substitution is not supported. |
| Secrets at rest on deploy hosts | I | Env files are written with `umask 077` and renamed atomically into `~/.forge/SERVICE/env` (`0700`). Accepted: Docker stores container environment in its configuration (readable with `docker inspect`) and the registry login in `~/.docker/config.json`; anyone with Docker access on the host is root-equivalent. Retained stopped containers keep the environment they were created with. |
| Direct access to application containers | S, I | Application containers publish no ports; only forge-proxy (80/443) is published. Accessories bind `127.0.0.1` unless an explicit address is configured. Docker-published ports bypass host firewalls such as `ufw`, which the deployment guide states. |
| Client spoofs its address or scheme | S | forge-proxy is the edge: `ReverseProxy.Rewrite` drops inbound `Forwarded` and `X-Forwarded-*` headers, forge-proxy also drops `X-Real-IP`, and `X-Forwarded-For` is set to the connecting address only (replaced, never appended) and `X-Forwarded-Proto` from the listener. The application reads `X-Forwarded-For` only from peers in `FORGE_HTTP_TRUSTED_PROXIES`, which `forge deploy` sets for the proxied role to the `forge` network's subnets (a network without a subnet fails the deploy); the scheme header is never read. Tests: `TestForwardedChainIsReplacedNotAppended`, `TestApplicationResolvesClientBehindProxy` (real proxy, client on another loopback address, spoofed headers through and around the proxy), `TestProxiedRoleTrustsTheForgeNetworkUnlessConfigured`. **Residual:** any container on the `forge` network (accessories, other services on the same hosts) can reach the application directly and choose its `X-Forwarded-For`, i.e. pick its own throttle key or spend another client's source budget; set an explicit, narrower value when hosts are shared with untrusted services (ADR 0037). |
| Proxy control surface | E, T | Control is a Unix socket inside the container (directory `0700`, an existing one restricted at start and a link refused, socket `0600`, owned by `nonroot`), reachable only through `docker exec`, i.e. by root-equivalent users on the host. There is no network control endpoint. Control requests are size-limited JSON with unknown fields rejected. |
| Unhealthy or wrong version receives traffic | D, T | A target receives traffic only after `healthy_count` consecutive passing health checks; otherwise the previous target keeps serving and the deploy fails (exit `4`). A failure on any host routes every switched host back to its still-running previous container. A failed revert is reported (exit `7`), never hidden. |
| Requests dropped during a switch | D | Targets are swapped atomically; requests hold the target they started on, and the previous target is drained (up to `drain_timeout`) before its container is stopped with SIGTERM and `stop_timeout`. A test switches targets 20 times under concurrent load and requires zero failed requests. |
| Slow or oversized requests exhaust the application | D | `ReadHeaderTimeout` and idle timeout on the proxy; after `-idle-timeout` a response write the client does not read and a silent WebSocket tunnel are closed too, releasing the target (`TestClientThatStopsReadingIsDisconnected`, `TestIdleTunnelIsClosed`, `TestIdleKeepAliveConnectionIsClosed`); bodies above `max_body_bytes` get `413`; bodies up to 1 MiB, chunked or not, are buffered with a 30-second deadline before the application is contacted (`408` otherwise); larger bodies are streamed and each read must receive data within 30 seconds; `response_timeout` bounds the wait for response headers. Accepted: a client trickling a large body just fast enough keeps one application connection busy; there is no total time limit per connection, so a client that reads or sends a little in every idle interval (as with nginx `send_timeout`) keeps its connection, bounded by `-max-connections` (10,000 per listener by default; further clients wait in the listen backlog) and the open-file limit (no per-address limit). Request lines and headers are capped by `-max-header-bytes` (64 KiB by default; `431` above it). |
| Certificates for unintended names, ACME abuse | S, D | autocert issues certificates only for host names registered with `tls` for a service (IP addresses and wildcards are rejected). Account keys and certificates are kept in the proxy volume, in a `0700` directory (an existing one restricted at start) with files synced to disk on write. Enabling `ssl` accepts the Let's Encrypt terms. |
| Concurrent deploys corrupt state | T | A lock (atomic `mkdir` on every host, with holder, time and message) guards setup, deploy, rollback and prune; partial acquisition is released and reported with exit `3`. `lock release` refuses a lock held by another performer without `--force`. Accepted: `--force` and manual removal of `~/.forge/SERVICE/lock` bypass it, and the holder string is self-reported. |
| Repudiation of deploys | R | Each deploy and rollback appends a JSON line (time, performer, version, containers) to `~/.forge/SERVICE/deploys.log` on every host. Accepted: the performer is `user@hostname` of the operator machine, not an authenticated identity, and the log is writable by the SSH user. |
| Malicious or mutable proxy image | T, E | The proxy is built from this repository (`cmd/forge-proxy/Dockerfile`: distroless static, `nonroot`, no shell, base images pinned by digest). Releases publish it as `ghcr.io/rocketinsidecorp/forge-proxy`, signed keyless with provenance and SBOM (supply chain, above); verify it with `cosign verify` and reference the verified digest. `forge deploy setup` warns when `proxy.image` is not pinned by digest. Accepted: `forge deploy` does not verify signatures itself. |
| Malicious hook or migration | E | Hooks are local executables from the repository, run without a shell and only when executable; they inherit the operator's environment. Migrations run the image's own `migrate` command once, before any switch; a failure aborts before containers change (exit `5`). |
| Interrupted deploy leaves mixed versions | T | Ctrl-C cancels remote commands; a switch already started inside forge-proxy completes. The command exits `7` and `forge deploy details` shows the state. The lock is still released. |

## Identity and tenancy

| Threat | STRIDE | Mitigation |
| ------ | ------ | ---------- |
| Session token stolen from persistence | S, E | Tokens contain 256 random bits; persistence stores only the SHA-256 digest. `Token` exposes the plaintext only through explicit `Reveal`. |
| Unattended or stolen session used long after its last use | S, E | Besides the absolute lifetime (24 h by default), a PostgreSQL session ends after `FORGE_AUTH_SESSION_IDLE_TIMEOUT` (default 2 h) without a request: the resolver refuses a stale `last_seen_at` like a revocation (fail closed). The use is written at most once a minute per session by a conditional `UPDATE`, decided by the database clock. |
| CSRF token recovered through compressed responses (BREACH) | I | Pages embed the token masked with a fresh 32-byte one-time pad on every render (`csrf.Token`), so no two responses contain the same token bytes; the middleware unmasks and compares in constant time. The cookie and the JSON cookie-login response keep the raw token, which no compressed page reflects. |
| Extra credential-entry points | S, D | Generated applications mount only the HTML sign-in flow; the bearer and cookie JSON logins, JSON MFA completion and JSON recovery are opt-in (`forge new --api-auth`). Production logs a warning when a sign-in, MFA or recovery service counts attempts in the per-process `MemoryLoginThrottler`. |
| Browser session token read by JavaScript | I, E | Cookie sessions use the fixed `__Host-forge_session` cookie with `Secure`, `HttpOnly`, `Path=/`, no `Domain`, and `SameSite=Lax`. Cookie login never returns the session token in its body. |
| Cross-site request forgery | T, E | Unsafe cookie-authenticated requests require the fixed `__Host-forge_csrf` 256-bit token to match exactly one `X-CSRF-Token` header in constant time. Cookie logout includes the CSRF check by default. HTML forms use the same token through `csrf.Protection` (see HTTP edge). Safe methods bypass the check and therefore must not mutate state. |
| Login CSRF | S, T | Cookie login requires exactly one HTTPS `Origin` whose host equals `Request.Host`. The HTML sign-in form carries the CSRF token the sign-in page issues, and `auth.Browser` requires `csrf.Verified`, so an exempted route, a missing middleware or a JSON body cannot sign a victim into the attacker's account. The bearer login surface remains available for non-browser clients. |
| CSRF token fixation across sign-in | S, T | Every browser sign-in (JSON cookie login, HTML form, MFA completion) sets a fresh `__Host-forge_csrf` token through one helper, so a token planted or observed before authentication does not survive it. |
| Open redirect after sign-in | S, I | `return_to` is accepted only when `web.IsLocalPath` holds (no scheme, host, `//` or `/\` prefix, backslash, control, space or non-ASCII byte, at most 2048 bytes), and it is re-validated when rendered, when posted and before the `303`. `AuthenticateBrowser` adds it only for GET and HEAD. |
| Account or tenant enumeration through the HTML forms | I | A failed sign-in shows one message at `422` for any wrong organization, email or password (with the dummy-hash timing path); reset requests answer the same `303` and notice for known, unknown and malformed accounts and for delivery or audit failures; throttling keys do not depend on account existence. |
| MFA challenge leaked from the browser | S, I | The pending challenge lives only in the `HttpOnly`, `Secure`, `SameSite=Strict` `__Host-forge_mfa` cookie that expires with it; it never appears in a URL, page or script, and no session exists until the second factor succeeds. |
| Second factor changed or weakened from a stolen session | S, E | Every `/mfa` change ([ADR 0045](adr/0045-generated-mfa-settings-pages.md)) needs the CSRF token and the password again, and once a factor exists a current authenticator or backup code, used up; confirming a new key needs the same proof, so a session alone can neither see a pending key again nor guess its code. Wrong passwords and codes give one answer (residual: a right password with a wrong code costs one more database round trip, a timing difference the five-per-five-minutes throttle bounds). Tests: `TestBrowserMFAEnrollmentNeedsThePasswordAtBothSteps`, `TestBrowserMFAChangesNeedThePasswordAndAFreshCode`, `TestMFAPagesAgainstPostgres` (generated). |
| Step-up backup code lost, or a sign-in deadlocked, by a factor change | D | A step-up backup code is only checked (`VerifyMFAStepUp`) and used up by the change in its own transaction, so a change that fails keeps it and a code used meanwhile refuses the change (`ErrMFAStepUpInvalid`). Every MFA transaction locks the `forge_users` row before any MFA row, so a sign-in racing a disable or rotation waits instead of deadlocking (`40P01`). A pending key is read only with the kind the account's factor implies, so an enrollment confirmation never checks or shows a rotation's key. A step-up proof is bound to its account and required by every change of an existing factor. Tests: `TestMFAStepUpProofIsBoundToItsAccount`, `TestBrowserMFAFailedChangeKeepsTheStepUpBackupCode`, `TestMFAStepUpBackupCodeUsedMeanwhileRefusesTheChange`, `TestPendingTOTPIsNeverReadAsTheOtherKind`, `TestMFASignInStepsLockTheUserBeforeAnyMFARow`, `TestMFAStepUpBackupCodeIsUsedUpByTheChangeAgainstPostgres`. |
| Code guessing through the two-factor settings | S, D | Step-ups count on the MFA throttler (five per account, 60 per source in five minutes) before the password is checked, wrong codes of a new key included; counters are cleared only after a change succeeds, and never by a password-only step-up of an account with a factor, so interleaving password-only requests does not buy guesses. Tests: `TestBrowserMFAStepUpIsThrottled`, `TestBrowserMFAPasswordOnlyStepUpKeepsTheCodeCounter`. |
| Password oracle on the two-factor settings of an enrolled account | I | `POST /mfa` and `POST /mfa/confirm` need no code, so once a factor exists a wrong password would answer `422` and a right one `303`. `stepUp` therefore counts the attempt on the throttler and then refuses an account with a factor (`ErrMFAAlreadyEnabled`, `303`) before it checks the password: both passwords get the same answer. Test: `TestBrowserMFAEnrollmentRoutesDoNotRevealThePasswordOfAnEnrolledAccount`. **Residual (timing):** an account without a factor pays for the password hash and one with a factor does not, so a session holder can measure whether the account is enrolled, which `GET /mfa` already shows them; the request is throttled (five per account in five minutes) and the hash is not a password oracle. |
| Session holder locks the owner out of `/mfa` | D | Step-ups count per account (five in five minutes) whoever sends them, so a session holder (a stolen session, or an open one) can spend the budget with wrong passwords and make the owner's `/mfa` changes answer `429` until it expires. **Accepted:** the lockout lasts at most five minutes, blocks only the two-factor changes (sign-in has its own counters), and the alternative, counting per session, would give a stolen session unlimited guesses at the password and codes. |
| TOTP key or backup codes leaked from the settings pages | I | They are shown only after re-authentication, on `no-store` pages, never logged (`TOTPSecret`, `TOTPProvisioningURI` and `MFABackupCode` redact themselves) and backup codes only once; the store keeps the seed encrypted and backup codes as digests. |
| Signed-in page served from a cache after sign-out | I | `AuthenticateBrowser` marks authenticated responses `Cache-Control: no-store`. |
| Reset flow that promises an email nobody sends | R, D | Generated applications mount the reset pages and link only when `auth/recoverymail` is configured from `FORGE_MAIL_*` and `FORGE_AUTH_PASSWORD_RESET_URL`; half-configured mail stops startup. |
| Reset token leaked from the emailed link | I | `GET /passwords/edit` moves the token into a `no-store` form; Forge sends `Referrer-Policy: no-referrer` and pages load no third-party resources. Tokens are one-time, digest-only and expire (ADR 0013). |
| First-owner provisioning abused to add or take over an account | S, E | `setup` refuses once any tenant exists (checked under an advisory lock in the provisioning transaction), creates the tenant, owner and role atomically with an `auth.identity.provisioned` audit event, and is an operator command, not an HTTP route. |
| Owner password exposed during setup | I | The password is read from a terminal with echo off, one line of standard input, or `FORGE_SETUP_PASSWORD`; it is never an argument (visible in process lists and shell history), never printed or logged, and must be at least 12 characters. Prefer the prompt or `--password-stdin` over the variable, which other processes of the same user can read. |
| Password guessing and spraying | S, D | Attempts are counted before any credential check against hashed keys of the canonical login, the source (the resolved client address, `web.ClientIP`: the socket peer, or the first untrusted `X-Forwarded-For` entry from the right when the peer is a trusted proxy; IPv6 per `/64`) and the pair: 5 per login and source, 50 per login, 300 per source in 15 minutes. Unknown, malformed and look-alike logins take the same throttle path, the same credential lookup (random identifiers when malformed) and a dummy PBKDF2 verification. The default process-local limiter is bounded; PostgreSQL deployments can share counters across replicas. Tests: `TestLoginLetterCaseVariantsShareOneThrottleBudget`, `TestLoginCountsMalformedAttemptsAgainstTheSource`, `TestLetterCaseAndUnicodeVariantsDoNotGetFreshGuesses` (generated). |
| Throttle as a denial of service | D | One source cannot lock a login out for others: the tight limit is per login and source, and refused attempts are not counted, so hammering cannot burn the shared login or source budgets. A full memory table evicts the oldest idle counters instead of refusing everybody, and keeps blocking ones. The PostgreSQL throttler locks counters in a fixed order, rolls refused attempts back and deletes a few expired counters on every attempt, so the table follows the live windows. Tests: `TestOneSourceCannotLockALoginOutForOtherSources`, `TestFullTableEvictsIdleCountersAndKeepsBlockingOnes`, `TestLoginThrottlerKeepsOneSourceFromLockingALoginOut`, `TestLoginThrottlerNeverExceedsALimitUnderConcurrency`, `TestLoginThrottlerPrunesExpiredCountersWhileCounting`. Behind a proxy, all clients used to be one source, so 300 attempts from anyone refused every sign-in and 30 reset requests every reset (forge-go#11); with the proxy trusted each client has its own counters and cannot escape them with forged headers (`TestSourceThrottleBehindTrustedProxyCountsEachClient`, `TestTrustedProxiesResolve`). |
| Look-alike (Unicode) logins | S, I | `auth.CanonicalLogin` refuses non-ASCII logins at storage, lookup and throttle keys (strings.ToLower folds the Kelvin sign to `k`; PostgreSQL can fold `İ` to `i`); tenant slugs are ASCII-lowercased. Reset links go to the address the store holds, never to the typed one. Tests: `TestRecoveryNeverLooksUpOrDeliversToALookAlike`, `TestLoginTreatsLookAlikeLoginsAsUnknownAccounts`, `TestResetLinksGoToTheStoredAddressAndLookAlikesGetNothing` (generated). |
| Timing oracle on reset requests and sign-in | I | Reset requests are dispatched to a bounded lifecycle-owned queue (or the persistent job queue) and answered after at least 100 ms; sign-in does the same lookup and hash for malformed or unknown organizations; unknown reset tokens are refused before PBKDF2. Tests: `TestRecoveryRequestNeverAnswersFasterThanTheResponseTime`, `TestRecoveryRequestAnswersWhileTheSenderIsStillBlocked`, `TestLoginRunsTheSameLookupForMalformedAndUnknownIdentities`, `TestRecoveryResetChecksTheTokenBeforeHashingThePassword`. |
| Stale or forged role claims | S, E | Tokens carry no claims. The resolver contract requires current user, membership, expiration and permissions on every request. Bearer and cookie transports are explicit and do not fall back to one another; query and tenant headers are not authentication fallbacks. |
| Missing authorization check | E | `auth.Require` denies without a principal and denies a principal without the exact permission. Permissions have no wildcard semantics. Application route coverage remains the application's responsibility. |
| Tenant omitted or forged | E, I | `tenancy.Require` has no default. Authentication installs the tenant returned by the server-side resolver; client tenant headers are ignored. |
| Tenant leaks through a pooled PostgreSQL connection | I, E | `InTenantTx` sets `forge.tenant_id` transaction-locally on every retry. Integration tests prove RLS read/write isolation and that the setting is cleared. |
| Serving role bypasses row-level security, or can switch it off | E, I, T | Generated PostgreSQL applications serve as a runtime role (`NOSUPERUSER NOBYPASSRLS NOREPLICATION`, owns nothing, data privileges only) and migrate as a separate owner role (`FORGE_MIGRATION_DATABASE_URL`; the development roles come from `docker/postgres/init.sql`). Outside development and test `postgres.Open` refuses by default, for every pool (`config.Database.Environment`, set from `FORGE_ENV`; a `Database` built in code without one, `config.Default().Database` included, is checked; the only opt-out is `postgres.AllowRowSecurityBypass()` in code, and a lazy pool checks each connection before its first use), to start when the login role (`session_user`) or the role in effect (`current_user`) is a superuser, has `BYPASSRLS`, `CREATEROLE` or `REPLICATION`, is a member of a superuser, `BYPASSRLS` or `REPLICATION` role or of `pg_execute_server_program`, `pg_write_server_files` or `pg_read_server_files`, owns, or can `SET ROLE` to the owner of, a table with row-level security, or holds `TRUNCATE`, `REFERENCES` (table or column) or `TRIGGER` on one (directly, through `PUBLIC` or through any membership, whatever its `INHERIT` and `SET` options, a deliberate over-refusal: none of them is subject to RLS, and `TRUNCATE` empties every tenant's rows), or holds any privilege on a partition without RLS of an RLS parent (a direct query of the partition skips the parent's policies), or when the two differ (a role setting that `SET ROLE NONE` undoes) (`ErrRowSecurityBypass`). The runtime role has no temporary tables and only `USAGE, SELECT` on sequences. The generated repository, sign-in and bootstrap tests run as the runtime role (`postgrestest.NewRLS`) and prove it sees only the transaction's tenant, nothing without one, cannot insert for another tenant, and cannot run `CREATE` (temporary tables included), `ALTER`, `TRUNCATE` or `DROP` (`TestRuntimeRoleIsConfinedByRowLevelSecurity`, `TestRequireRowSecurityRefusesBypassingRolesOutsideDevelopmentAndTest`, the generated `Test<Resource>RowLevelSecurity` and `Test<Resource>RuntimeRoleCannotChangeTheSchema`). **Residual:** row-level security stops a query that forgets its tenant predicate, not SQL injected into the serving process, which can call `set_config('forge.tenant_id', ...)` itself; the check reads the tables of the database it is connected to, and a role that owns only tables without row-level security passes; it runs at startup only, and not in development or test; applications that leave `FORGE_MIGRATION_DATABASE_URL` unset migrate and serve as one role; `forge deploy` gives the owner's credential to the one-off migrate container alone (`migrate.env`, [forge-go#57](https://github.com/rocketinsidecorp/forge-go/issues/57)), and refuses a configuration that also lists a `migrate.env` name under `env` or `servers.*.env`; the migrate env file rests (`0600`) on the migrate host until the step ends, and a deploy killed outright leaves it there until the next deploy that uses `migrate.env`, or until it is deleted by hand. |
| False database-isolation assurance | I, E | Forge explicitly makes no RLS-equivalent claim for MySQL, MariaDB or SQLite; their repositories must filter every operation by tenant. |
| Secrets accidentally persisted in audit records | I | `auth.SecurityEvent` has a closed field set with identifiers and SHA-256 digests only; there is no arbitrary metadata/payload map for passwords, bearer tokens, reset links, TOTP seeds, challenges, or backup codes. |
| Audit history lost when identities are deleted | R | PostgreSQL audit actor/subject/membership identifiers intentionally have no foreign keys, so history survives identity cleanup. |
| Audit records tampered with by a database owner | T, R | Not prevented cryptographically. Forge exposes append-only application APIs, but a database owner can still alter/delete rows; external immutable shipping/signing remains a hardening concern. |
| Agent action identity spoofing or tenant mismatch | S, E | `agent.Engine` accepts no caller-supplied principal; it requires the authenticated principal and matching tenant established in context by auth middleware. PostgreSQL journal completion is scoped to execution, tenant, actor, and reserved status. |
| Agent action partial side effect hidden as a definitive failure | T, R | Executor errors and post-execution audit/output uncertainty are persisted as `unresolved` where possible, indexed for reconciliation, and returned with `MayHaveExecuted`; tenant-scoped operator decisions are stored separately, once per execution, without rewriting the original row or retrying the action. |

## Rate limiting, cache and file storage

See [RATE_LIMITING.md](RATE_LIMITING.md), [CACHING.md](CACHING.md),
[STORAGE.md](STORAGE.md) and ADRs [0031](adr/0031-rate-limiting.md),
[0032](adr/0032-cache.md), [0033](adr/0033-file-storage.md).

| Threat | STRIDE | Mitigation |
| ------ | ------ | ---------- |
| Limiter key spoofing: a client rotates a forwarded header or address to get a fresh bucket per request | S, D | `ratelimit.ByClientIP` keys by the resolved client address: `X-Forwarded-For` is read only when the TCP peer is in `FORGE_HTTP_TRUSTED_PROXIES` (empty by default), from the right, skipping trusted hops; malformed entries fall back to the peer; `X-Real-IP` and `Forwarded` are never read; `/0` and malformed lists stop the process at startup. `ratelimit.ByRemoteAddr` keys by the peer only. IPv6 clients are keyed by `/64`. Tests send spoofed headers from untrusted peers, forged prefixes through a trusted proxy and rotated IPv6 addresses, and prove the limit holds (`TestByClientIPBehindTrustedProxy`, `TestMiddlewareDoesNotTrustForwardedHeaders`, `FuzzTrustedProxiesResolve`). `KeyFunc` documents that its result must not be client-chosen. **Residual:** an over-broad trusted list lets anything inside it choose its key. |
| Limiter memory exhaustion by distinct keys | D | `Memory` is bounded by `MaxKeys` (heap-ordered expiry, no goroutines); `EvictSoonest` never refuses new clients, `Deny` never drops a counter; counters saturate. Shared stores keep one 64-character-key row per live bucket and prune in bounded batches. Residual: with `EvictSoonest`, more than `MaxKeys` distinct keys in one window can reset other clients' counters, so never key it on attacker-choosable per-target values (use `Deny` or a database limiter). Shared stores prune expired buckets after every `PruneBatch` hits. |
| Limiter bypass or outage when its store fails | D, E | The middleware fails closed (`503`) by default; `FailOpen` is an explicit per-route choice. Limiter errors are logged server-side and never returned to the client. |
| Personal data in limiter storage | I | Keys are SHA-256 digests of length-prefixed (scope, window, identifier); addresses and e-mail addresses are never stored. |
| Unbounded or stale cache growth | D | Entries, value size, key size and TTL are all bounded; memory also by bytes; database stores prune expired entries and evict the oldest writes in bounded batches. Residual: the database entry bound is soft but tight (a prune runs after every `PruneBatch` writes per process, so the table stays within about one batch of `MaxEntries`). |
| Cache poisoning through attacker-influenced keys or values | T, E | Keys are built with `cache.Key` (length-prefixed parts: no delimiter smuggling across namespaces); entries are decoded strictly and an undecodable entry is a miss; values are copied. **Residual (application):** per-user or per-tenant data must carry the user or tenant in the key; whoever can write the table (the application database role) can poison every replica. |
| Secrets or identifiers leaked through the cache | I | Database rows hold `SHA-256(key)`, not the key; keys and values are never logged and errors never contain them. Values are plain application data: do not cache secrets. |
| Thundering herd on a cold key | D | `Fetch` collapses concurrent misses in a process into one computation; waiters honour their own contexts; a cancelled leader does not fail them. Across replicas the herd is not collapsed (documented). |
| Upload abuse: oversized bodies, many files or fields, slow or endless streams | D | `Receive` caps the body from `Content-Length` and with `http.MaxBytesReader` before reading, bounds files, text fields and their sizes, streams files (512-byte sniff window; text fields are held in memory but limited to `MaxFields` values in total, repeated names included, and `MaxFields x MaxFieldBytes` bytes), and every `Put` enforces `MaxBytes` while copying. `FORGE_STORAGE_MAX_UPLOAD_BYTES` cannot exceed the server body limit. Residual: the global body limit cannot be raised per route, and disk space is not metered per user. |
| Hostile file content: HTML, SVG or script uploaded as an image; polyglots | T, E | The allow-list is mandatory and decided on the content type detected from the bytes, not the client label; labels that need a signature must match it; text labels need text content. Files are served as downloads (`attachment`, `nosniff`, sandboxing CSP) except raster images explicitly requested inline. Residual: `http.DetectContentType` looks at 512 bytes, so a valid image with appended active content is still an image to a browser that decodes it; use a separate origin for user files and do not widen `InlineTypes`. No malware scanning. |
| Path traversal and symlink escape in the disk adapter | T, I, E | `storage.ValidateKey` makes `..`, hidden files, separators, drive letters and escapes impossible by construction in every adapter; the root is an `os.Root`, so the operating system refuses `..`, absolute paths and symbolic links that leave it. Tests plant escaping symlinks and traversal keys and check that nothing outside the root is read or written. |
| Partial or torn files after a crash or concurrent overwrite | T | Temp file, `fsync` and `rename`; a failed or oversized write leaves the old blob; a concurrency test proves readers never see a torn write. Orphaned temp files are bounded by `PruneTemp`. |
| Client-chosen file name used as a path or header | T | Keys are UUIDv7; the name is sanitized (directories, control and bidirectional characters, quotes, leading dots) and encoded by `mime.FormatMediaType`; a test proves header injection through stored metadata is impossible. |
| Signed link tampering or forgery | S, T, E | HMAC-SHA256 (`crypto/hmac`, no custom cryptography) over key, expiry, disposition and binding with a 32-byte-minimum key, compared in constant time; strict parameter parsing (one of each, decimal expiry, canonical signature). Negative tests cover other keys, extended expiry, added `inline`, duplicate and malformed parameters. |
| Signed link replay: a leaked or forwarded link works until it expires | I | A link is a bearer capability. Default lifetime 15 minutes, maximum 7 days; responses are `Cache-Control: private` for at most the remaining lifetime; `SignOptions.Binding` ties a link to a principal so a forwarded link fails; rotating the key revokes all links. **Residual:** within its lifetime an unbound link works for anyone who holds it, and links are logged by proxies and browsers like any URL; serve them over TLS and keep lifetimes short. |
| Existence oracle for stored keys | I | The signature, expiry and binding are checked before the store is consulted; unsigned and forged requests get the same `403` whether the key exists or not. |
| Missing or weak signing key | S, E | There is no default key: signing fails without `FORGE_STORAGE_SIGNING_KEY`; `config` requires a canonical base64url key of at least 32 bytes, and requires one in production when storage is configured; the key is a `config.Secret` and errors never echo it. |
| Stored XSS from served files | T, I | See hostile file content above: active content never renders on the application origin, and every response is `nosniff` with `default-src 'none'; sandbox`. |

## Credentials and attribute encryption

See [CREDENTIALS.md](CREDENTIALS.md), [ENCRYPTION.md](ENCRYPTION.md) and
[ADR 0036](adr/0036-encrypted-credentials-and-attribute-encryption.md).

| Threat | STRIDE | Mitigation |
| ------ | ------ | ---------- |
| Key committed to the repository | I | `init` and `forge new` add `/config/credentials/*.key` to `.gitignore` and `config/credentials/*.key` to `.dockerignore` (creating them when missing); a missing credentials directory is created 0700; the key file is created 0600 and `init` never prints a key. **Residual:** nothing stops `git add -f`; add a secret scanner to CI, and rotate the key if it was ever committed (history keeps it). |
| Key loss | D | Deliberately unrecoverable. The docs tell operators to back keys up and to store the key list of each deployment; `rotate-key` never re-encrypts before the new key has a destination, and updates the key file in an order that keeps the on-disk pair readable at every instant. Data-encryption keys stored in the file are lost with it; back them up separately if the data matters. |
| Key exposed or replaced through the environment or a key file | I, T | Key files readable by group or others are refused, and so is a credentials directory that group or others can write (`ErrDirectoryPermissions`, `chmod 700`), for reading and writing keys; files are opened through `os.Root` with `O_NONBLOCK` and checked with `Stat`, so a FIFO is refused instead of blocking, and a key or credentials file that is a symbolic link is refused (`ErrSymlink`, `Lstat` before the open and the same file after it), even one pointing inside the directory (`TestWritableCredentialsDirectoriesAreRefused`, `TestFIFOsAtCredentialsPathsAreRefusedWithoutBlocking`, `TestSymlinkedCredentialsFilesAreRefused`); errors never echo key text. **Residual:** `FORGE_MASTER_KEY` is as visible as any environment variable (container inspect, `/proc/<pid>/environ` for the same user and root, crash reports). Use a mounted key file from a secret store where that matters. |
| Plaintext left by `credentials edit` (temporary file, editor swap, backup, undo, viminfo) | I | The file lives in a fresh 0700 directory, memory-backed `/dev/shm` on Linux, mode 0600; the whole directory (swap files included) is overwritten and removed on success, failure, invalid input and `SIGTERM`/`SIGHUP` (caught for the whole command, not only while the editor runs); Vim-family editors (recognized by name and by what the name resolves to) run without swap, backup, undo and viminfo; the editor does not inherit `FORGE_*` variables, so `FORGE_MASTER_KEY` is not exposed to it. **Residual:** `SIGKILL`, `SIGQUIT` (Go's default: exit with a goroutine dump) and power loss can leave the directory, and the process memory holds the plaintext while the editor runs; overwriting is best effort on copy-on-write or journaling filesystems; editors outside the Vim family (a busybox `vi`, nano, Emacs, GUI editors) may keep their own copies (check their settings); the editor and anything in `$EDITOR` is trusted. |
| Another process or user reads the editor file | I | 0700 directory, 0600 file, random directory name, created by the current user. Root and the same user can read it by definition. |
| Edit lost or torn: concurrent change, crash while writing | T, D | The encrypted file is replaced with temporary file, `fsync` and `rename`; a file changed while the editor was open is not overwritten; invalid JSON, duplicate keys or a non-object are refused before anything is written. |
| Staging (or another environment's) file swapped in for production | T, S | The environment name, format version and key id are part of the GCM associated data, taken from the caller, not from the file; the swap fails authentication even when both environments share a key (tested). **Residual:** an older, valid file of the same environment decrypts (rollback to a previous commit); git history and review are the control. |
| Ciphertext tampering or downgrade of the credentials file | T | Authenticated encryption; strict envelope parsing (known fields only, version 1, no trailing data, bounded size); any failure is one indistinguishable `ErrDecrypt`. |
| Secrets shown by `show`, logs or errors | I | `show` redacts all values and `--reveal` refuses a non-terminal stdout; `Store` prints as `[REDACTED]` through `fmt`, `slog` and JSON; `Secret` returns `config.Secret`; parse, decode and lookup errors give a path or a line and column, never a value (tested with distinctive secrets). **Residual:** the application can still log `Reveal()` output. |
| Duplicate keys hide a value from review | T | Duplicate JSON keys at any depth are rejected on save and on load. |
| Missing credential found only at runtime | D | Outside development and test, a missing file, key or `Options.Required` path stops startup, listing every missing path. |
| Ciphertext copied between rows, columns or tables (privilege escalation, account takeover through a swapped token) | T, E | The associated data is `(key id, table, column, record id)`; `Decrypt` fails with `ErrDecrypt`; tests swap rows, columns and tables, in memory and on PostgreSQL, and the re-encryption helper stops on a swapped row. **Residual:** the same ciphertext restored to the same row (replay of an old value) is accepted; use a version column. |
| Equality leaks from encryption | I | Encryption is always randomized (fresh 96-bit nonce); there is no deterministic mode. Equality search needs an explicit blind index. |
| Blind index reveals values or distribution | I | `HMAC-SHA256` under a key derived separately from the encryption key, bound to table and column: equal values in one column match, nothing else leaks without the key. **Residual:** anyone with the table sees equal values and their frequencies; with the key, low-entropy values can be enumerated. Docs restrict it to opt-in, high-entropy, normalized columns. |
| Key or nonce misuse | T, I | Master keys are 32 bytes from `crypto/rand`; AES and blind-index subkeys come from HKDF-SHA256 with distinct purposes (no key reuse across primitives); nonces are random per value, documented limit 2^32 values per key before rotation. GCM is not key-committing: key selection is by identifier from a ring the operator controls, never by an attacker. |
| Rotation destroys or reverts data | T, D | `Reencrypt` is a compare-and-set on the old ciphertext (concurrent writes win), bounded batches, resumable by `LastID`, idempotent, and stops on a row that does not decrypt; a removed key yields `ErrUnknownKey`, never wrong data. On PostgreSQL an unscoped `postgres.EncryptedColumn` checks `relkind`, `relrowsecurity`/`relforcerowsecurity`, ownership and `rolsuper`/`rolbypassrls` before every page and refuses (`encryption.ErrConfiguration`) a missing relation, a view, or a table whose row-level security hides rows from the role (it would scan 0 rows and report success); `postgres.WithTenant` runs every page and update in a transaction with `set_config('forge.tenant_id', id, true)`. The guide makes a count of rows not starting with `fg1.<active id>.`, run as a role that sees every row and paired with `count(*)`, the only proof of completion before an old key is removed; a report never is. Key rings refuse identifiers equal ignoring case, so the prefix count is exact under MySQL/MariaDB case-insensitive collations. Tested with a `NOBYPASSRLS` runtime role and a non-superuser owner on a `FORCE` policy, and with the exempt roles (superuser, `BYPASSRLS`, owner without `FORCE`) rotating unscoped (`TestEncryptedColumnRotatesTenantTablesPerTenantAndRefusesUnscopedRuns`, `TestEncryptedColumnExemptRolesRotateTenantTablesUnscoped`, `TestRowSecurityAppliesOnlyToRolesItBinds`). **Residual:** removing a key while that count is not 0 makes the remaining values unreadable; MySQL, MariaDB and SQLite have no row-level security, so `NewSQLRewriter` visits every row, and over a PostgreSQL `database/sql` driver it has no row-level security check; `WithTenant` sets only `forge.tenant_id`, so on policies that read another setting a scoped run sees no row and reports success (the count catches it). |
| Key text in configuration errors | I | `ParseKeyRing` names a key by its position among the sorted identifiers and the active identifier by its length, so a key pasted as an identifier is never echoed (`TestParseKeyRingErrorsNeverEchoAKeySwappedWithAnIdentifier`). |
| Oversized or hostile ciphertexts | D | Plaintext, ciphertext and file sizes are bounded (1 MiB / 2 MiB); malformed values fail before any allocation proportional to their length. Key lists hold at most 8 keys; `rotate-key` checks the resulting list before printing or writing anything, and a full list rotates without `--keep-old` (`TestCredentialsRotateKeyWithAFullKeyListRotatesAndKeepOldFailsCleanly`). |
| Memory disclosure | I | Keys and plaintexts are cleared best effort; Go gives no guarantee (the garbage collector copies values and strings are immutable; zeroizing every intermediate copy as Forge-Rust does is WONTFIX here), and swap and core dumps can hold them (**residual**). |

## Internationalization

See [I18N.md](I18N.md) and [ADR 0042](adr/0042-internationalization.md).

| Threat | STRIDE | Mitigation |
| ------ | ------ | ---------- |
| Path traversal through a locale name (`Accept-Language`, the `locale` cookie, `?locale=`, a path prefix, `FORGE_I18N_DEFAULT_LOCALE`) | T, I | Locale names are validated against a BCP 47 subset (`language[-Script][-REGION]`, letters and digits only) and canonicalized before any use; only locales loaded at startup from the embedded files can be selected, so request input never reaches the filesystem. File names must be canonical (`pt-br.json` is refused). Tested with `../`, `%2e%2e`, `/`, `\`, NUL and `_` names. |
| XSS through translated text or its arguments | T, E | `t` returns plain text that `html/template` escapes for its context; arguments are interpolated before that escaping. Only keys ending in `_html` are markup, and in them every argument is HTML-escaped unless it is `template.HTML`. A missing `_html` key is never markup. Tested with script payloads in element, attribute and `_html` contexts. **Residual:** `_html` translations are trusted code: a malicious or careless translator can inject markup, and an argument interpolated into `href="%{url}"` of an `_html` translation is HTML-escaped but not URL-checked (schemes such as `javascript:` are not filtered, same as Rails), so the author must never pass a user-supplied URL there (pass only URLs the code builds, or put the link in the template, where `html/template` filters schemes) and review translation files like templates. The page CSP still blocks inline scripts. |
| Memory or log exhaustion through missing keys built from input | D | Missing-translation warnings are logged once per locale and key, for at most 1,024 distinct problems (then one "suppressed" line, and a count in `SuppressedWarnings`); keys longer than 256 bytes or with invalid segments are refused before lookup and truncated in logs. |
| Oversized or hostile request headers | D | `Accept-Language` over 4096 bytes is ignored; only its first 32 entries are parsed; tags over 64 bytes, malformed q-values and subtags are skipped. |
| Oversized or ambiguous translation files | D, T | 1 MiB per file, 512 files, 16 levels, 50,000 keys per locale; duplicate keys (in one object or across files) and a second top-level key are startup errors, so review sees exactly what is served. Files are embedded at build time. |
| Locale cookie tampering | T | The cookie only selects among available locales; invalid values are ignored. It is `Secure`, `HttpOnly`, `SameSite=Lax`. Translated responses (every page the views renderer writes, and handlers that call `i18n.SetHeaders`) carry `Vary: Accept-Language, Cookie` so shared caches do not serve one visitor's language to another; assets and JSON are not marked, so they stay cacheable. **Residual:** a custom handler that writes translated text without `SetHeaders` can be cached across languages. |
| Path guard bypassed by the locale path prefix (`PathPrefix: true`) | E | The i18n middleware's handler is an `httpserver.Rewriter`: `forge.App` (and `httpserver`) collects it when the chain is composed and removes the prefix once per request before the first application middleware runs, so a guard registered with `forge.WithHTTPMiddleware` or `App.Use`, before or after the i18n middleware, sees `/admin` for `/pt-BR/admin`, `/PT-br/admin/users` or `/pt-BR/%61dmin`, exactly the path the router serves. A context marker removes the segment at most once (`/pt-BR/en/admin` is `/en/admin`, never `/admin`); `/pt-BR%2F..%2Fadmin` leaves `/../admin`, which the router refuses. Tested by `TestALocalePrefixCannotBypassAPathGuardRegisteredBeforeTheNegotiation` (both registration APIs, both orders, two i18n middleware, percent-encoded and double prefixes; the bypass reproduces without the fix), `TestRewritesRunBeforeEveryMiddlewareWhereverTheyAreRegistered`, `TestMiddlewareRemovesThePrefixOnceAndAsARewriter`. **Residual:** an i18n middleware wrapped inside another middleware, or served by a server Forge did not build, strips the prefix only for what runs after it; guards must decide by `r.URL.Path` (`r.RequestURI` keeps the prefix); a `WithHTTPMiddleware` that replaces the request context with one that drops Forge's values loses the once-only marker, so a later `App.Use` i18n middleware strips a second segment (`/pt-BR/en/admin` served as `/admin` after the guards saw `/en/admin`). |
| Open redirect through the sign-in return path with a locale prefix | T | `AuthenticateBrowser` restores the removed prefix (`i18n.PathPrefix`: an available locale's canonical name, never request text) in front of the stripped request URI, and the result must pass `web.IsLocalPath` (no `//`, backslash, control character, scheme or host) here and again in `auth.ReturnPath` at sign-in; otherwise the unprefixed path is used. Tested with `//evil`, `/pt-BR//evil`, backslash and encoded-slash variants. |
| Wrong-language or missing text hides a security message in production | I | Missing translations fall back to the default locale, then the humanized key, and are logged; development and test show `translation missing: LOCALE.KEY`, which the generated tests reject; `forge i18n check` exits 1 on any missing key or plural form. The failed sign-in message stays one key (`sessions.invalid_credentials`) for every wrong field in every locale, so translation cannot reintroduce account enumeration. |

## Residual risks

- XSS defeats CSRF protection: a script on the page can read the token.
  Escaping and the page CSP are the defenses; templates that build
  `template.HTML` from input reopen it.
- Routes listed in `csrf.Options.Exempt` (webhooks) have no CSRF or origin
  check and must authenticate requests themselves, for example by signature.
- Browsers that send neither `Sec-Fetch-Site` nor `Origin` get only the token
  check against cross-origin form posts.
- The `owner` role receives every permission, including those later
  migrations register; members who should not hold all of them need other
  roles. A tenant administrator who can create roles can already grant any
  permission within the tenant.
- Throttle residual risks: counters of the default limiter live in one
  process (a restart or several replicas multiply the budget; use the
  PostgreSQL throttler); behind a proxy that is not listed in
  `FORGE_HTTP_TRUSTED_PROXIES` the source is the proxy, so its clients share
  a budget, and a listed network can choose its source; an
  attacker who controls 50 sources (or `/64`s) can still keep one known login
  throttled for 15 minutes at a time (10 sources for recovery requests for an
  hour); one with very many sources can fill the in-memory table with
  blocking counters, after which new attempts are refused until counters
  expire; the PostgreSQL throttler has no row cap, only pruning that follows
  the attempt rate; `/64` counting also groups unrelated subscribers who share
  a prefix, and a subscriber with a larger allocation gets many budgets.
- Reset-request residual risks: the in-process `auth.RecoveryQueue` is not
  durable, so requests queued or running when the process stops are lost, and
  a full queue drops requests (logged), so a flood can delay legitimate
  resets; the account-dependent work still happens, just after the answer, so
  it is visible only through server load and the mail that arrives; with
  `auth/recoveryqueue` the stored payload holds the typed canonical login
  until the job is pruned; a service built without a dispatcher still does the
  work inline (the 100 ms floor hides it only while delivery is faster);
  sign-in does slightly more work (session issuance) when it succeeds.
- Accounts stored with a non-ASCII login before the canonical-login rule
  cannot sign in or recover until an operator gives them an ASCII address
  (AUTHENTICATION.md).
- A reset link that reaches the wrong person (forwarded email, shared
  mailbox) lets them choose the password until it expires or is used; the
  reset form cannot show which account the token belongs to.

- Direct network exposure of a `trusted-proxy` deployment.
- A published telemetry metrics port, or `FORGE_TELEMETRY_OTLP_ALLOW_PLAINTEXT=true`
  outside a trusted network. Trace IDs propagate to every service reached
  through `telemetry.Transport`, including third parties.
- `sslmode=verify-ca` without host name verification, or
  `FORGE_DATABASE_ALLOW_PLAINTEXT=true` outside a trusted network.
- MySQL/MariaDB TLS can only verify against the system certificate pool; a
  server with a private CA can only be reached in production with
  `tls=skip-verify` (unverified) plus `FORGE_DATABASE_ALLOW_PLAINTEXT=true`.
- On MySQL, writes and DDL have no server-side timeout; bound them with
  context deadlines.
- SQLite: whoever can read the volume can read the database; there is no
  database-level authentication.
- Without `FORGE_MIGRATION_DATABASE_URL` the same `FORGE_DATABASE_URL` serves
  and migrates, so that role holds DDL privileges. Generated PostgreSQL
  applications set both in development; in production, provision the two
  roles ([Database roles](DATABASE.md#database-roles-postgresql)) and give
  the serving processes only `FORGE_DATABASE_URL`. MySQL, MariaDB and SQLite
  applications are generated with one user.
- Handler code that ignores the body limit's error, logs secrets, builds SQL
  from input, or builds responses from untrusted input.
- Long-running or lock-heavy migrations, and partial state from
  `no-transaction` migrations.
- TLS certificate rotation requires a restart.
- Default CSP blocks HTML rendering; applications that relax it take on XSS
  risk. XSS can act with a browser session and read its CSRF token even though
  the HttpOnly session cookie itself is not readable by JavaScript.
- A signed image proves which workflow built it from which commit, not that
  the commit is benign; anyone who can push a `v*` tag on the default branch
  can publish one. Fuzzing finds what its properties check, in the time it
  is given.
