# Database

Forge supports PostgreSQL, MySQL, MariaDB, and SQLite
([ADR 0009](adr/0009-multiple-databases.md)). Applications write each
database's own SQL; Forge does not hide dialects. What it shares across
databases is everything around the SQL: configuration, connection setup
with secure defaults, transactions, error translation, migrations, test
databases, health checks, and the generated Docker setup.

Forge is SQL-first. Repositories contain explicit SQL, written by hand or
generated by sqlc. There is no ORM and no query builder.

| Database | `forge new --database` | Adapter | Test helper | Development image | Tested version |
| -------- | ---------------------- | ------- | ----------- | ----------------- | -------------- |
| PostgreSQL (default) | `postgresql` (`postgres`, `pg`) | `postgres` (pgx v5) | `postgres/postgrestest` | `postgres:18-alpine` | 18 |
| MySQL | `mysql` | `mysql` (go-sql-driver/mysql) | `mysql/mysqltest` | `mysql:8.4` | 8.4 |
| MariaDB | `mariadb` | `mysql` | `mysql/mysqltest` | `mariadb:11.8` | 11.8 |
| SQLite | `sqlite` (`sqlite3`) | `sqlite` (modernc.org/sqlite, pure Go) | `sqlite/sqlitetest` | none (a file) | bundled with the driver |

`--database none` (or `--skip-database`, which conflicts with `--database`)
generates an application without a database.

Shared, standard-library-only packages:

- `sqldb`: the error translation every adapter uses, transaction retries,
  bounded pool shutdown, and the `database/sql` wrapper (`sqldb.DB`) that the
  MySQL and SQLite adapters return.
- `migrate`: the migration engine and the `migrate`/`rollback` commands.
- `dbtest`: test-server discovery shared by the `*test` packages.

Every adapter exposes the same functions: `Open`, `Translate`,
`NewMigrator(cfg, migrations, logger)`, `Commands(fs)`, and a test package
with `New`, `NewMigrated`, `Config`, and `NewWithConfig`.

## Selecting a database

The scheme of `FORGE_DATABASE_URL` selects the adapter:

| URL | Adapter |
| --- | ------- |
| `postgres://user:password@host:5432/db?sslmode=verify-full` (or `postgresql://`) | `postgres` |
| `mysql://user:password@host:3306/db?tls=true` | `mysql` (MySQL and MariaDB) |
| `sqlite:storage/app.db` (relative to the working directory) or `sqlite:///var/lib/app/app.db` (absolute) | `sqlite` |

`config.Database.Adapter()` reports the selection and
`config.Database.SQLitePath()` returns the SQLite file path (percent-decoded).
Each adapter's `Open` and `NewMigrator` refuse a URL that selects another
adapter, so an application wired for MySQL cannot start against a
PostgreSQL URL by mistake. Any other scheme fails validation at startup.

## Configuration

| Variable                            | Default | Notes |
| ----------------------------------- | ------- | ----- |
| `FORGE_DATABASE_URL`                | (empty) | See above. Empty means no database: validation passes, `Open` fails. Stored as `config.Secret`. |
| `FORGE_DATABASE_MAX_CONNS`          | `10`    | Pool size, `1`-`1000`. |
| `FORGE_DATABASE_MIN_CONNS`          | `0`     | `0` to `FORGE_DATABASE_MAX_CONNS`. Used by PostgreSQL only; `database/sql` has no minimum. |
| `FORGE_DATABASE_MAX_CONN_LIFETIME`  | `30m`   | Connections are replaced after this age. Must be positive. |
| `FORGE_DATABASE_MAX_CONN_IDLE_TIME` | `5m`    | Idle connections are closed after this. Must be positive. |
| `FORGE_DATABASE_CONNECT_TIMEOUT`    | `5s`    | Per connection attempt, and the bound on the startup ping. On SQLite it is also the `busy_timeout`. |
| `FORGE_DATABASE_STATEMENT_TIMEOUT`  | `30s`   | Server-side statement bound; see the table below. At least `1ms`, because the databases treat `0` as no limit. |
| `FORGE_DATABASE_ALLOW_PLAINTEXT`    | `false` | `true` lets `production` connect to PostgreSQL or MySQL without the required TLS setting. |

What each adapter sets up:

| | PostgreSQL | MySQL / MariaDB | SQLite |
| --- | --- | --- | --- |
| Production TLS rule | `sslmode=verify-full`, or `verify-ca` with `sslrootcert` | `tls=true` | none (local file) |
| URL parameters | pgx parameters; the Forge variables override pool size, timeouts, and `statement_timeout`; `application_name` defaults to `forge` | only `tls` (`true`, `skip-verify`, `preferred`, `false`; default `false`); anything else is rejected | none accepted |
| Statement timeout | `statement_timeout`, every statement | MySQL: `max_execution_time`, read-only `SELECT` only. MariaDB: `max_statement_time`, every statement | none; statements stop when their context ends |
| Session | `timestamptz` scanned as UTC | `utf8mb4`, `time_zone = '+00:00'`, strict `sql_mode`, times as UTC `time.Time` | foreign keys on, WAL, `synchronous=NORMAL`, `busy_timeout`, immediate transactions, UTC time format, defensive mode, double-quoted strings disabled |
| `Open` returns | `*postgres.DB` (pgx pool) | `*sqldb.DB` | `*sqldb.DB` |

Rules enforced at startup ([ADR 0005](adr/0005-environment-configuration-fail-fast.md)):

- **PostgreSQL in `production`:** `sslmode` must be `verify-full`, or
  `verify-ca` with `sslrootcert` in the URL. `require` is rejected: it
  encrypts without checking the certificate, so the connection can be
  intercepted. A missing `sslmode` is rejected too: libpq's default,
  `prefer`, falls back to plaintext silently. `verify-ca` without
  `sslrootcert` is rejected: pgx would trust the system roots and check no
  host name, so a certificate any public CA issued for any name would pass;
  with `sslrootcert` it trusts that file alone. Only `verify-full` also checks
  the server's host name and needs no `sslrootcert` for a publicly trusted
  CA. (Forge-Rust refuses `verify-ca` altogether, because SQLx adds the web
  roots even with `sslrootcert`; see
  [RAILS_PARITY.md](RAILS_PARITY.md#parity-follow-ups).)
- **PostgreSQL ignores the `PG*` TLS variables:** `PGSSLMODE`, `PGSSLSNI`,
  `PGSSLNEGOTIATION`, `PGCHANNELBINDING` and `PGREQUIREAUTH` (and a service
  file named by `PGSERVICE`) cannot change what `FORGE_DATABASE_URL` says. A
  URL without `sslmode` gets libpq's default, `prefer`, whatever
  `PGSSLMODE` holds. `PGSSLROOTCERT`, `PGSSLCERT`, `PGSSLKEY` and
  `PGSSLPASSWORD` have no neutral value, so a set one that the URL does not
  name (`sslrootcert=...`, ...) stops the application at startup, with an
  error that names the variable and never a value: ignoring it could replace
  the CA the URL's `sslmode` verifies against. The serving pool
  (`postgres.Open`, lazy or not) takes no session setting from the
  environment: it **refuses to open while `PGOPTIONS` is set** (non-empty),
  with an error that names the variable and never its value, because a
  `PGOPTIONS='-c forge.tenant_id=...'` would give every pooled session a
  default tenant (a query outside `InTenantTx` would see that tenant's rows
  instead of none). Forge-Rust refuses the same way (SQLx cannot drop the
  variable once read); unset it for the application and name session settings
  in the URL's `options` parameter instead. `PGTZ` and `PGAPPNAME` are
  ignored: sessions are in UTC and the `application_name` is the URL's, else
  `forge`. Session settings in a service file the URL names
  (`service=...&servicefile=...`: its `options`, `application_name` and the
  like) are dropped from the serving pool unless the URL repeats them. This
  covers every command that opens the application's pool: `serve`, `routes`,
  `openapi`, `seed`, `forge setup` and `jobs`. The migrator is the exception
  and still honours `PGOPTIONS`, `PGTZ` and `PGAPPNAME`, so
  `PGOPTIONS='-c lock_timeout=5s' forge migrate` works. The other `PG*`
  variables (`PGUSER`, `PGPASSWORD`, ...) still fill what the URL leaves out,
  as for `psql`. Forge does this without editing its own environment: it
  writes the default of each such parameter into the URL it gives pgx, and
  replaces a service named by `PGSERVICE` with an empty one. The URL itself
  must be unambiguous: a fragment, an `@` after the host, whitespace in the
  query or a repeated parameter is refused (`config.Load` already refuses
  them; a `config.Database` built in code gets the same check).
- **MySQL/MariaDB in `production`:** `tls=true`, which verifies the server
  certificate. `skip-verify` and `preferred` encrypt without verifying and are
  rejected in production.
- Both rules are lifted only by `FORGE_DATABASE_ALLOW_PLAINTEXT=true`; use it
  only when the database is reachable exclusively over a trusted private
  network.
- **MySQL URL:** needs a user, host, and database; the port defaults to
  `3306`. Percent-encode special characters in the password.
- **SQLite URL:** no host, no query parameters, no `:memory:`, and no
  `file:` path.
- Validation errors name the variable and never echo its value. URL parse
  errors are not wrapped, because they quote the URL, password included.

`config.Secret` prints `[REDACTED]` through `fmt` (`%v`, `%s`, `%#v`),
`log/slog`, and JSON or text marshaling. `Reveal()` is the only way to read
the value; pass it straight to the component that needs it. `forge doctor`
prints the URL without the password and without query parameters other than
`sslmode`.

### MySQL and MariaDB session

The MySQL driver configuration is built field by field from the URL; Forge
never formats a DSN string, so no value in the URL can inject driver
options. Server-side prepared statements are used (no client-side
interpolation), `LOAD DATA LOCAL INFILE`, cleartext and old passwords are
disabled, and multi-statement execution is off on the application pool.

Every new connection detects the server flavor and runs one setup statement
before `database/sql` can use it; if the setup fails, the connection is
discarded. The `sql_mode` is:

```text
ONLY_FULL_GROUP_BY,STRICT_ALL_TABLES,NO_ZERO_IN_DATE,NO_ZERO_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION
```

so invalid data is rejected instead of being truncated, stored as zero
dates, or turned into `NULL`. On MySQL, `INSERT`, `UPDATE`, `DELETE`, and DDL
are not bounded server-side; bound them with a context deadline.

### SQLite

- The file (mode `0600`) and its directory (mode `0750`) are created if
  missing. SQLite gives its `-wal` and `-shm` files the same permissions.
- Connections are opened through a percent-encoded `file:` URI, so
  characters such as `?` or `#` in the path cannot inject parameters. The
  pragmas come from Forge, never from the URL.
- `_defensive=1` prevents corrupting the file through `writable_schema`;
  `_dqs=0` makes `"name"` always an identifier, never a string literal.
- Transactions begin `IMMEDIATE`, taking the write lock up front, so two
  transactions that read and then write cannot deadlock on the lock upgrade.
  A connection waits up to `busy_timeout` for the lock.
- `time.Time` values are written as UTC `TEXT`
  (`2006-01-02 15:04:05.999999999+00:00`), which sorts chronologically.
  Columns declared `TIMESTAMP`, `DATETIME`, or `DATE` scan back as UTC
  `time.Time`. `STRICT` tables allow only `TEXT` for them, which scans as a
  string.
- Use `STRICT` tables so SQLite enforces column types; a type mismatch is then
  translated like a check violation.
- SQLite serves one application instance on one host. Its locks are not
  reliable on network file systems.

## Opening the pool

```go
func Configure(ctx context.Context, app *forge.App) error {
	database, err := postgres.Open(ctx, app.Config().Database) // or mysql.Open, sqlite.Open
	if err != nil {
		return err
	}
	if err := app.OnShutdown(database.Shutdown); err != nil {
		database.Close()
		return err
	}
	if err := app.Readiness("database", database.Ping); err != nil {
		return err
	}
	// build repositories and use cases, register routes
	return nil
}
```

This is what `forge new` generates in `app/bootstrap/bootstrap.go`, with the
adapter chosen by `--database`. On PostgreSQL, `Open` refuses in staging and
production a serving role that could bypass row-level security ([Database
roles](#database-roles-postgresql)); no option is needed.

`Open` fails if `FORGE_DATABASE_URL` is empty or selects another adapter,
applies the pool and session settings above, and pings the database within
`FORGE_DATABASE_CONNECT_TIMEOUT`, so a wrong URL or unreachable database stops
startup instead of failing the first request. With `postgres.Lazy(true)` (or
`mysql.Lazy(true)`) it connects on the first query instead, and a lazy
PostgreSQL pool checks the role of each connection it opens (see [Database
roles](#database-roles-postgresql)) before its first use. Generated
applications pass `Lazy(!app.Serving())`, so `routes` and `openapi`, which run
`Configure` only to describe the application, need no reachable database:

```go
database, err := postgres.Open(ctx, app.Config().Database, postgres.WithTelemetry(app.Telemetry()),
	postgres.Lazy(!app.Serving()))
```

`App.OnShutdown` hooks run after the HTTP server has drained, and also when
`Configure` returns an error. `Shutdown(ctx)` closes the pool but stops
waiting when `ctx` ends and reports how many connections were still in use;
the hooks share the `FORGE_HTTP_SHUTDOWN_TIMEOUT` budget with the HTTP drain
(see [DEPLOYMENT.md](DEPLOYMENT.md#graceful-shutdown)). `Close` differs by
adapter: the PostgreSQL pool's `Close` waits for borrowed connections to be
released; `sqldb.DB.Close` follows `database/sql` and does not wait for
queries in progress (idle connections close at once, busy ones when they are
released).

`Ping` matches `health.Check`. With it registered, `/health/ready` returns
`503` while the database is unreachable. Each readiness check runs with a
2-second timeout (`health.DefaultCheckTimeout`).

## Database roles (PostgreSQL)

Row-level security is defense in depth only when the role the application
serves with cannot bypass it. A PostgreSQL application therefore uses two
roles ([ADR 0046](adr/0046-postgresql-runtime-and-migration-roles.md)):

| Role | Variable | Attributes and privileges |
| ---- | -------- | ------------------------- |
| runtime (`app_runtime` in development) | `FORGE_DATABASE_URL` | `NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE NOREPLICATION`; owns no table or schema and is a member of no role; `SELECT, INSERT, UPDATE, DELETE` on the tables and `USAGE, SELECT` on the sequences, no temporary tables, nothing else. `FORCE ROW LEVEL SECURITY` policies apply to it and it cannot run DDL. |
| migration (`app_migrator` in development) | `FORGE_MIGRATION_DATABASE_URL` | owns the database and the `public` schema and applies the migrations, so it owns every table; `NOSUPERUSER NOBYPASSRLS`. Used only by `migrate` and `rollback` (and `forge db`), never by the serving process. |

`<app> migrate` and `<app> rollback` connect with
`FORGE_MIGRATION_DATABASE_URL` when it is set. It supplies the role (user,
password, host, port and parameters) and is validated like
`FORGE_DATABASE_URL`, production TLS rules included; its database is ignored
(a `dbname`, `database`, `service` or `servicefile` parameter is refused), so
migrations always change the database the application serves. Unset, they use
`FORGE_DATABASE_URL`, as before. SQLite has no roles and ignores the variable.
Unlike `forge db`, which refuses `host`, `hostaddr` and `port` parameters
because its local-database safety check reads only the URL's host, the
application's commands accept them like `FORGE_DATABASE_URL` does: they have
no such check, and Forge still refuses a URL whose parameters would make pgx
connect elsewhere than its host and port, so a migration role may reach the
server another way than the serving one (for example directly instead of
through a connection pooler).

**Refusal outside development and test.** `postgres.Open`, in every
environment except `development` and `test` (so in `staging` and
`production`; the environment is `config.Database.Environment`, which
`config.Load` and `forge.New` set from `FORGE_ENV`, and a `config.Database`
built in code without one, `config.Default().Database` included, is checked
too), checks both the role the URL logs
in as
(`session_user`) and the role in effect (`current_user`), and fails before
anything is served when either is a superuser, has `BYPASSRLS`,
`CREATEROLE` (before PostgreSQL 16 `CREATEROLE` can grant itself membership
in a `BYPASSRLS` role) or `REPLICATION` (logical decoding reads every
tenant's changes), is a member of a superuser, `BYPASSRLS` or `REPLICATION`
role (it could `SET ROLE` to it), is a member of `pg_execute_server_program`,
`pg_write_server_files` or `pg_read_server_files` (paths to superuser or to
the data files), or owns, or could `SET ROLE` to the owner of, a table with
row-level security enabled (an owner can run `ALTER TABLE ... NO FORCE ROW
LEVEL SECURITY`), holds `TRUNCATE`, `REFERENCES` (also on a single column)
or `TRIGGER` on such a table, itself, through `PUBLIC` or through a role it
belongs to (none of the three is subject to row-level security: `TRUNCATE`
empties every tenant's rows; the usual cause is a `GRANT ALL`), or holds any
privilege on a partition that lacks row-level security of its own under a
partitioned table that has it (querying the partition directly skips the
parent's policies: enable and force row-level security, with the same
policies, on every partition). Membership counts whatever its `INHERIT` and
`SET` options, so even a `WITH INHERIT FALSE, SET FALSE` grant, which cannot
use the other role's privileges, is refused: a deliberate, fail-closed
over-refusal. It also fails when the two differ: a role setting
(`?options=-c%20role=...`, `ALTER ROLE ... SET role`) makes the session act
as another role, and `SET ROLE NONE` turns it back into the login role, so
the URL must log in as the serving role itself. The error wraps
`postgres.ErrRowSecurityBypass` and names the role. This is `Open`'s default
for every application, generated or hand-written, and for every pool it opens
(the `jobs`, `seed` and `auth setup` commands included).
`postgres.RequireRowSecurity(environment)` adds the check for an explicit
staging or production environment, whatever `cfg.Environment` says; it never
switches the check off, and it wins over the opt-out. There is no override
variable; the only opt-out, `postgres.AllowRowSecurityBypass()`, is in code, for a pool that must use such a role on purpose (an administration or
reporting tool), never for the pool that serves tenants:

```go
// Reporting connects as a BYPASSRLS role on purpose and serves no request.
reports, err := postgres.Open(ctx, reportingConfig, postgres.AllowRowSecurityBypass())
```

Development and test are not checked, so local tools can connect as an
administrator.

**Behaviour change (forge-go QG9).** The refusal used to apply only to a
pool opened with `postgres.RequireRowSecurity`, as the generated bootstrap
did; a hand-written application or a second pool was not checked. Now every
`postgres.Open` checks outside development and test. A deployment that
serves as a superuser, a `BYPASSRLS` role or a role holding `TRUNCATE` on a
tenant table now refuses to start: fix the role ([Database
roles](#database-roles-postgresql)), or pass `AllowRowSecurityBypass()` to a
pool that really needs it. A role that owns only tables without row-level security is
accepted, and the check reads the tables of the database it is connected to.
Keep the serving role separate from the migration role: it must own no table
with row-level security and be no member of the migration role.

**Privileges for new tables.** The runtime role gets its grants from the
migration role's default privileges, set once per database. The generated
`docker/postgres/init.sql` sets them, with the schema privileges, in
`template1`, so the development database and every database `forge db
create` or `reset` makes later inherit them. For a production database,
provision the equivalent once, as an administrator:

```sql
CREATE ROLE myapp_migrator LOGIN PASSWORD '...' NOSUPERUSER NOBYPASSRLS;
CREATE ROLE myapp_runtime  LOGIN PASSWORD '...' NOSUPERUSER NOBYPASSRLS;
ALTER DATABASE myapp OWNER TO myapp_migrator;
-- connected to myapp:
REVOKE ALL ON SCHEMA public FROM PUBLIC;
GRANT ALL ON SCHEMA public TO myapp_migrator;
GRANT USAGE ON SCHEMA public TO myapp_runtime;
ALTER DEFAULT PRIVILEGES FOR ROLE myapp_migrator IN SCHEMA public
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO myapp_runtime;
ALTER DEFAULT PRIVILEGES FOR ROLE myapp_migrator IN SCHEMA public
    GRANT USAGE, SELECT ON SEQUENCES TO myapp_runtime;
REVOKE TEMPORARY ON DATABASE myapp FROM PUBLIC;
```

Tables created before the default privileges existed need an explicit
`GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO
myapp_runtime` (and the same for sequences). Moving an existing application
that served and migrated as one role: create both roles, `ALTER TABLE ...
OWNER TO` the migration role for each table (or `REASSIGN OWNED BY old TO
myapp_migrator`), grant as above, then point `FORGE_DATABASE_URL` at the
runtime role and `FORGE_MIGRATION_DATABASE_URL` at the migration role.

A data migration that reads or writes a tenant table runs as the migration
role, which `FORCE` subjects to the policy: set the tenant inside it
(`SELECT set_config('forge.tenant_id', '<tenant uuid>', true)`).

Escape hatches for features Forge does not wrap: `(*postgres.DB).Pool()`
returns the `*pgxpool.Pool` (for `COPY` or `LISTEN`/`NOTIFY`), and
`(*sqldb.DB).SQL()` returns the `*sql.DB`.

## Repositories and `DBTX`

Repositories depend on a `DBTX` interface so they run on the pool or inside
a transaction:

| Adapter | Interface | Satisfied by | sqlc target |
| ------- | --------- | ------------ | ----------- |
| `postgres` | `postgres.DBTX`: `Exec`, `Query`, `QueryRow` (pgx signatures) | `*postgres.DB`, `pgx.Tx` | `pgx/v5` |
| `mysql`, `sqlite` | `sqldb.DBTX`: `ExecContext`, `PrepareContext`, `QueryContext`, `QueryRowContext` | `*sqldb.DB`, `*sql.DB`, `*sql.Tx`, `*sql.Conn` | `database/sql` |

Forge does not bundle or configure sqlc. sqlc's `:copyfrom` for pgx also
needs `CopyFrom`, which `*postgres.DB` does not have; use `Pool()` for that.

A PostgreSQL repository with a keyset-paginated list:

```go
package persistence

import (
	"context"
	"errors"

	"github.com/jackc/pgx/v5"

	"github.com/rocketinsidecorp/forge-go/fault"
	"github.com/rocketinsidecorp/forge-go/pagination"
	"github.com/rocketinsidecorp/forge-go/postgres"
	"github.com/rocketinsidecorp/forge-go/uuid"
)

type Note struct {
	ID      uuid.UUID
	Body    string
	Version int
}

var ErrNoteNotFound = fault.New("note_not_found", "note not found", fault.CategoryNotFound, 0)

type NoteRepository struct{ db postgres.DBTX }

func NewNoteRepository(db postgres.DBTX) *NoteRepository { return &NoteRepository{db: db} }

func (r *NoteRepository) Create(ctx context.Context, note Note) error {
	_, err := r.db.Exec(ctx,
		`INSERT INTO notes (id, body, version) VALUES ($1, $2, $3)`,
		note.ID, note.Body, note.Version)
	return postgres.Translate(err) // nil stays nil
}

func (r *NoteRepository) Get(ctx context.Context, id uuid.UUID) (Note, error) {
	var note Note
	err := r.db.QueryRow(ctx, `SELECT id, body, version FROM notes WHERE id = $1`, id).
		Scan(&note.ID, &note.Body, &note.Version)
	if errors.Is(err, pgx.ErrNoRows) {
		return Note{}, ErrNoteNotFound // domain-specific, instead of the generic not_found
	}
	return note, postgres.Translate(err)
}

// List returns one page, newest first.
func (r *NoteRepository) List(ctx context.Context, page pagination.Request) (pagination.Page[Note], error) {
	// One extra row tells NewPage whether another page exists.
	var rows pgx.Rows
	var err error
	if page.HasCursor() {
		rows, err = r.db.Query(ctx,
			`SELECT id, body, version FROM notes WHERE id < $1 ORDER BY id DESC LIMIT $2`,
			page.After, page.Limit+1)
	} else {
		rows, err = r.db.Query(ctx,
			`SELECT id, body, version FROM notes ORDER BY id DESC LIMIT $1`,
			page.Limit+1)
	}
	if err != nil {
		return pagination.Page[Note]{}, postgres.Translate(err)
	}
	notes, err := pgx.CollectRows(rows, func(row pgx.CollectableRow) (Note, error) {
		var note Note
		err := row.Scan(&note.ID, &note.Body, &note.Version)
		return note, err
	})
	if err != nil {
		return pagination.Page[Note]{}, postgres.Translate(err)
	}
	return pagination.NewPage(notes, page.Limit, func(n Note) uuid.UUID { return n.ID }), nil
}
```

The same list with `database/sql` (MySQL shown; for SQLite use
`sqlite.Translate`, with the same `?` placeholders):

```go
type NoteRepository struct{ db sqldb.DBTX }

func (r *NoteRepository) Get(ctx context.Context, id uuid.UUID) (Note, error) {
	var note Note
	err := r.db.QueryRowContext(ctx, `SELECT id, body, version FROM notes WHERE id = ?`, id).
		Scan(&note.ID, &note.Body, &note.Version)
	if errors.Is(err, sql.ErrNoRows) {
		return Note{}, ErrNoteNotFound
	}
	return note, mysql.Translate(err)
}

func (r *NoteRepository) List(ctx context.Context, page pagination.Request) (pagination.Page[Note], error) {
	query, args := `SELECT id, body, version FROM notes ORDER BY id DESC LIMIT ?`, []any{page.Limit + 1}
	if page.HasCursor() {
		query = `SELECT id, body, version FROM notes WHERE id < ? ORDER BY id DESC LIMIT ?`
		args = []any{page.After, page.Limit + 1}
	}
	rows, err := r.db.QueryContext(ctx, query, args...)
	if err != nil {
		return pagination.Page[Note]{}, mysql.Translate(err)
	}
	defer rows.Close()
	var notes []Note
	for rows.Next() {
		var note Note
		if err := rows.Scan(&note.ID, &note.Body, &note.Version); err != nil {
			return pagination.Page[Note]{}, mysql.Translate(err)
		}
		notes = append(notes, note)
	}
	if err := rows.Err(); err != nil {
		return pagination.Page[Note]{}, mysql.Translate(err)
	}
	return pagination.NewPage(notes, page.Limit, func(n Note) uuid.UUID { return n.ID }), nil
}
```

In the HTTP adapter, `pagination.FromQuery(r.URL.Query())` reads `cursor`
and `limit` (default `50`, maximum `200`) and returns a `400` fault for
invalid values. `pagination.Page[T]` serializes as
`{"items":[...],"next_cursor":"..."}`, with `next_cursor` omitted on the last
page. The cursor is the last item's UUIDv7, base64url-encoded without
padding; decoding is strict and accepts only a UUIDv7.

Keyset pagination over the primary key uses the index directly, costs the
same at any depth, and does not skip or repeat rows when rows are inserted
between requests, unlike `OFFSET`. It orders by creation time only; sorting
by another column needs a cursor over that column, which `pagination` does not
provide.

## Transactions

```go
// PostgreSQL
err := db.InTx(ctx, func(tx pgx.Tx) error {
	return persistence.NewNoteRepository(tx).Create(ctx, note)
})

// MySQL, MariaDB, SQLite (*sqldb.DB)
err := db.InTx(ctx, func(tx *sql.Tx) error {
	return persistence.NewNoteRepository(tx).Create(ctx, note)
})
```

- `InTx` commits when `fn` returns `nil` and rolls back when `fn` returns an
  error or panics (the panic continues after the rollback). `fn`'s error is
  returned unchanged, so faults from repositories reach the caller as they
  are. `BEGIN` and `COMMIT` failures are returned wrapped; pass the result
  through the adapter's `Translate` if it goes to a client.
- Queries must go through `tx`. A repository built on the pool inside `fn`
  runs outside the transaction. `InTx` is not re-entrant: calling it inside
  `fn` starts a second, independent transaction on another connection.
- PostgreSQL rolls back with its own 5-second deadline, detached from `ctx`,
  so a cancelled request still releases its connection; `database/sql` rolls
  back by itself when the context is cancelled.

`InTxWith` takes `postgres.TxOptions` or `sqldb.TxOptions`:

| Field       | PostgreSQL | MySQL / MariaDB | SQLite |
| ----------- | ---------- | --------------- | ------ |
| `Isolation` | `postgres.ReadCommitted` (default), `RepeatableRead`, `Serializable` | a `sql.IsolationLevel`; default is the server's (`REPEATABLE READ` for InnoDB) | ignored by the driver; SQLite transactions are serializable |
| `ReadOnly`  | `READ ONLY` transaction | read-only transaction | begins a deferred transaction instead of an immediate one; it does not block writes |
| `Attempts`  | maximum runs of the whole transaction; values below 1 mean 1 (no retry) | same | same |

A retry happens only for errors classified as a conflict, whether they came
from a statement, from `fn` (a translated fault keeps the original error as
its cause), or from `COMMIT`:

| Database | Retried errors |
| -------- | -------------- |
| PostgreSQL | `40001` serialization failure, `40P01` deadlock |
| MySQL / MariaDB | `1213` deadlock, `1205` lock wait timeout |
| SQLite | `SQLITE_BUSY`, `SQLITE_LOCKED` (the write lock stayed taken longer than `busy_timeout`) |

Between attempts it waits 10 ms, doubling up to 500 ms. If `ctx` ends while
waiting, the last error is returned joined with the context error.
`SERIALIZABLE` transactions on PostgreSQL should always set `Attempts`.

**No side effects inside a transaction function.** On retry, `fn` runs again
from the start. It must not send email, call external APIs, publish messages,
or change state outside the transaction, because those effects either repeat
or remain after a rollback. Do such work after the transaction commits.
The Phase 4 foundation provides `events.Event` and
`outbox/postgres.Insert`. Pass the active `pgx.Tx` from `postgres.InTx` so the
event row commits or rolls back with the domain change. A PostgreSQL
dispatcher can deliver these events with bounded concurrency and retries;
delivery is at-least-once, so consumers must be idempotent. Start it with
`outbox/postgres.NewDispatcher(db.Pool(), handler, options)` and run it under
an application-owned context. Handler calls happen outside database
transactions, and the dispatcher renews its lease while the handler runs.
Each worker claims up to `DispatcherOptions.BatchSize` events (default 10) in
one transaction and delivers them in order, acknowledging each on its own.
Canceling the context stops the dispatcher between its own statements: it
cancels the running handler, records that handler's result (an
acknowledgement, a retry, or a dead letter on its last attempt), and hands
back the events not yet started without using an attempt. Each of those
statements is bounded to 5 seconds, including waiting for a pool connection,
so a worker can take about 15 seconds past its handler's return to stop
(record, the last lease renewal, release); workers stop in parallel. Keep
`FORGE_HTTP_SHUTDOWN_TIMEOUT` (30 s by default) above that, plus the time your
handlers need to honour cancellation.
Dead-letter rows are retained for operator inspection; automated replay and
queue metrics are not yet provided. See
[ADR 0018](adr/0018-transactional-outbox-foundation.md) and
[ADR 0019](adr/0019-outbox-dispatch.md). Both outbox migrations are
intentionally irreversible because rollback would delete persisted event data.

## Optimistic locking

Give the table an integer `version` column and make every write conditional
on the version the caller read. PostgreSQL and SQLite support `RETURNING`:

```sql
UPDATE notes
SET body = $3, version = version + 1
WHERE id = $1 AND version = $2
RETURNING id, body, version
```

MySQL has no `UPDATE ... RETURNING`; check the affected row count instead:

```go
result, err := r.db.ExecContext(ctx,
	`UPDATE notes SET body = ?, version = version + 1 WHERE id = ? AND version = ?`,
	body, id, expectedVersion)
if err != nil {
	return mysql.Translate(err)
}
if n, err := result.RowsAffected(); err != nil || n == 1 {
	return mysql.Translate(err)
}
// zero rows: see below
```

Zero rows means either the row no longer exists or someone else wrote it
first. Distinguish the two before answering:

```go
var exists bool
if err := r.db.QueryRowContext(ctx, `SELECT EXISTS (SELECT 1 FROM notes WHERE id = ?)`, id).Scan(&exists); err != nil {
	return mysql.Translate(err)
}
if !exists {
	return ErrNoteNotFound // 404
}
return ErrStaleNote // 409: reload and retry
```

Clients send back the version they received. `examples/basic-api`
(PostgreSQL) uses this pattern for completing a task.

## Error translation

Each adapter's `Translate(err)` maps driver errors to a database-independent
kind, and `sqldb.Translate` maps kinds to faults, so every database produces
the same public codes. The result is a `*fault.Error` that is safe to send
to clients: a stable code, a generic message, and an HTTP status. The
original error stays in the chain (`Cause`) for logs and
`errors.Is`/`errors.As`. `nil` and errors that already contain a
`*fault.Error` pass through unchanged.

| Code | Status | Retryable | PostgreSQL | MySQL / MariaDB | SQLite |
| ---- | ------ | --------- | ---------- | --------------- | ------ |
| `not_found` | 404 | no | `pgx.ErrNoRows` | `sql.ErrNoRows` | `sql.ErrNoRows` |
| `timeout` | 503 | yes | `context.DeadlineExceeded`; `57014` | `context.DeadlineExceeded`; `3024` (MySQL), `1969` (MariaDB) | `context.DeadlineExceeded`; `SQLITE_INTERRUPT` |
| `canceled` | 503 | yes | `context.Canceled` | `context.Canceled` | `context.Canceled` |
| `already_exists` | 409 | no | `23505` | `1062` | `SQLITE_CONSTRAINT_UNIQUE`, `SQLITE_CONSTRAINT_PRIMARYKEY` |
| `reference_violation` | 409 | no | `23503` | `1451`, `1452` | `SQLITE_CONSTRAINT_FOREIGNKEY` |
| `conflict` | 409 | no | `23P01` exclusion | - | - |
| `constraint_violation` | 400 | no | `23514` check, `22001`, `22003`, `22007`, `22008` | `3819` (MySQL check), `4025` (MariaDB check), `1406` too long, `1264` out of range, `1292` bad value | `SQLITE_CONSTRAINT_CHECK`, `SQLITE_CONSTRAINT_DATATYPE` (STRICT type mismatch) |
| `transaction_conflict` | 409 | yes | `40001`, `40P01` | `1213`, `1205` | `SQLITE_BUSY`, `SQLITE_LOCKED` |
| `database_unavailable` | 503 | yes | `*pgconn.ConnectError`, `53300`, `57P01`, `57P03`, class `08` | invalid/bad connection, network errors, `1040`, `1203`, `1053` | `SQLITE_FULL`, `SQLITE_IOERR`, `SQLITE_CANTOPEN` |
| `internal_error` | 500 | no | anything else, including `23502` not null and other class `22` errors | anything else, including `1048` not null | anything else, including `SQLITE_CONSTRAINT_NOTNULL` |

Only errors a client can cause by sending bad values map to `400`. A NOT NULL
violation or a failed cast usually means the application passed the wrong
value, so it is a server error; `web.Error` logs `5xx` responses with the
fault's cause. Validate input in the domain before it reaches the database,
and treat `constraint_violation` as the last line of defence.

For `already_exists`, `reference_violation`, `conflict`, and
`constraint_violation`, the constraint the database reported, if any, is
stored in `Metadata["constraint"]`. `web.Error` serializes only `code` and
`message`, never metadata, causes, SQL, or constraint names.

To give a specific constraint its own domain error, check it before
translating:

```go
if postgres.ConstraintName(err) == "notes_slug_key" {
	return ErrSlugTaken
}
return postgres.Translate(err)
```

What `ConstraintName` returns depends on the database:

| Adapter | `ConstraintName` | Raw code |
| ------- | ---------------- | -------- |
| `postgres` | the constraint name | `postgres.SQLState(err)` |
| `mysql` | parsed from the message: `table.key` on MySQL 8 and `key` on MariaDB for duplicates; the constraint name for foreign keys and checks | `mysql.ErrorNumber(err)` |
| `sqlite` | `table.column` for UNIQUE/PRIMARY KEY and STRICT type errors, the CHECK name (or expression if unnamed); nothing for foreign keys | `sqlite.ErrorCode(err)` (extended code; `& 0xff` for the primary code) |

`*fault.Error` values compare by `Code` in `errors.Is`, so a domain sentinel
such as `ErrNoteNotFound` is still recognized after `WithCause` or wrapping.
`errors.Is(err, sql.ErrNoRows)` (or `pgx.ErrNoRows`) also keeps working on a
translated error, because the original error is its cause.

## Advisory locks (PostgreSQL)

```go
err := db.InTx(ctx, func(tx pgx.Tx) error {
	acquired, err := postgres.TryAdvisoryXactLock(ctx, tx, postgres.LockKey("billing:invoice-run"))
	if err != nil || !acquired {
		return err // another process is doing it
	}
	// work that must not run concurrently across processes
	return nil
})
```

- `LockKey(name)` hashes a descriptive name to a 64-bit key (FNV-1a). Use
  distinct, namespaced names. Do not use the `forge:` prefix; the migrator
  uses `forge:schema_migrations`.
- `AdvisoryXactLock` waits for the lock; `TryAdvisoryXactLock` reports whether
  it got it. Both are transaction-scoped: PostgreSQL releases the lock at
  commit or rollback, so it cannot leak.
- A blocking wait is a statement and is bounded by
  `FORGE_DATABASE_STATEMENT_TIMEOUT`; on timeout it fails with `57014`.

The MySQL and SQLite adapters provide no application-level lock helpers.

## Migrations

The engine is the `migrate` package; each adapter supplies a dialect
(placeholders, session preparation, a non-blocking lock, table lookup) and a
dedicated connection pool that is never shared with the application. See
[ADR 0008](adr/0008-sql-migrations-embedded-in-the-binary.md) and
[ADR 0009](adr/0009-multiple-databases.md).

### Files

Generated applications keep migrations in `db/migrations`. `db/db.go` embeds
them with `//go:embed all:migrations` (`all:` includes the `.keep` file, so
the directory can be empty) and exposes them through `db.Migrations()`.

```text
db/migrations/20260926143000_create_notes.up.sql
db/migrations/20260926143000_create_notes.down.sql   (optional)
```

- File names must match `<YYYYMMDDHHMMSS>_<name>.<up|down>.sql`, where the
  name uses lowercase letters, digits, and underscores. Any other `*.sql` file
  is an error, so a typo cannot silently skip a migration. Non-`.sql` files
  are ignored, as are subdirectories.
- Every file must contain SQL besides `--` comment lines and whitespace.
- A file may contain several statements.
- A migration without a `.down.sql` file is irreversible.
- Write the SQL of the database you use; migrations are not portable between
  databases.

### Composing framework and application migrations

`migrate.LoadMigrationSets` validates and merges independent migration
filesystems into one version-ordered history. This is useful when an
application owns `db/migrations` while a framework subsystem such as
`auth/postgres` contributes its own embedded schema.

Migration versions remain globally unique across every set. A duplicate version
between framework and application migrations is an error even when the names or
SQL differ. Set validation and collision detection happen before a database
connection opens.

For operational commands, every adapter exposes `CommandsFromSets(...fs.FS)`.
For example, a PostgreSQL application that owns migrations and enables Forge
identity can register:

```go
forge.Main(
    bootstrap.Configure,
    postgres.CommandsFromSets(db.Migrations(), authpostgres.Migrations())...,
)
```

The resulting `migrate`, `migrate status`, and `rollback` commands operate
on the same merged history and the same `forge_schema_migrations` table.

### Framework migrations

The migrations Forge packages ship (identity, outbox, agent journal, job
queue, scheduled job ticks, rate limiter, cache) are registered by version, name and owning package
in `migrate.FrameworkMigrations()`
([ADR 0039](adr/0039-framework-migration-ownership.md)):

- `rollback` reverts only your own migrations, the most recently applied
  first, even when a framework migration was applied after them. When only
  framework migrations are left it reverts nothing and fails (exit status 1)
  with `nothing to roll back: every applied migration belongs to Forge
  (newest <version>_<name>, from the <package> package) ...`.
- Removing a framework set from `CommandsFromSets` (turning the feature off)
  keeps `migrate` and `rollback` working: its applied migrations stay, with
  their tables, and `migrate status` shows them as `disabled`. Adding the set
  back finds them applied and verifies their checksums.
- A framework version is reserved: an application migration with that version
  and another name is refused before the database is contacted.
- Reverting a framework migration is deliberate library code, never a
  command: `Migrator.DownFramework(ctx, steps)` reverts the most recently
  applied framework migrations the migrator contains and never one of yours.
  The job queue, scheduled job ticks, rate-limit, cache and outbox migrations have no down script
  and are refused as irreversible.

```sh
forge db rollback -steps 3   # your three newest migrations; framework tables stay
forge db status              # framework migrations of a set you removed: "disabled"
```

`forge generate migration NAME` (run in the application root) creates the
pair with the current UTC time as the version. `NAME` must match
`^[a-z][a-z0-9_]{0,99}$`. If another migration in `db/migrations` already
uses that second, or the second is a framework migration's reserved version
(`migrate.FrameworkMigrations()`, which the migrator would refuse alongside
yours), the version is moved forward one second at a time until it is free.
The model, resource, scaffold and controller generators choose their
migration versions the same way. Existing files are never
overwritten. Both generated files contain only comments, so the migrator
refuses them until you write the SQL. Delete the `.down.sql` file if the
change cannot be reverted.

### Transactions and `-- forge:no-transaction`

Each migration file runs in a transaction together with the insert (or, for
rollback, the delete) of its row in `forge_schema_migrations`. How much that
protects depends on the database:

| Database | A failing migration |
| -------- | ------------------- |
| PostgreSQL | leaves nothing behind: DDL is transactional |
| SQLite | leaves nothing behind: DDL is transactional |
| MySQL / MariaDB | leaves the statements before the failure applied: DDL commits implicitly. The migration is not recorded. Keep each migration small, ideally one DDL statement, and write it so it can be completed by hand. |

A first line of `-- forge:no-transaction` runs that file (up and down are
separate) without the engine's transaction; its row is recorded afterwards.

- **PostgreSQL:** needed for statements PostgreSQL forbids in a transaction,
  such as `CREATE INDEX CONCURRENTLY`. Put exactly one statement in such a
  file: PostgreSQL runs a multi-statement query string as one implicit
  transaction, which these statements reject. A failed
  `CREATE INDEX CONCURRENTLY` leaves an invalid index that you must drop by
  hand before retrying.

  ```sql
  -- forge:no-transaction
  CREATE INDEX CONCURRENTLY IF NOT EXISTS notes_created_by_idx ON notes (created_by);
  ```

- **SQLite:** needed to rebuild a table that other tables reference (SQLite's
  way to change a column), because `PRAGMA foreign_keys` is ignored inside a
  transaction. If a statement fails, the migration session is closed, which
  rolls the rebuild back:

  ```sql
  -- forge:no-transaction
  PRAGMA foreign_keys = OFF;
  BEGIN;
  CREATE TABLE notes_new (...);
  INSERT INTO notes_new SELECT ... FROM notes;
  DROP TABLE notes;
  ALTER TABLE notes_new RENAME TO notes;
  COMMIT;
  PRAGMA foreign_keys = ON;
  ```

### Fail-closed rules

`migrate` and `rollback` refuse to run when:

- an applied migration's up script changed (its SHA-256 checksum differs);
  add a new migration instead of editing an applied one. Only the up script
  is checksummed, so a down script may be edited after the migration was
  applied, for example to fix a broken rollback;
- the database contains a version this build does not know, which usually
  means an older release is deploying over a newer schema (a registered
  framework migration whose set you no longer compose is not unknown: it is
  tolerated as `disabled`);
- a migration, in the build or recorded in the database, uses a framework
  migration's reserved version under another name;
- a file name does not follow the convention, a file is empty, a version is
  used by two names, or a down script has no up script;
- a rollback includes an irreversible migration: every step is checked
  before any is reverted.

Problems with the files themselves also stop `migrate status`, because files
are validated before the database is contacted.

A pending migration whose version is older than the newest applied one is
still applied (out-of-order application), so parallel branches can merge.

### Bookkeeping, locking, and sessions

Applied migrations are recorded in a table with portable types:

```sql
CREATE TABLE IF NOT EXISTS forge_schema_migrations (
    version    BIGINT       PRIMARY KEY,
    name       VARCHAR(255) NOT NULL,
    checksum   CHAR(64)     NOT NULL,
    applied_at BIGINT       NOT NULL  -- Unix microseconds, written by the migrator
);
```

Every `migrate` and `rollback` run uses a dedicated session and takes a
cross-process lock first, so concurrent runs from several replicas or jobs
are serialized and each migration is applied once. The lock is taken without
blocking inside the database and polled (50 ms, doubling to 1 s; the wait
ends when the process is interrupted), because a blocked lock statement
would deadlock with `CREATE INDEX CONCURRENTLY` in the holder on PostgreSQL.
While waiting, the migrator logs
`waiting for another process to finish migrating`. Sessions are never
reused, so settings a migration changes cannot leak.

| Database | Lock | Session preparation |
| -------- | ---- | ------------------- |
| PostgreSQL | session advisory lock (`pg_try_advisory_lock`) on key `LockKey("forge:schema_migrations")` | `statement_timeout = 0` |
| MySQL / MariaDB | `GET_LOCK(name, 0)`; the name includes a hash of the current database, so migrations of different databases on one server do not wait for each other. Released when the session closes. | statement timeout lifted (`max_execution_time` or `max_statement_time` set to 0); multi-statement execution enabled on this pool only |
| SQLite | an operating-system file lock (a write transaction on a sidecar SQLite file `<database>-migrate.lock`, created `0600`). The kernel releases it if the process dies, so no stale lock is left. It works for processes on one host, including containers sharing a volume, but not reliably on network file systems. | none (no statement timeout) |

`migrate status` is read-only: it takes no lock, so it answers while a long
migration runs, and it does not create the table; a database that was never
migrated shows every migration as pending. It reports modified and unknown
migrations instead of refusing.

### Commands

Application binaries with one migration set are still built with
`forge.Main(bootstrap.Configure, <adapter>.Commands(db.Migrations())...)`.
Applications composing framework and application schemas use the adapter's
`CommandsFromSets` helper instead. In both cases the binary
accepts:

| Command | Effect |
| ------- | ------ |
| `<app> migrate` | Apply pending migrations in version order; prints each one, or `database is up to date` |
| `<app> migrate status` | One line per migration: `applied`, `pending`, `modified` (changed after applying), `unknown` (in the database, not in the build), or `disabled` (a framework migration whose set the build no longer composes), with the UTC apply time |
| `<app> rollback [-steps N]` | Revert the `N` most recently applied application migrations (default 1), last applied first; framework migrations are never reverted |

`rollback` orders by `applied_at` (then by version, for migrations applied in
the same microsecond), so after an out-of-order migration it reverts the one
that was actually applied last, not the highest version. It skips framework
migrations ([Framework migrations](#framework-migrations)).

Invalid arguments (`migrate foo`, `rollback -steps 0`) exit with status `2`;
other failures exit with `1`. These commands load the same `FORGE_*`
configuration as `serve`, so the production rules also apply, and they fail
if `FORGE_DATABASE_URL` is empty. They connect as the migration role of
`FORGE_MIGRATION_DATABASE_URL` when it is set ([Database
roles](#database-roles-postgresql)).

During development:

| Command | Effect |
| ------- | ------ |
| `forge migrate [status]` | Build `cmd/<name>` and run `<app> migrate [status]` |
| `forge rollback [-steps N]` | Build `cmd/<name>` and run `<app> rollback [-steps N]` |
| `docker compose up` | The `migrate` service runs `migrate` once; `app` starts only after it succeeds |
| `docker compose run --rm migrate rollback` | Roll back inside the Compose stack |

`forge migrate` and `forge rollback` load `.env.development` and
`.env.local` (see the
[README](../README.md#development-environment-files)) and require a single
command under `cmd/`.

### Database lifecycle (`forge db`)

`forge db` is the Rails `db:*` family for the development loop
([ADR 0035](adr/0035-development-loop.md)). `forge migrate`, `forge rollback`
and `forge seed` stay as aliases of `forge db migrate|rollback|seed`.

| Command | Effect |
| ------- | ------ |
| `forge db create` | Create the database named in `FORGE_DATABASE_URL`; a no-op when it exists |
| `forge db drop` | Drop it (PostgreSQL: `WITH (FORCE)`, ending open sessions); a no-op when absent |
| `forge db setup` | `create`, then `migrate`, then `seed` |
| `forge db prepare` | `setup` when the database is missing, else `migrate`; safe to run on every start |
| `forge db reset` | `drop`, then `setup` |
| `forge db migrate` / `status` / `rollback [-steps N]` / `seed` | Build the application and run its command of that name |
| `forge db schema:dump` | Write `db/schema.sql` |
| `forge db schema:load` | Run `db/schema.sql` into an existing, empty database |
| `forge db console [-- ARGS]` | Open `psql`, `mysql` or `sqlite3` on the database; `ARGS` go to the client |

```sh
forge db prepare
forge db schema:dump && git add db/schema.sql
# CI or a test database:
forge db create && forge db schema:load
```

**Which server connection.** `create` and `drop` cannot connect to the database
they create or remove. PostgreSQL uses the `postgres` maintenance database
(then `template1`), MySQL and MariaDB `information_schema`; SQLite creates or
deletes the file (`0600`) and its `-wal`, `-shm`, `-journal` and
`-migrate.lock` companions. By default the credentials are those of
`FORGE_DATABASE_URL`, so that role needs `CREATEDB` (PostgreSQL) or
`CREATE`/`DROP` (MySQL). Set `FORGE_MIGRATION_DATABASE_URL` to a privileged
role instead: it is validated like `FORGE_DATABASE_URL`, must use the same
adapter, and its database is ignored (the target is always the one in
`FORGE_DATABASE_URL`). It is used by `create`, `drop`, `schema:*` and
`console`, and the application's own `migrate` and `rollback` connect as it
too ([Database roles](#database-roles-postgresql)). These commands refuse either URL when its query picks the server or database (`host`, `hostaddr`, `port`, `dbname`, `service` and the like): put them in the URL's host, port and path, which is what the local-database check reads. A port must be a number from 1 to 65535 without leading zeros. A
database name must be 1-63 characters of letters, digits, `_`, `-` or `$`;
`postgres`, `template0`, `template1`, `mysql`, `information_schema`,
`performance_schema` and `sys` are never created or dropped.

**Behaviour change (QG1).** `<app> migrate` and `<app> rollback` used
`FORGE_DATABASE_URL` even when `FORGE_MIGRATION_DATABASE_URL` was set; they now
connect as the role it names, so new tables belong to that role. If it names
an administrator only meant for `create` and `drop`, give the serving role its
grants (see [Database roles](#database-roles-postgresql)) or unset it.

**Behaviour change (forge-go#23, #24).** A raw space, tab or other control
character in a database URL's query is refused when the configuration loads;
percent-encode it (`%20`). `forge db` also refuses session-setting query
parameters on the URL it connects with (`FORGE_MIGRATION_DATABASE_URL`, or
`FORGE_DATABASE_URL` when it is not set): `options` (`-c search_path=...`),
and any other parameter pgx would send as a session setting such as
`search_path`. The application's own `FORGE_DATABASE_URL` may still carry
`options` when a privileged URL is set. `forge db` does not read the `PG*`
variables of forge's own environment (`PGSSLMODE`, `PGOPTIONS`,
`PGSERVICE`, `PGUSER` and the rest) for its PostgreSQL connection, as for
`psql` and `pg_dump`: a URL without `sslmode` uses libpq's default `prefer`.
The variables are neutralized by naming the default of each in the URL given
to pgx (a service named by `PGSERVICE` is replaced by an empty one), never by
unsetting them in the running process.
Put `sslmode` and the other settings in the URL; a `PGSSLROOTCERT`,
`PGSSLCERT`, `PGSSLKEY` or `PGSSLPASSWORD` the URL does not name makes
`forge db` refuse to connect, naming the variable. A missing `sslrootcert`,
`sslcert` or `sslkey` file is reported as an invalid TLS setting.

**Schema file.** `schema:dump` runs `pg_dump --schema-only --no-owner
--no-privileges`, `mysqldump --no-data --skip-add-drop-table` or `sqlite3
.schema` (the tool must be on `PATH`; a PostgreSQL `pg_dump` must be at least
the server's major version) and makes the output deterministic: version and
date comments, `pg_dump`'s random `\restrict` tokens and MySQL `AUTO_INCREMENT`
counters are removed. Row-level-security policies are part of the dump. The
applied migrations follow as `INSERT INTO forge_schema_migrations ... applied_at
= 0` statements, so a database built by `schema:load` already knows its history
and `forge db migrate` reports it up to date. `schema:load` uses
`psql --single-transaction`, `mysql` or `sqlite3` inside a transaction and fails
instead of replacing tables that already exist. Migrations remain the history of
record; the schema file is for fresh databases.

**Credentials are never arguments.** PostgreSQL tools receive `PGHOST`,
`PGUSER`, `PGPASSWORD`, `PGDATABASE` and `PGSSL*` in their environment (any
inherited `PG*` variable is dropped first, and pgx's own connection ignores
them too); MySQL tools read a `0600` temporary option file passed first as `--defaults-file` (the only option file they read,
so `~/.my.cnf` cannot redirect them) and removed afterwards; SQLite takes
an absolute path. Error messages name the host and database, never the URL.

**Protected databases.** `drop`, `reset`, `schema:load` and `rollback` refuse to
run unless the database is local and `FORGE_ENV` is `development` or `test`.
Production and staging, and any server that is not on this machine (loopback,
`localhost`, a Unix socket path and SQLite files are local), need
`--force-production` and either typing the database name at the prompt, or
`--yes` with `FORGE_ALLOW_DESTRUCTIVE=true` in the process environment (an env
file cannot set it). This holds even when `FORGE_ENV` is unset, which defaults to
`development`: the server address decides. `schema:load` and `console` also
refuse system databases such as `postgres`. Ctrl-C in `forge db console` goes to
the client, not to forge. PostgreSQL-only capabilities
(row-level security, roles, `LISTEN/NOTIFY`) are not emulated on other backends;
`forge db` behaves the same on every adapter, and tenant isolation on MySQL,
MariaDB and SQLite remains the repositories' predicates.

### Production

Migrations are an explicit release step; `serve` never applies them.

1. Build the release image. It contains the migrations.
2. Run `<app> migrate` from that image with the production environment, as a
   one-off container or a Kubernetes Job:

   ```sh
   docker run --rm -e FORGE_DATABASE_URL="$DATABASE_URL" \
     -e FORGE_MIGRATION_DATABASE_URL="$MIGRATION_DATABASE_URL" myapp:1.4.0 migrate
   ```

   On PostgreSQL, `FORGE_MIGRATION_DATABASE_URL` is the migration role that
   owns the schema; never give it to the serving containers, which get only
   `FORGE_DATABASE_URL` ([Database roles](#database-roles-postgresql)).
   `forge deploy` gives it to the migrate step alone through `migrate.env`
   in `config/deploy.yml` ([DEPLOYMENT.md](DEPLOYMENT.md#database-roles)).

   For SQLite, mount the same volume the application uses:

   ```sh
   docker run --rm -v myapp-storage:/app/storage myapp:1.4.0 migrate
   ```

3. Roll out the new application version only after the command exits `0`.

If `migrate` fails, migrations applied before the failing one in the same run
stay applied; the failing one is rolled back on PostgreSQL and SQLite, but
may be partly applied on MySQL and MariaDB. Fix forward with a new migration,
or roll back explicitly. Starting several `migrate` runs at once is safe:
they wait for each other.

### Zero-downtime changes

During a rolling deploy, the old and new application versions run against
the same schema. Write migrations that both can use:

- **Expand, then contract.** Add new columns, tables, or indexes in one
  release; switch the code to them; remove the old ones in a later release.
  Renaming a column in place breaks the version still running.
- **New columns:** make them nullable or give them a constant default. Add
  `NOT NULL` after a backfill.
- **Backfills:** batch large updates rather than rewriting a big table in one
  transaction.
- **Avoid long locks.** Migration sessions have no statement timeout. An
  `ALTER TABLE` waiting for its lock blocks every query queued behind it.

PostgreSQL specifics:

- Indexes on existing tables: `CREATE INDEX CONCURRENTLY` in its own
  `-- forge:no-transaction` file (and `DROP INDEX CONCURRENTLY` in the down
  script).
- Constraints on existing tables: add them `NOT VALID`, then
  `VALIDATE CONSTRAINT` in a later migration; validation does not block
  writes.
- In transactional migrations, start with `SET LOCAL lock_timeout = '5s';`
  so a blocked migration fails instead of stalling traffic, then retry it.

MySQL and MariaDB: request online DDL explicitly (`ALGORITHM=INSTANT` or
`ALGORITHM=INPLACE, LOCK=NONE`) so the server fails the statement instead of
silently copying and locking the table.

SQLite: a migration holds the database's write lock for its whole
transaction, so requests that write wait (up to `busy_timeout`) until it
commits. Keep migrations short.

## UUIDv7 identifiers

Forge's identifier is the UUIDv7 in the `uuid` package
([ADR 0001](adr/0001-uuidv7-default-identifier.md)). Generate IDs in Go
(`uuid.New()`) before the insert, so the application knows the ID without a
round trip and tests can inject it.

| Database | Column type | Notes |
| -------- | ----------- | ----- |
| PostgreSQL | `uuid` | `uuid.UUID` is passed to pgx and scanned directly. Generated tables have no default: an insert without an ID fails instead of minting one in the database. |
| MySQL / MariaDB | `CHAR(36)` | `uuid.UUID` is written and read as its canonical text. |
| SQLite | `TEXT` | same as MySQL. |

```sql
CREATE TABLE notes (
    id      uuid    PRIMARY KEY,
    body    text    NOT NULL,
    version integer NOT NULL DEFAULT 1 CHECK (version >= 1)
);
```

- Forge's identity tables (`auth/postgres`) have no id default either: the
  repositories generate the ids, so applications with Forge identity run on
  PostgreSQL 16 and 17 too. (They declared `DEFAULT uuidv7()` until forge-go
  QG9; the migrations were edited before any release, and a database that
  applied the earlier text still verifies.) When an application migration
  fails on an older server with
  `function uuidv7() does not exist` (SQLSTATE 42883), the error adds the
  server version and the two ways out: PostgreSQL 18, or a `uuidv7()`
  function defined by an earlier migration. The failed migration is rolled
  back; the ones before it stay applied. Nothing scans migrations in advance,
  so an application that defines its own `uuidv7()` keeps working.
- `uuid.UUID` accepts only version 7 when parsing or scanning. Do not use
  version 4 defaults such as `gen_random_uuid()` or MySQL's `UUID()`
  (version 1).
- UUIDv7 values begin with a millisecond timestamp. PostgreSQL compares
  `uuid` values bytewise, and the canonical lowercase text form sorts the
  same way, so `ORDER BY id` is creation order at millisecond precision on
  every database. IDs from one process are also strictly increasing within a
  millisecond; IDs from different processes in the same millisecond are not
  ordered by creation. Keyset pagination (`WHERE id < ? ORDER BY id DESC`)
  needs no extra index.
- A UUIDv7 reveals its creation time. Do not use one where that is sensitive.

## Testing

| Adapter | Package | Server URL | Needs |
| ------- | ------- | ---------- | ----- |
| PostgreSQL | `postgres/postgrestest` | `FORGE_TEST_POSTGRES_URL`, else `FORGE_TEST_DATABASE_URL` if it is a `postgres://` URL | a user that can create databases |
| MySQL / MariaDB | `mysql/mysqltest` | `FORGE_TEST_MYSQL_URL`, else `FORGE_TEST_DATABASE_URL` if it is a `mysql://` URL | a user that can create and drop databases (the generated applications use `root`) |
| SQLite | `sqlite/sqlitetest` | none: a file in the test's temporary directory | nothing; these tests always run |

```go
func TestNoteRepository(t *testing.T) {
	t.Parallel()
	db := postgrestest.NewMigrated(t, migrations.Migrations())
	notes := persistence.NewNoteRepository(db)
	// ...
}
```

| Function | Returns |
| -------- | ------- |
| `New(t)` | A pool connected to a new, empty database |
| `NewMigrated(t, fsys)` | The same, with every migration in `fsys` applied |
| `Config(t)` | A `config.Database` for a new, empty database, for code that opens its own pool (for example `Configure`) |
| `NewWithConfig(t)` | Both the pool and its configuration |
| `NewRLS(t, sets...)` (PostgreSQL) | A database owned by a new migration role that applied the migrations, and pools as that role (`Migrator`), as a new `NOSUPERUSER NOBYPASSRLS NOREPLICATION` runtime role holding only data privileges (`Runtime`, `RuntimeConfig`, `RuntimeRole`) and as the test server's user (`Admin`); the database and both roles are dropped when the test ends. Generated repository, sign-in and bootstrap tests run as `Runtime`, so row-level security applies to them as in production. The test server's user must be able to create roles (a superuser, as in the generated Compose service and CI) |

- PostgreSQL and MySQL helpers create a database named `forge_test_<random>`
  on the test server and drop it when the test ends (PostgreSQL with
  `WITH (FORCE)`, which needs PostgreSQL 13 or later). The drop is registered
  immediately after the database is created, so it also happens when opening
  the pool fails. Parallel tests are isolated.
- The SQLite helper opens a new file with the production settings in
  `t.TempDir()`, which the test removes.
- The adapter-specific variables let one process test several databases;
  the framework CI sets `FORGE_TEST_POSTGRES_URL` and `FORGE_TEST_MYSQL_URL`.
  Generated applications use `FORGE_TEST_DATABASE_URL`.
- Without a server URL, PostgreSQL and MySQL tests are skipped. With
  `FORGE_TEST_REQUIRE_DATABASE=true` they fail instead; set this in CI so
  database tests cannot silently stop running. The generated and framework CI
  workflows do.
- `forge test` runs `go test` (default `./...`) with `.env.development` and
  `.env.local` loaded; the generated `.env.development` sets
  `FORGE_TEST_DATABASE_URL` to the Compose database server (for PostgreSQL,
  as the image's superuser `postgres`, which creates the per-test roles; for
  MySQL and MariaDB, as `root`). SQLite applications need no test URL.
- Never point a test URL at a server holding data you care about. Tests only
  drop the databases they created, but they create databases on that server
  with its credentials.
