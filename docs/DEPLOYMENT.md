# Deployment

Applications generated by `forge new` ship with a production `Dockerfile`, a
`.dockerignore`, and a `compose.yaml` for local development with the chosen
database (PostgreSQL, MySQL, MariaDB, or SQLite).
This document covers running them. Database details are in
[DATABASE.md](DATABASE.md).

## The generated image

- Multi-stage build on `golang:1.27.3-alpine` with BuildKit cache mounts for
  the module and build caches. Both base images are pinned by digest
  (`image:tag@sha256:...`, the same digests as Forge's own `Dockerfile`), so
  a moved tag cannot change what you build; the generated
  `.github/dependabot.yml` proposes new digests weekly. To move to another
  Go release, replace the whole `FROM` reference, digest included:
  `docker buildx imagetools inspect golang:1.27.4-alpine` prints the new
  index digest. The build stage runs on the builder's platform and
  cross-compiles (`TARGETOS`/`TARGETARCH`), so `--platform linux/arm64` (or
  `builder.platform` in `config/deploy.yml`) needs no emulator.
- `CGO_ENABLED=0`, `-trimpath`: a static binary with no local paths embedded.
  This holds for SQLite too: its driver is pure Go.
- Runtime image `gcr.io/distroless/static-debian12:nonroot` (pinned by
  digest): no shell, no package manager, runs as the `nonroot` user.
- SQL migrations are embedded in the binary, so the same image serves HTTP
  and migrates its database.
- Defaults baked into the image:

  ```dockerfile
  ENV FORGE_ENV=production \
      FORGE_HTTP_ADDR=0.0.0.0:8080 \
      FORGE_HTTP_TRANSPORT=trusted-proxy
  EXPOSE 8080
  USER nonroot:nonroot
  HEALTHCHECK --interval=10s --timeout=3s --start-period=5s --retries=3 \
    CMD ["/app/server", "healthcheck"]
  ENTRYPOINT ["/app/server"]
  CMD ["serve"]
  ```

- SQLite applications also get `/app/storage`, created in the build stage
  and owned by `nonroot`, and
  `FORGE_DATABASE_URL=sqlite:///app/storage/production.db` in the image
  environment. Mount a persistent volume at `/app/storage`.
- `.dockerignore` excludes `.git`, `.github`, `.env`, `.env.*` (including the
  committed `.env.development`), `bin`, `storage` (local SQLite files), and
  test/profile artefacts, keeping local settings, data, and secrets out of
  the build context.

BuildKit is required for cache mounts (default in current Docker releases).

## Build and run

```sh
docker build -t myapp .
docker run --rm -p 8080:8080 \
  -e FORGE_DATABASE_URL='postgres://myapp:...@db.internal:5432/myapp?sslmode=verify-full' \
  myapp
curl -i http://localhost:8080/health/ready
```

For MySQL or MariaDB use `mysql://myapp:...@db.internal:3306/myapp?tls=true`.
For SQLite, mount the storage volume instead:

```sh
docker run --rm -p 8080:8080 -v myapp-storage:/app/storage myapp
```

An application generated with a server database fails at startup if
`FORGE_DATABASE_URL` is unset or the database is unreachable. The container
starts in `production` with `trusted-proxy` transport; for a real deployment,
put it behind a TLS-terminating proxy (see below).

## Local development with Compose

```sh
docker compose up --build
```

The generated `compose.yaml` runs the same image in development mode:

| Service | Purpose |
| ------- | ------- |
| database server | PostgreSQL (`postgres:18-alpine`, service `postgres`, volume at `/var/lib/postgresql`, the path the PostgreSQL 18 image expects), MySQL (`mysql:8.4`, service `mysql`), or MariaDB (`mariadb:11.8`, service `mariadb`), with a named volume and a healthcheck. Published on `127.0.0.1:<port>`, where the port (20000-29999) is derived from the application name so it does not clash with a local server on its default port. Not present for SQLite. |
| `migrate` | Runs the application's `migrate` command once, after the database server is healthy. |
| `app` | Starts after `migrate` completed successfully (`service_completed_successfully`). Published on `127.0.0.1:8080`. `stop_grace_period: 35s`. `docker compose watch` rebuilds it on source changes. |

With SQLite, `migrate` and `app` share a `storage` volume mounted at
`/app/storage`, and the database file is
`/app/storage/development.db`.

`migrate` and `app` run with `FORGE_ENV=development`,
`FORGE_HTTP_TRANSPORT=plain`, and a `FORGE_DATABASE_URL` pointing at the
database service without TLS. All ports are published on the host loopback
only. The database passwords in `compose.yaml` and `.env.development` are
fixed development values. For MySQL and MariaDB, `.env.development` connects
the application as the application user and tests as `root`, because only
`root` may create the throwaway test databases.

For PostgreSQL, `docker/postgres/init.sql` runs once, as the image's
superuser, when the volume is empty, and creates two development-only roles
and the database ([Database roles](DATABASE.md#database-roles-postgresql)):

- `app_migrator`: owns the database and its schema and applies the
  migrations. Only the one-off `migrate` service receives its credential,
  `FORGE_MIGRATION_DATABASE_URL`.
- `app_runtime`: what `app` serves with (`FORGE_DATABASE_URL`): no superuser,
  no `BYPASSRLS`, no ownership, only data privileges, so the row-level
  security policies apply to it.

The health check probes over TCP, which the server opens only after
`init.sql` has finished. `.env.development` points `FORGE_DATABASE_URL` and
`FORGE_MIGRATION_DATABASE_URL` at the same two roles and
`FORGE_TEST_DATABASE_URL` at the superuser, which the tests use to create
their own databases and roles. A volume created before the roles existed
keeps its old users: run `docker compose down --volumes` once to recreate it.

Useful commands:

```sh
docker compose up -d postgres                 # database only, for forge dev (or mysql, mariadb)
docker compose run --rm migrate migrate status
docker compose run --rm migrate rollback
docker compose down --volumes                 # also deletes the database
```

Without Docker for the application, `forge dev` builds it into a temporary
directory and runs the binary directly (not via `go run`, which does not
forward signals). It loads `.env.development` and `.env.local`, which point at
the Compose database server (or, for SQLite, `storage/development.db` in the
project), and sets `FORGE_ENV=development` unless it is already
set. The default address is then `127.0.0.1:8080`. On Ctrl-C, `forge dev`
forwards the interrupt and waits up to 35 seconds for the application to shut
down.

## Transport: `trusted-proxy` vs `tls`

**`trusted-proxy`** (image default): a reverse proxy or load balancer
terminates TLS and forwards plain HTTP to the container. This is the same
model as Rails 8 `assume_ssl` behind kamal-proxy. Forge sends HSTS and accepts
the configuration in `production`.

Requirements:

- The application port must be reachable **only** through the proxy. Do not
  publish it to the internet or to untrusted networks. The proxy must redirect
  or reject plain HTTP from clients.
- `r.RemoteAddr` is the proxy's address. To give sign-in throttles, rate
  limits and audit the real client address, list the proxy's network in
  `FORGE_HTTP_TRUSTED_PROXIES` (see [Client addresses behind a
  proxy](#client-addresses-behind-a-proxy)). Forge never derives the scheme
  from `X-Forwarded-Proto`.

**`tls`**: Forge terminates TLS itself using Go's `crypto/tls` defaults.

```sh
docker run --rm -p 8443:8443 \
  -e FORGE_HTTP_ADDR=0.0.0.0:8443 \
  -e FORGE_HTTP_TRANSPORT=tls \
  -e FORGE_HTTP_TLS_CERT_FILE=/certs/tls.crt \
  -e FORGE_HTTP_TLS_KEY_FILE=/certs/tls.key \
  -e FORGE_DATABASE_URL="$DATABASE_URL" \
  -v "$PWD/certs:/certs:ro" \
  myapp
```

Certificates are read once at startup; rotating them requires a restart. The
files must be readable by the `nonroot` user. The `healthcheck` subcommand
switches to HTTPS in `tls` mode, so the Docker `HEALTHCHECK` keeps working.

**`plain`**: no TLS, no HSTS. Allowed in `development`, `test`, and
`staging`; rejected in `production`.

### Client addresses behind a proxy

Sign-in and password-reset throttles, `ratelimit.ByClientIP`, the anonymous
stream cap and audit source digests count the client address `web.ClientIP`
returns ([ADR 0037](adr/0037-trusted-proxies-and-client-ip.md)). By default
that is the TCP peer, so behind a proxy every client is the proxy and shares
one budget. List the proxies that set `X-Forwarded-For`:

```sh
docker run --rm -p 8080:8080 \
  -e FORGE_HTTP_TRUSTED_PROXIES=172.18.0.0/16,fd00:1::/64 \
  -e FORGE_DATABASE_URL="$DATABASE_URL" \
  myapp
```

- Only when the peer is inside a listed network is the header read, from the
  right, skipping listed addresses; the first unlisted address is the client.
  A client that reaches the application directly cannot choose its address.
- An empty, malformed or non-address entry on that walk falls back to the
  peer. `Forwarded` and `X-Real-IP` are never read.
- The value is validated at startup: malformed entries, `/0` and prefixes
  broader than IPv4 `/8` or IPv6 `/16` stop the process (bare addresses are
  unaffected). Empty (the default) trusts nobody.
- List only proxy networks, and keep the application port reachable only
  through them; anything inside a listed network can claim any client
  address.
- Your proxy must overwrite the header, or append the address it received
  the connection from (nginx `$proxy_add_x_forwarded_for`, most load
  balancers); forge-proxy overwrites.

`forge deploy` sets `FORGE_HTTP_TRUSTED_PROXIES` for the proxied role to the
subnets of the `forge` Docker network on each host. Override it in
`config/deploy.yml` (`env.clear`), for example to an empty string to trust
nobody. The network's subnet includes the Docker gateway (for example
`172.18.0.1`), so processes on the host reach the application from a trusted
address. On a Docker network without IPv6, IPv6 clients reach forge-proxy
through docker-proxy from the gateway address and share one bucket; enable
IPv6 on the `forge` network or set `"userland-proxy": false` in the Docker
daemon configuration. Check what a container received (the filter runs on the host, so no
other variable leaves it):

```sh
ssh deploy@HOST "docker inspect --format '{{range .Config.Env}}{{println .}}{{end}}' CONTAINER | grep '^FORGE_HTTP_TRUSTED_PROXIES='"
```

## Database

### TLS to the database

In `production`, Forge refuses to start unless the database URL requires
TLS:

| Database | Required | Notes |
| -------- | -------- | ----- |
| PostgreSQL | `sslmode=verify-full`, or `verify-ca` with `sslrootcert` | `require` is rejected: it encrypts but does not authenticate the server. `verify-full` checks the certificate chain and the host name; use it whenever the provider supports it. `verify-ca` checks the chain only, and without `sslrootcert` pgx would trust the system roots, so a certificate any public CA issued for any name would pass: it is refused unless the URL has `sslrootcert=/path/to/ca.pem` (mount the CA; pgx then trusts that file alone). |
| MySQL / MariaDB | `tls=true` | Verifies the server certificate against the system certificate pool. `skip-verify` and `preferred` do not verify and are rejected in production. Only the `tls` parameter is accepted, so a private CA cannot be configured through the URL. |
| SQLite | none | A local file; protect it with file permissions and the volume. |

`FORGE_DATABASE_ALLOW_PLAINTEXT=true` disables the PostgreSQL and MySQL
checks. Use it only when the database is reachable exclusively over a
trusted private network.

Provide `FORGE_DATABASE_URL` from the orchestrator's secret store at runtime,
never through the image. Forge keeps it in a `config.Secret`, which is
redacted in logs and formatted output.

### Database roles

On PostgreSQL, serve as a runtime role that is `NOSUPERUSER NOBYPASSRLS
NOCREATEROLE NOREPLICATION`, owns no table and holds only `SELECT, INSERT, UPDATE, DELETE`,
and migrate as a separate role that owns the schema. In `staging` and
`production` (every environment except `development` and `test`)
`postgres.Open`, so every application, refuses to start when the role `FORGE_DATABASE_URL`
logs in as, or acts as, is a superuser, has `BYPASSRLS`, `CREATEROLE` or
`REPLICATION`, is a member of a superuser, `BYPASSRLS` or `REPLICATION` role
or of `pg_execute_server_program`, `pg_write_server_files` or
`pg_read_server_files`, owns (or can `SET ROLE` to the owner of) a table
with row-level security or holds `TRUNCATE`, `REFERENCES` or `TRIGGER` on
one or any privilege on a partition of one that lacks its own, and when the
URL makes the
session act as another role than its login (`options=-c role=...`), with an
error that wraps `postgres.ErrRowSecurityBypass`. [Database
roles](DATABASE.md#database-roles-postgresql) has the SQL to provision both
roles once.

**With `forge deploy`.** The migrate step gets the schema owner's credential
through `migrate.env`, an overlay of the one-off container that no serving
container ever sees. Put the secret's name under it and the value in
`.forge/secrets`; the serving roles keep `FORGE_DATABASE_URL` alone:

```yaml
servers:
  web:
    hosts: [192.0.2.10, 192.0.2.11]
env:
  clear: {FORGE_ENV: production}
  secret: [FORGE_DATABASE_URL, FORGE_AUTH_MFA_KEY]        # every container
migrate:
  enabled: true
  cmd: ["migrate"]
  role: web
  env:
    secret: [FORGE_MIGRATION_DATABASE_URL]                # the migrate step only
```

```sh
# .forge/secrets: FORGE_MIGRATION_DATABASE_URL=$FORGE_MIGRATION_DATABASE_URL
export FORGE_DATABASE_URL="$RUNTIME_DATABASE_URL" \
       FORGE_MIGRATION_DATABASE_URL="$MIGRATION_DATABASE_URL"
forge deploy --dry-run     # shows the migrate env file upload; values stay hidden
forge deploy
```

`migrate.env` has the same `clear` and `secret` keys as the role `env`
blocks; secrets come from `.forge/secrets` like every other secret, and a
missing one stops the deploy before any remote command. The migrate
container's environment is the global `env`, plus the env of `migrate.role`,
plus `migrate.env`. A name in `migrate.env` may not also be in the global
`env` or in any `servers.*.env`, clear or secret: that is a configuration
error ("FORGE_MIGRATION_DATABASE_URL is in migrate.env and in env.secret:
remove it from env.secret, so only the migrate step receives it"), because
the containers of that block would receive it too. An explicit `env:` with no
value (`null`, `~`) is an error like an empty block. The merged environment
is written to its own file,
`~/.forge/SERVICE/env/migrate.step.env` (mode `0600`, `umask 077`, atomic
rename, content over stdin, as for the role files), on the first host of the
migrate role only, used by the `migrate` container alone, and deleted, with
its temporary `.tmp` copy, when the step ends: after success, a failed
migration, a failed or interrupted upload, and a cancelled deploy. If the
delete fails the deploy continues with a warning naming the file, and you
remove it by hand. A deploy that is killed outright (`kill -9`, the machine
losing power) cannot clean up, so the file stays until the next deploy that
uses `migrate.env`; if you remove `migrate.env` from the configuration
afterwards, delete `~/.forge/SERVICE/env/migrate.step.env` on the migrate host
by hand, because deploys without `migrate.env` never touch it. The
role env files, and so the serving containers, are written exactly as before.
Without a `migrate.env` block nothing changes: the container gets the env
file of `migrate.role`, which is the runtime role's, and the migration fails
closed on PostgreSQL when that role cannot run DDL. `migrate.env` with
`migrate.enabled: false` is an error.

Moving the credential out of `env` into `migrate.env` does not reach the
containers already deployed: the stopped ones kept for `forge deploy rollback`
were created from the old env file and still hold it, and rolling back to a
version deployed before the change starts one of them again. They age out as
later deploys push them past `retain` (`forge deploy prune` removes them then);
to drop them sooner, `docker rm` the stopped containers of those versions on
each host, and do not roll back past the change.

`forge app exec` still uses the role's env file, never `migrate.env`:
`forge app exec migrate status` runs as the runtime role. To roll a migration
back by hand, run the one-off container yourself with the credential from
your secret store (`docker run --rm ... rollback`, below).

### Migrations

Run migrations as a separate release step before rolling out a new version;
`serve` never applies them. Use the release image itself:

```sh
docker run --rm -e FORGE_DATABASE_URL="$DATABASE_URL" \
  -e FORGE_MIGRATION_DATABASE_URL="$MIGRATION_DATABASE_URL" myapp:1.4.0 migrate
```

`FORGE_MIGRATION_DATABASE_URL` belongs to this one-off step only; the
serving containers get `FORGE_DATABASE_URL` alone. For SQLite, mount the application's storage volume instead
(`-v myapp-storage:/app/storage`); the database URL is already in the image.

In Kubernetes, run the same command as a Job (or a pre-deploy hook) and
deploy only after it succeeds. The `migrate` command loads the full
configuration, so the production HTTP rules also apply; the image defaults
satisfy them.

- Several `migrate` runs at the same time are safe: a lock serializes them
  (a PostgreSQL advisory lock, a MySQL/MariaDB `GET_LOCK`, or, for SQLite, an
  operating-system lock on `<database>-migrate.lock` that works only on the
  same host), and each migration is applied once.
- On MySQL and MariaDB, DDL commits implicitly: a failed migration can leave
  part of its statements applied. Keep migrations small.
- The migrator refuses to run if an applied migration was modified or if the
  database has a migration the image does not know (for example, an older
  release deploying over a newer schema).
- Migrations run without a statement timeout. Bound lock waits in
  migrations that touch busy tables (for example `SET LOCAL lock_timeout` on
  PostgreSQL).
- Keep schema changes compatible with the version still running during a
  rolling deploy (expand, then contract).

`<app> migrate status` lists applied, pending, modified, and unknown
migrations. `<app> rollback [-steps N]` reverts the most recent ones. See
[DATABASE.md](DATABASE.md#migrations) for file conventions, fail-closed
rules, and zero-downtime guidance.

### Connection pool sizing

Each process opens at most `FORGE_DATABASE_MAX_CONNS` connections (default
`10`). Keep `replicas x FORGE_DATABASE_MAX_CONNS`, plus migration jobs and
other clients, below the server's `max_connections`, or put a connection
pooler in front of the server.

### SQLite in production

- Run a single application instance on a single host, with the database on
  a local persistent volume mounted at `/app/storage`. SQLite's locks, and
  Forge's migration lock, are not reliable on network file systems.
- The database file is created `0600` and its directory `0750`, owned by the
  `nonroot` user in the image.
- There is no server-side statement timeout: bound request work with
  contexts (the driver interrupts a statement when its context ends).
- Back up the file with SQLite's online backup mechanisms (for example
  `VACUUM INTO`), not by copying a file that is being written.

## Health checks

| Endpoint            | Meaning |
| ------------------- | ------- |
| `GET /health/live`  | Process is serving HTTP. Always `200`. |
| `GET /health/ready` | All registered readiness checks pass (`200`), else `503`. |
| `GET /health`       | Alias of `/health/ready`. |

Generated applications register a `database` readiness check that pings the
database through the pool, so `/health/ready` returns `503` while the
database is unreachable. The response lists check names and pass/fail only,
never error details. Each check has a 2-second timeout
(`health.DefaultCheckTimeout`), so a hung database or a saturated pool reports
unready instead of blocking the probe; checks run one after another.

The Docker `HEALTHCHECK` runs `/app/server healthcheck`, which loads the same
configuration as the server and requests `/health/live` (not readiness) from
`127.0.0.1` on the port in `FORGE_HTTP_ADDR` (2-second timeout). The listen
address must therefore include loopback (`0.0.0.0:PORT` or
`127.0.0.1:PORT`); binding to a single non-loopback IP makes the check fail.

Kubernetes ignores the Docker `HEALTHCHECK`. Equivalent probes:

```yaml
livenessProbe:
  httpGet:
    path: /health/live
    port: 8080
  periodSeconds: 10
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
  periodSeconds: 5
  timeoutSeconds: 3
```

Do not point the liveness probe at `/health/ready`: a database outage would
then restart every replica.

## Graceful shutdown

On `SIGTERM` or `SIGINT` the server stops accepting connections and waits for
in-flight requests to finish. Then the shutdown hooks registered with
`App.OnShutdown` run in reverse order; generated applications register
`database.Shutdown`, which closes the database pool.

The drain and the hooks share one budget, `FORGE_HTTP_SHUTDOWN_TIMEOUT`
(default `30s`), counted from the signal:

- If requests are still running when the drain deadline passes, the server
  closes their connections, which cancels their request contexts so they
  stop and release resources such as database connections. Shutdown then
  reports an error.
- The hooks' context expires at the same point. `database.Shutdown` stops
  waiting for connections still held by requests when it does, instead of
  blocking exit.

Give the orchestrator a grace period slightly longer than
`FORGE_HTTP_SHUTDOWN_TIMEOUT` so it does not send `SIGKILL` first:

- Docker Compose: `stop_grace_period`. The generated file sets `35s`, which
  covers the whole default shutdown.
- `docker stop`: `--time`/`-t`.
- Kubernetes: `terminationGracePeriodSeconds`.

Listeners close immediately on `SIGTERM`; readiness does not flip to `503`
first. If your load balancer needs time to deregister the pod, add a
`preStop` delay in the orchestrator.

## forge deploy

`forge deploy` puts the image on your own servers over SSH, Kamal-style, with
zero-downtime switches through **forge-proxy**
([ADR 0030](adr/0030-forge-deploy.md)). Hosts need only an SSH server and
Docker; your machine needs `ssh` and, to build, the `docker` CLI.

### From a fresh VPS

1. **Prepare each host** (Debian/Ubuntu shown) as root:

   Install Docker Engine from Docker's signed apt repository, following
   Docker's guide for [Ubuntu](https://docs.docker.com/engine/install/ubuntu/)
   or [Debian](https://docs.docker.com/engine/install/debian/) (check it for
   changes), rather than piping a script into a shell:

   ```sh
   apt-get update && apt-get install -y ca-certificates curl
   install -m 0755 -d /etc/apt/keyrings
   . /etc/os-release   # ID is ubuntu or debian
   curl -fsSL "https://download.docker.com/linux/$ID/gpg" -o /etc/apt/keyrings/docker.asc
   chmod a+r /etc/apt/keyrings/docker.asc
   echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/$ID ${UBUNTU_CODENAME:-$VERSION_CODENAME} stable" \
     > /etc/apt/sources.list.d/docker.list
   apt-get update && apt-get install -y docker-ce docker-ce-cli containerd.io
   ```

   Then create the deploy user and open the firewall:

   ```sh
   adduser --disabled-password --gecos '' deploy
   usermod -aG docker deploy          # docker access is root-equivalent
   install -d -m 700 -o deploy -g deploy /home/deploy/.ssh
   cp ~/.ssh/authorized_keys /home/deploy/.ssh/ && chown deploy: /home/deploy/.ssh/authorized_keys
   ufw allow 22,80,443/tcp && ufw enable
   ```

   Ports Docker publishes bypass `ufw`. Forge publishes only the proxy's 80
   and 443; application containers publish nothing and accessories bind
   `127.0.0.1` unless you give another address.

   Connect once with `ssh deploy@HOST` so its host key is in your
   `known_hosts`: Forge never disables host key checking. Use an SSH agent
   for passphrase-protected keys (commands run with `BatchMode=yes`).

2. **Get forge-proxy.** Use a released image, signed by this repository's
   release workflow: verify it, then note the digest
   ([SUPPLY_CHAIN.md](SUPPLY_CHAIN.md)):

   ```sh
   cosign verify ghcr.io/rocketinsidecorp/forge-proxy:v0.1.0 \
     --certificate-identity-regexp '^https://github\.com/rocketinsidecorp/forge-go/\.github/workflows/release\.yml@refs/tags/v' \
     --certificate-oidc-issuer https://token.actions.githubusercontent.com
   docker buildx imagetools inspect ghcr.io/rocketinsidecorp/forge-proxy:v0.1.0 --format '{{ .Manifest.Digest }}'
   ```

   Or build and push it once from a Forge checkout:

   ```sh
   docker build -f cmd/forge-proxy/Dockerfile -t registry.example.com/acme/forge-proxy:0.1.0 .
   docker push registry.example.com/acme/forge-proxy:0.1.0
   docker buildx imagetools inspect registry.example.com/acme/forge-proxy:0.1.0   # Digest: sha256:...
   ```

3. **Configure** the application:

   ```sh
   forge deploy init        # config/deploy.yml, .forge/secrets (0600), ignore entries
   $EDITOR config/deploy.yml .forge/secrets
   ```

4. **Point DNS** for `proxy.hosts` at the web hosts (needed for `ssl: true`).

5. **Deploy:**

   ```sh
   export REGISTRY_PASSWORD=... FORGE_DATABASE_URL=...   # referenced as $VAR in .forge/secrets
   forge deploy setup --dry-run   # review every remote command
   forge deploy setup             # docker check, network, proxy, accessories
   forge deploy                   # build, push, migrate, switch
   forge deploy details
   forge logs -f
   ```

### config/deploy.yml

```yaml
service: shop                                # container names, ~/.forge/shop
image: registry.example.com/acme/shop        # no tag: the version is the tag
registry:
  server: registry.example.com
  username: acme
  password: REGISTRY_PASSWORD                # a secret NAME, not the password
servers:
  web:                                       # routed through forge-proxy
    hosts: [192.0.2.10, 192.0.2.11]
  jobs:
    hosts: [192.0.2.11]
    cmd: ["jobs"]                            # arguments to the image entrypoint
    env: {clear: {JOBS_CONCURRENCY: "8"}}
env:
  clear: {FORGE_ENV: production}
  secret: [FORGE_DATABASE_URL, FORGE_AUTH_MFA_KEY]
volumes: []                                  # e.g. shop-storage:/app/storage (SQLite)
proxy:
  image: registry.example.com/acme/forge-proxy@sha256:...
  hosts: [shop.example.com]
  ssl: true                                  # Let's Encrypt (accepts its terms)
  acme_email: ops@example.com
  app_port: 8080
  healthcheck: {path: /health/ready, interval: 1s, timeout: 2s, healthy_count: 3, deploy_timeout: 60s}
  drain_timeout: 30s
  response_timeout: 30s
  max_body_bytes: 67108864
migrate:
  enabled: true
  cmd: ["migrate"]
  role: web                                  # whose env file the migrate container starts from
  env:                                       # added for the migrate container only
    secret: [FORGE_MIGRATION_DATABASE_URL]   # the schema owner; never in env: or servers.*.env
accessories:
  db:
    image: postgres:18-alpine
    host: 192.0.2.20
    port: 5432                               # published on 127.0.0.1 only
    volumes: ["shop-postgres:/var/lib/postgresql"]
    env: {secret: [POSTGRES_PASSWORD]}
builder: {context: ., dockerfile: Dockerfile, platform: linux/amd64, args: {}}
retain: 5                                    # versions kept per role (2 to 100; the running one counts)
stop_timeout: 35s                            # > FORGE_HTTP_SHUTDOWN_TIMEOUT
boot_timeout: 60s                            # readiness wait for non-proxied roles
hooks: .forge/hooks
parallelism: 4                               # hosts handled at once
ssh: {user: deploy, port: 22, proxy_jump: bastion.example.com}
```

Decoding is strict: unknown or duplicate keys, a second YAML document,
durations that are not strings (`30s`), a tag in `image`, a password in
`registry.password`, host names starting with `-` (also `ssh.proxy_jump` and
`registry.server`, which `ssh -J` and `docker login` would read as options),
`retain` below 2, and more than one proxied role are errors. `retain` counts
the running version, so `retain: 1` would prune the previous version after
every deploy and leave nothing to roll back to; it is refused (the default
is 5). `migrate.env` is validated like the role `env` blocks and must not be
empty. `servers.web` is proxied by default; set `proxy: true` or
`false` on a role to change that. An accessory `port` of `5432` or
`6543:5432` binds `127.0.0.1`; write `IP:HOST_PORT:CONTAINER_PORT` to choose
another address deliberately.

YAML nesting is bounded by the decoder: Forge-Go relies on yaml.v3's own
maximum depth (10,000 levels), while Forge-Rust refuses nesting deeper than
100 levels (and files over 1 MiB) with a line-numbered error. No real
`deploy.yml` comes near either limit.

### Secrets

`.forge/secrets` contains `NAME=value` or `NAME=$VARIABLE` (`${VARIABLE}`)
lines. Passthrough copies a variable from your environment, so values can
come from a password manager or the CI secret store; an unset variable is an
error. Quotes are removed and nothing inside them is expanded. There is no
command substitution. The file must be mode `0600`. Values are sent to each
host on stdin and written to `~/.forge/SERVICE/env/ROLE.env` (mode `0600`,
`umask 077`, atomic rename), which containers read with `--env-file`. They
never appear in command lines, dry runs or progress output.

Redaction of streamed output is best effort. `forge logs` and non-interactive
`forge app exec` replace the exact values from `.forge/secrets` (4 characters
or longer) line by line, but **output is otherwise not redacted**: an encoded,
partial or derived value (URL-encoded, base64, a decrypted credential, a
token the application created) passes through, and interactive sessions
(`forge app exec --interactive`, `forge app shell`) and `docker logs` on the
host are not filtered at all. Applications must not print secrets; treat
streamed output as sensitive.

### Commands

Every command reads `config/deploy.yml` (`--config`/`-c`) and
`.forge/secrets` (`--secrets`), and accepts `--dry-run`: mutating remote and
local commands are printed (`$`), stdin is described (`<`) but not shown, and
read-only queries (`?`, such as `docker ps`) still run, so the plan names the
exact containers that would be stopped or pruned.

| Command | Effect |
| ------- | ------ |
| `forge deploy init [--service NAME]` | Write a commented `config/deploy.yml` and `.forge/secrets`; add `.forge/secrets` to `.gitignore` and `.forge` to `.dockerignore`. Never overwrites. |
| `forge deploy setup [--json]` | Check Docker, create `~/.forge/SERVICE` (0700) and the `forge` network, log in to the registry, start forge-proxy (ports 80 and 443) and accessories. Idempotent. Warns if the proxy image is not pinned by digest. |
| `forge deploy [--version V] [--skip-build] [--json]` | Deploy; the version defaults to the abbreviated commit of a clean working tree. |
| `forge deploy rollback VERSION [--json]` | Restart the retained containers of VERSION on every host through the same health-gated switch. Migrations are not reverted. |
| `forge deploy prune [--json]` | Remove stopped containers beyond `retain` per role, and images no remaining container uses. Never touches running containers. |
| `forge deploy details [--json]` | Containers and versions per host and role, proxy routing and maintenance, lock holder, last deploys. |
| `forge deploy lock status\|acquire\|release [--message M] [--force]` | Inspect or hold the lock (for maintenance windows). `release` removes only a lock this performer holds, and only while its record is unchanged; it refuses one held by someone else (or without a record) unless `--force`. |
| `forge deploy maintenance on\|off` | Serve forge-proxy's static 503 page (with `Retry-After`) instead of the application. |
| `forge logs [-f] [--role R] [--host H] [--since 1h] [--grep REGEX] [--lines N]` | Stream `docker logs` of the current role container from every matching host, each line prefixed `host\|`. `--grep` filters locally. Ctrl-C stops the remote `docker logs` processes too. |
| `forge app exec [--role R] [--host H] [--interactive] [--reuse] CMD...` | Run CMD on one host (the first of the role unless `--host`): by default in a one-off container of the image the role currently runs, with its env file, where CMD goes to the image entrypoint (`forge app exec migrate status`); `--reuse` runs inside the running container (`forge app exec --reuse /app/server healthcheck`). |
| `forge app shell [--image IMAGE]` | Interactive shell over `ssh -t`. Distroless images have no shell: `--image busybox:1.37` starts a sidecar sharing the container's network and process namespaces, without the application's environment. |

Exit codes: `0` success, `1` failure (invalid configuration, SSH or remote
command failure), `2` invalid arguments (an unknown flag or subcommand, a
missing or extra argument; nothing ran), `3` the lock is held (nothing changed), `4` a new container
failed its health check and every host serves its previous version, `5` the
migration failed before any switch, `6` a hook failed, `7` a failure could not
be fully reverted (run `forge deploy details`). With `--json`, the report is
printed on stdout also on failure, with `ok`, `error` and `exit_code`.

### How a deploy switches without downtime

1. Take the lock on every host (`mkdir ~/.forge/SERVICE/lock`, atomic; the
   holder, time and message are recorded). It is released at the end, also
   on failure, but only if its record is still the deploy's own: a lock
   somebody else took after a `--force` release is left in place with a
   warning (or a note that it was already released). The record is written
   to a temporary file (created with `set -C`, so a leftover name is never
   truncated) and claimed with `ln`, which fails if the lock already has one,
   so a record is never seen half written. Only a successful `ln` wins: the
   hard link is created atomically by `link(2)`, which fails with `EEXIST`
   when `lock/info` exists, and `info` is removed only by a release whose
   record matches or by `--force`. A lock directory without a record file
   (the process was killed between the `mkdir` and the claim) older than a
   minute is taken over in place by the next deploy or `lock acquire`
   without `--force`, with a warning printed after the claim has succeeded;
   nothing is removed, so two deploys cannot both win it (a test forces the
   interleaving: a second acquire completes between the first one's
   staleness check and its claim). A younger one reports holder `unknown`,
   and so does a lock with an empty record file (left by earlier versions);
   `lock release --force` clears either at once. The release compares the
   record and then removes the directory as separate shell steps, so it is
   race-aware, not transactional: removing a foreign lock takes a force
   release and a new acquire inside the same few milliseconds.

   The lock needs `~/.forge` on every host to be on a file system that
   supports hard links (any local Linux file system does). Without them
   `ln` fails and every acquire reports the lock as held, which fails
   closed: nothing deploys. The acquire prints `ln`'s own error on stderr
   in that case, and an empty lock directory may be left behind (clear it
   with `lock release --force`). On NFS, `link(2)` is atomic on a correctly
   configured server, but client caching can delay what other hosts see;
   keep `~/.forge` on local disk.
2. Run `pre-build`, build and push the image (unless `--skip-build`), run
   `pre-deploy`.
3. On all hosts in parallel (at most `parallelism`): registry login, `docker
   pull`, write the env files.
4. Run `migrate` once, in a one-off container on the first host of the
   migrate role. A failure stops here: nothing was started or switched.
   The container gets the environment of the migrate role overlaid with
   `migrate.env` (the schema owner's `FORGE_MIGRATION_DATABASE_URL`, see
   [Database roles](#database-roles)), written for this step only and deleted
   afterwards; without `migrate.env` it gets that role's env file.
5. On every host, for each role (the proxied one first), start the new
   container on the `forge` network with no published ports. For the
   proxied role, `forge-proxy deploy` probes `healthcheck.path` until it
   passes `healthy_count` times in a row, then switches traffic atomically
   and waits up to `drain_timeout` for requests still running on the old
   container. Other roles wait until Docker reports the container healthy
   (or running for three checks) within `boot_timeout`.
6. If any host fails, every switched host is routed back to its previous
   container, which is still running, and the new containers are stopped
   and removed. A role deployed for the first time keeps its healthy new
   container, since there is nothing to go back to.
7. When all hosts succeeded: stop the previous containers with `docker stop
   -t stop_timeout` (SIGTERM, then the application's graceful shutdown),
   prune beyond `retain`, append a JSON line (time, performer, version,
   containers) to `~/.forge/SERVICE/deploys.log`, run `post-deploy`.

Interrupting a deploy (Ctrl-C) during step 5 does not revert: forge-proxy
finishes a switch it has started, so hosts may run different versions. The
command exits `7`; check `forge deploy details` and deploy or roll back
again.

Keep migrations compatible with the version still serving until the switch
(expand, then contract), as described in [DATABASE.md](DATABASE.md).

### Hooks

Executables in `.forge/hooks` (`hooks:` in the config) run locally from the
project directory: `pre-build` (before the build), `pre-deploy` (before any
host is touched; also on rollback) and `post-deploy` (after success). They
receive `FORGE_COMMAND` (`deploy` or `rollback`), `FORGE_SERVICE`,
`FORGE_VERSION`, `FORGE_IMAGE`, `FORGE_HOSTS` and `FORGE_ROLES` (comma
separated), `FORGE_PERFORMER` and, in `post-deploy`, `FORGE_RUNTIME` (seconds),
plus your environment. A non-zero exit aborts with exit code `6`; a hook file
that is not executable is an error, not skipped.

### forge-proxy

The proxy container (`forge-proxy`) listens on 8080 and 8443 inside, published
as 80 and 443, runs as `nonroot` and keeps its routing state and ACME
certificates in the `forge-proxy-data` volume, so it resumes routing after a
restart. It:

- routes by `Host` (one service per host name; a service without hosts gets
  unmatched requests) and answers unknown hosts with `404`;
- with `ssl: true`, obtains certificates from Let's Encrypt for exactly the
  configured hosts (TLS 1.2+) and redirects plain HTTP with `308`. The ACME
  cache directory is kept `0700` (an existing one is restricted at start, a
  symbolic link is refused), and its files are synced to disk when written;
- is the internet edge: it drops any `Forwarded`, `X-Forwarded-*` and
  `X-Real-IP` headers the client sent, sets `X-Forwarded-For` to the
  connecting address only (replacing, never appending), `X-Forwarded-Proto`
  and `X-Forwarded-Host`, and keeps the original `Host`. The proxied role
  trusts that `X-Forwarded-For` because `forge deploy` sets
  `FORGE_HTTP_TRUSTED_PROXIES` to the `forge` network (see [Client addresses
  behind a proxy](#client-addresses-behind-a-proxy)); `X-Forwarded-Proto` is
  not interpreted. Running forge-proxy behind another load balancer is not
  supported: client addresses would be the load balancer's;
- rejects bodies over `max_body_bytes` with `413`; reads bodies up to 1 MiB
  completely, with or without `Content-Length`, before contacting the
  application, and answers `408` if one does not arrive within 30 s; streams
  larger bodies, answering `408` when no data arrives for 30 s; gives the
  application `response_timeout` to send response headers;
- disconnects clients that hold connections without using them, after
  `-idle-timeout` (120 s by default): a keep-alive connection waiting for its
  next request, a response the client stops reading (writes go out in
  4 KiB pieces, each of which must reach the client within the timeout),
  and an upgraded (WebSocket) connection with no data in either direction.
  The application connection and the in-flight count are released with it,
  so a stalled client cannot hold a drain open. WebSocket applications
  should ping more often than that. There is no total time limit per
  connection: like nginx's `send_timeout`, a client that reads or sends a
  little in every interval keeps its connection, bounded only by the
  container's open-file limit and by `-max-connections` (forge-proxy has no
  per-address limit);
- bounds what one client can make it hold: request lines and headers up to
  `-max-header-bytes` (64 KiB by default, `4096` to `1048576`; larger ones get
  `431`), and at most `-max-connections` open connections on each listener
  (10,000 by default, like Forge-Rust's forge-proxy; further clients wait in
  the kernel's listen backlog until one closes). Both are flags of
  `forge-proxy run` with those defaults, which every `forge deploy setup`
  uses; `config/deploy.yml` does not expose them;
- writes JSON access logs (service, host, method, path without query,
  status, bytes, duration, client IP, target) to `docker logs forge-proxy`;
- is controlled only through a Unix socket inside the container (directory
  `0700`, restricted at start if it already exists; socket `0600`):
  `docker exec forge-proxy /usr/local/bin/forge-proxy status`.

To upgrade the proxy, change `proxy.image`, then on each host run
`docker rm -f forge-proxy` and `forge deploy setup`: requests fail for the
few seconds the proxy restarts. Certificates from static files are not
supported yet.
