# Deployment

Applications generated by `forge new` ship with a production `Dockerfile`, a
`.dockerignore`, and a `compose.yaml` for local development with the chosen
database (PostgreSQL, MySQL, MariaDB, or SQLite).
This document covers running them. Database details are in
[DATABASE.md](DATABASE.md).

## The generated image

- Multi-stage build on `golang:${GO_VERSION}-alpine` (`GO_VERSION` build
  argument, default `1.27`) with BuildKit cache mounts for the module and
  build caches.
- `CGO_ENABLED=0`, `-trimpath`: a static binary with no local paths embedded.
  This holds for SQLite too: its driver is pure Go.
- Runtime image `gcr.io/distroless/static-debian12:nonroot`: no shell, no
  package manager, runs as the `nonroot` user.
- SQL migrations are embedded in the binary, so the same image serves HTTP
  and migrates its database.
- Defaults baked into the image:

  ```dockerfile
  ENV FORGE_ENV=production \
      FORGE_HTTP_ADDR=0.0.0.0:8080 \
      FORGE_HTTP_TRANSPORT=trusted-proxy
  EXPOSE 8080
  USER nonroot:nonroot
  HEALTHCHECK --interval=10s --timeout=3s --start-period=5s --retries=3 \
    CMD ["/app/server", "healthcheck"]
  ENTRYPOINT ["/app/server"]
  CMD ["serve"]
  ```

- SQLite applications also get `/app/storage`, created in the build stage
  and owned by `nonroot`, and
  `FORGE_DATABASE_URL=sqlite:///app/storage/production.db` in the image
  environment. Mount a persistent volume at `/app/storage`.
- `.dockerignore` excludes `.git`, `.github`, `.env`, `.env.*` (including the
  committed `.env.development`), `bin`, `storage` (local SQLite files), and
  test/profile artefacts, keeping local settings, data, and secrets out of
  the build context.

BuildKit is required for cache mounts (default in current Docker releases).

## Build and run

```sh
docker build -t myapp .
docker run --rm -p 8080:8080 \
  -e FORGE_DATABASE_URL='postgres://myapp:...@db.internal:5432/myapp?sslmode=verify-full' \
  myapp
curl -i http://localhost:8080/health/ready
```

For MySQL or MariaDB use `mysql://myapp:...@db.internal:3306/myapp?tls=true`.
For SQLite, mount the storage volume instead:

```sh
docker run --rm -p 8080:8080 -v myapp-storage:/app/storage myapp
```

An application generated with a server database fails at startup if
`FORGE_DATABASE_URL` is unset or the database is unreachable. The container
starts in `production` with `trusted-proxy` transport; for a real deployment,
put it behind a TLS-terminating proxy (see below).

## Local development with Compose

```sh
docker compose up --build
```

The generated `compose.yaml` runs the same image in development mode:

| Service | Purpose |
| ------- | ------- |
| database server | PostgreSQL (`postgres:18-alpine`, service `postgres`, volume at `/var/lib/postgresql`, the path the PostgreSQL 18 image expects), MySQL (`mysql:8.4`, service `mysql`), or MariaDB (`mariadb:11.8`, service `mariadb`), with a named volume and a healthcheck. Published on `127.0.0.1:<port>`, where the port (20000-29999) is derived from the application name so it does not clash with a local server on its default port. Not present for SQLite. |
| `migrate` | Runs the application's `migrate` command once, after the database server is healthy. |
| `app` | Starts after `migrate` completed successfully (`service_completed_successfully`). Published on `127.0.0.1:8080`. `stop_grace_period: 35s`. `docker compose watch` rebuilds it on source changes. |

With SQLite, `migrate` and `app` share a `storage` volume mounted at
`/app/storage`, and the database file is
`/app/storage/development.db`.

`migrate` and `app` run with `FORGE_ENV=development`,
`FORGE_HTTP_TRANSPORT=plain`, and a `FORGE_DATABASE_URL` pointing at the
database service without TLS. All ports are published on the host loopback
only. The database passwords in `compose.yaml` and `.env.development` are
fixed development values. For MySQL and MariaDB, `.env.development` connects
the application as the application user and tests as `root`, because only
`root` may create the throwaway test databases.

Useful commands:

```sh
docker compose up -d postgres                 # database only, for forge dev (or mysql, mariadb)
docker compose run --rm migrate migrate status
docker compose run --rm migrate rollback
docker compose down --volumes                 # also deletes the database
```

Without Docker for the application, `forge dev` builds it into a temporary
directory and runs the binary directly (not via `go run`, which does not
forward signals). It loads `.env.development` and `.env.local`, which point at
the Compose database server (or, for SQLite, `storage/development.db` in the
project), and sets `FORGE_ENV=development` unless it is already
set. The default address is then `127.0.0.1:8080`. On Ctrl-C, `forge dev`
forwards the interrupt and waits up to 35 seconds for the application to shut
down.

All variables are optional; defaults apply when unset. Invalid values stop the
process at startup, and error messages name the variable without echoing its
value. Durations use Go syntax (`500ms`, `15s`, `1m`).

| ----------------------------------- | ---------------- | ----- |
| `FORGE_ENV`                         | `development`    | `development`, `test`, `staging`, `production` |
| `FORGE_HTTP_ADDR`                   | `127.0.0.1:8080` | Listen address. Use `0.0.0.0:PORT` in containers. |
| `FORGE_HTTP_TRANSPORT`              | `plain`          | `plain`, `tls`, `trusted-proxy`. `production` rejects `plain`. |
| `FORGE_HTTP_TLS_CERT_FILE`          | (empty)          | Required when transport is `tls` |

Test-only variables, read by the adapters' test packages:

| Variable                      | Notes |
| ----------------------------- | ----- |
| `FORGE_TEST_POSTGRES_URL`     | PostgreSQL server on which tests create and drop their own databases |
| `FORGE_TEST_MYSQL_URL`        | MySQL or MariaDB server, likewise; the user must be able to create and drop databases |
| `FORGE_TEST_DATABASE_URL`     | Used when the adapter-specific variable is unset and its scheme matches the adapter; generated applications set this one |
| `FORGE_TEST_REQUIRE_DATABASE` | `true` makes a missing test server a failure instead of a skip |

SQLite tests use temporary files and need none of these.

Run `forge doctor` with the same environment to validate a configuration
before deploying; it prints the database URL without the password and
without query parameters other than `sslmode`. Note
that `forge doctor` also reads `.env.development` and `.env.local` from the
current directory.

## Transport: `trusted-proxy` vs `tls`

**`trusted-proxy`** (image default): a reverse proxy or load balancer
terminates TLS and forwards plain HTTP to the container. This is the same
model as Rails 8 `assume_ssl` behind kamal-proxy. Forge sends HSTS and accepts
the configuration in `production`.

Requirements:

- The application port must be reachable **only** through the proxy. Do not
  publish it to the internet or to untrusted networks. The proxy must redirect
  or reject plain HTTP from clients.
- Forge does not derive client IP or scheme from `X-Forwarded-For` or
  `X-Forwarded-Proto`; `r.RemoteAddr` is the proxy's address.

**`tls`**: Forge terminates TLS itself using Go's `crypto/tls` defaults.

```sh
docker run --rm -p 8443:8443 \
  -e FORGE_HTTP_ADDR=0.0.0.0:8443 \
  -e FORGE_HTTP_TRANSPORT=tls \
  -e FORGE_HTTP_TLS_CERT_FILE=/certs/tls.crt \
  -e FORGE_HTTP_TLS_KEY_FILE=/certs/tls.key \
  -e FORGE_DATABASE_URL="$DATABASE_URL" \
  -v "$PWD/certs:/certs:ro" \
  myapp
```

Certificates are read once at startup; rotating them requires a restart. The
files must be readable by the `nonroot` user. The `healthcheck` subcommand
switches to HTTPS in `tls` mode, so the Docker `HEALTHCHECK` keeps working.

**`plain`**: no TLS, no HSTS. Allowed in `development`, `test`, and
`staging`; rejected in `production`.

## Database

### TLS to the database

In `production`, Forge refuses to start unless the database URL requires
TLS:

| Database | Required | Notes |
| -------- | -------- | ----- |
| PostgreSQL | `sslmode=require`, `verify-ca`, or `verify-full` | `require` encrypts but does not authenticate the server; `verify-ca` checks the certificate chain; `verify-full` also checks the host name; use it whenever the provider supports it. For a CA that is not publicly trusted, mount it and add `sslrootcert=/path/to/ca.pem`. |
| MySQL / MariaDB | `tls=true` | Verifies the server certificate against the system certificate pool. `skip-verify` and `preferred` do not verify and are rejected in production. Only the `tls` parameter is accepted, so a private CA cannot be configured through the URL. |
| SQLite | none | A local file; protect it with file permissions and the volume. |

`FORGE_DATABASE_ALLOW_PLAINTEXT=true` disables the PostgreSQL and MySQL
checks. Use it only when the database is reachable exclusively over a
trusted private network.

Provide `FORGE_DATABASE_URL` from the orchestrator's secret store at runtime,
never through the image. Forge keeps it in a `config.Secret`, which is
redacted in logs and formatted output.

### Migrations

Run migrations as a separate release step before rolling out a new version;
`serve` never applies them. Use the release image itself:

```sh
docker run --rm -e FORGE_DATABASE_URL="$DATABASE_URL" myapp:1.4.0 migrate
```

For SQLite, mount the application's storage volume instead
(`-v myapp-storage:/app/storage`); the database URL is already in the image.

In Kubernetes, run the same command as a Job (or a pre-deploy hook) and
deploy only after it succeeds. The `migrate` command loads the full
configuration, so the production HTTP rules also apply; the image defaults
satisfy them.

- Several `migrate` runs at the same time are safe: a lock serializes them
  (a PostgreSQL advisory lock, a MySQL/MariaDB `GET_LOCK`, or, for SQLite, an
  operating-system lock on `<database>-migrate.lock` that works only on the
  same host), and each migration is applied once.
- On MySQL and MariaDB, DDL commits implicitly: a failed migration can leave
  part of its statements applied. Keep migrations small.
- The migrator refuses to run if an applied migration was modified or if the
  database has a migration the image does not know (for example, an older
  release deploying over a newer schema).
- Migrations run without a statement timeout. Bound lock waits in
  migrations that touch busy tables (for example `SET LOCAL lock_timeout` on
  PostgreSQL).
- Keep schema changes compatible with the version still running during a
  rolling deploy (expand, then contract).

`<app> migrate status` lists applied, pending, modified, and unknown
migrations. `<app> rollback [-steps N]` reverts the most recent ones. See
[DATABASE.md](DATABASE.md#migrations) for file conventions, fail-closed
rules, and zero-downtime guidance.

### Connection pool sizing

Each process opens at most `FORGE_DATABASE_MAX_CONNS` connections (default
`10`). Keep `replicas x FORGE_DATABASE_MAX_CONNS`, plus migration jobs and
other clients, below the server's `max_connections`, or put a connection
pooler in front of the server.

### SQLite in production

- Run a single application instance on a single host, with the database on
  a local persistent volume mounted at `/app/storage`. SQLite's locks, and
  Forge's migration lock, are not reliable on network file systems.
- The database file is created `0600` and its directory `0750`, owned by the
  `nonroot` user in the image.
- There is no server-side statement timeout: bound request work with
  contexts (the driver interrupts a statement when its context ends).
- Back up the file with SQLite's online backup mechanisms (for example
  `VACUUM INTO`), not by copying a file that is being written.

## Observability

Telemetry is on with nothing exported. To scrape metrics from a container,
set `FORGE_TELEMETRY_METRICS_ADDR=0.0.0.0:9464` with
`FORGE_TELEMETRY_METRICS_PUBLIC=true` and let Prometheus reach that port on
the internal network only; to ship traces, point
`FORGE_TELEMETRY_OTLP_ENDPOINT` at an OpenTelemetry Collector. Details,
collector and Prometheus configuration: [OBSERVABILITY.md](OBSERVABILITY.md).

## Health checks

| Endpoint            | Meaning |
| ------------------- | ------- |
| `GET /health/live`  | Process is serving HTTP. Always `200`. |
| `GET /health/ready` | All registered readiness checks pass (`200`), else `503`. |
| `GET /health`       | Alias of `/health/ready`. |

Generated applications register a `database` readiness check that pings the
database through the pool, so `/health/ready` returns `503` while the
database is unreachable. The response lists check names and pass/fail only,
never error details. Each check has a 2-second timeout
(`health.DefaultCheckTimeout`), so a hung database or a saturated pool reports
unready instead of blocking the probe; checks run one after another.

The Docker `HEALTHCHECK` runs `/app/server healthcheck`, which loads the same
configuration as the server and requests `/health/live` (not readiness) from
`127.0.0.1` on the port in `FORGE_HTTP_ADDR` (2-second timeout). The listen
address must therefore include loopback (`0.0.0.0:PORT` or
`127.0.0.1:PORT`); binding to a single non-loopback IP makes the check fail.

Kubernetes ignores the Docker `HEALTHCHECK`. Equivalent probes:

```yaml
livenessProbe:
  httpGet:
    path: /health/live
    port: 8080
  periodSeconds: 10
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
  periodSeconds: 5
  timeoutSeconds: 3
```

Do not point the liveness probe at `/health/ready`: a database outage would
then restart every replica.

## Graceful shutdown

On `SIGTERM` or `SIGINT` the server stops accepting connections and waits for
in-flight requests to finish. Then the shutdown hooks registered with
`App.OnShutdown` run in reverse order; generated applications register
`database.Shutdown`, which closes the database pool.

The drain and the hooks share one budget, `FORGE_HTTP_SHUTDOWN_TIMEOUT`
(default `30s`), counted from the signal:

- If requests are still running when the drain deadline passes, the server
  closes their connections, which cancels their request contexts so they
  stop and release resources such as database connections. Shutdown then
  reports an error.
- The hooks' context expires at the same point. `database.Shutdown` stops
  waiting for connections still held by requests when it does, instead of
  blocking exit.

Give the orchestrator a grace period slightly longer than
`FORGE_HTTP_SHUTDOWN_TIMEOUT` so it does not send `SIGKILL` first:

- Docker Compose: `stop_grace_period`. The generated file sets `35s`, which
  covers the whole default shutdown.
- `docker stop`: `--time`/`-t`.
- Kubernetes: `terminationGracePeriodSeconds`.

Listeners close immediately on `SIGTERM`; readiness does not flip to `503`
first. If your load balancer needs time to deregister the pod, add a
`preStop` delay in the orchestrator.

## Dependency updates

Generated applications include `.github/dependabot.yml`, which checks Go
modules, GitHub Actions, and Docker base images weekly. The generated CI runs
`govulncheck` on every push and pull request.
